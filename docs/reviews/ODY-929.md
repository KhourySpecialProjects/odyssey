## Findings (most severe first)

### B1. Null due dates break the "earliest due date" pick — blocking (PR 2)

- **Where:** `frontend/lib/reminder-progress.ts:40-52` (`earliestDue`) and the
  query at `frontend/lib/requests/feed.ts:339-353`.
- **Problem:** `due-date.dueDate` is an optional `datetime`, and clearing a
  group's date writes `dueDate: null` onto the existing rows
  (`components/group/droplet-due-date-block.tsx:61` →
  `assignDropletDueDate(null, …)` → PUT `{ dueDate: null }`,
  `lib/requests/groups.ts:843-860`). `DateTime.fromISO(null).toMillis()` is
  `NaN`, so the sort comparator returns `NaN` and `Array.prototype.sort`
  leaves the order undefined.
- **Failure scenario:** a learner is in group A (date cleared, row now null)
  and group B (due tomorrow); the query has no sort, so the rows arrive in
  Strapi's order. Checked with this repo's luxon: sorting
  `["2026-11-20", null, "2026-11-14"]` returns them unchanged, so the card
  shows the 20th instead of the 14th; and when the null row lands first,
  `earliestDue` returns `{ dueDate: null }`, the card's `reminder?.dueDate`
  check fails and the chip disappears although a real date is due tomorrow.
- **Fix:** add `dueDate: { $notNull: true }` to the `/due-dates` filter (and
  optionally `sort: ["dueDate:asc"]`, as `getUserDueDates` does), and in
  `earliestDue` drop rows whose `DateTime.fromISO(dueDate)` is invalid before
  sorting. Add a test case with a null row next to a real one.

### N1. Progress text omits "· K to go" — non-blocking, confirm with Figma (PR 3)

- **Where:** `frontend/components/feed/reminder-card.tsx:123-125`.
- **Problem:** the ticket/plan acceptance criteria say
  "N of M lessons · K to go"; the card renders "N of M lessons". The
  developer decisions don't restate the string, so this may be deliberate.
- **Failure scenario:** design QA against the Figma Reminder Card flags the
  missing "K to go".
- **Fix:** if Figma has it, render
  `` `${viewed} of ${total} lessons · ${total - viewed} to go` `` and update
  `reminder-card.test.tsx`; otherwise note the deviation on the PR.

### N2. Datetime due dates are only tested as date-only strings — non-blocking (PR 2)

- **Where:** `frontend/tests/lib/reminder-progress.test.ts` (`dueChipText`
  table) and the feed test fixtures (`"2026-12-01"`).
- **Problem:** the column is a `datetime`, so real values look like
  `2026-11-14T04:59:00.000Z`. The maths handles them (they are converted into
  `now.zone` before `startOf("day")`, same as `droplet-tile.tsx:129-132`), but
  no test pins the midnight/zone behaviour the decision asks for.
- **Failure scenario:** a later refactor parses with `{ zone: "utc" }` or drops
  the zone option; an 11:30 pm ET deadline stored as next-day UTC then shows
  "Due tomorrow" on the day it's due, and no test fails.
- **Fix:** add rows like `["2026-11-13T03:30:00.000Z", "Due today"]` with
  `now` in `America/New_York`, and the same instant with `now` in
  `Asia/Tokyo` (→ "Due tomorrow").

### N3. Group/playlist feed branches have no type guard — non-blocking hardening (PR 1)

- **Where:** `frontend/lib/requests/feed.ts:135-139`.
- **Problem:** `{ group: { id: $in } }` and `{ playlist: { id: $in } }` match
  any announcement type. Reminders are private today only because nothing
  sets `group`/`playlist` on them.
- **Failure scenario:** ODY-931 creates reminders for group-assigned droplets
  and sets `group` on the row (the chip already names the group); every member
  of that group then sees, and can't mark read, another learner's reminder.
- **Fix:** add `type: { $ne: "reminder" }` (or `$in: ["group", "playlist"]`
  if those branches are meant for those types only) to both branches, with a
  feed test; or record in ODY-931 that reminders must never set
  `group`/`playlist`.

### N4. One failed side query drops both progress and due dates — non-blocking (PR 2)

- **Where:** `frontend/lib/requests/feed.ts:314-358`.
- **Problem:** `Promise.all` + one `catch` means a `/due-dates` error also
  discards the enrollment data (and vice versa). The degrade path is right
  (cards still render), just coarser than needed.
- **Fix:** `Promise.allSettled`, using whichever result fulfilled.

### N5. Contract catalogue never captures the two new queries — non-blocking (PR 2)

- **Where:** `frontend/testing/contract/strapi-query-catalog.ts:729`.
- **Problem:** the sentinel `fetchAnnouncements` call uses the default
  responder, which returns no reminder rows, so the new `/enrollments`
  (`droplet.lessons.orderIndex`) and `/due-dates` (`group.groupName`) query
  shapes are never validated against strict REST. I checked the keys by hand
  against the schemas and they exist, so this is a coverage gap, not a bug.
- **Fix:** give that call a `routes([...])` responder whose `/announcements`
  GET returns one `type: "reminder"` row with a droplet.

### N6. The unread count pays for reminder progress it never uses — non-blocking (PR 2)

- **Where:** `frontend/lib/requests/feed.ts:902-912`.
- **Problem:** `getUnreadAnnouncementCount` calls `fetchAnnouncements`, so a
  page with reminders triggers the two extra queries just to read
  `pagination.total`. Cached (900 s), and nothing renders the count yet, but
  ODY-930 will.
- **Fix:** pass an internal flag to skip `attachReminderData`, or let ODY-930
  count with its own query.

### N7. Empty `dropletIds` would drop the filter — non-blocking (PR 2)

- **Where:** `frontend/lib/requests/feed.ts:300-302, 319, 343`.
- **Problem:** if every reminder on the page lacks a droplet (droplet
  deleted), `$in: []` is serialised to nothing by `qs`, so both queries return
  all the viewer's enrollments/due dates (still the viewer's own, ≤ 250).
  Harmless output (`FeedBlock` falls back to the generic block when
  `droplet` is missing), wasted work.
- **Fix:** return `rows` early when `dropletIds.length === 0`.

### N8. "Resume" links all share one accessible name — non-blocking (PR 3)

- **Where:** `frontend/components/feed/reminder-card.tsx:155-157`.
- **Problem:** two reminders give screen-reader link lists two identical
  "Resume" links. WCAG 2.4.4 passes on context, but the links list (2.4.9)
  doesn't.
- **Fix:** `aria-label={`${label}: ${droplet?.name}`}` or visually hidden
  text, and query the link by that name in the test.

### N9. Disabled "Remind me later" gives no reason — non-blocking (PR 3)

- **Where:** `frontend/components/feed/reminder-card.tsx:139-149`.
- **Problem:** disabled is the decided behaviour, but `Button`'s
  `disabled:pointer-events-none` also blocks any tooltip, so nobody learns why
  it's dimmed.
- **Fix:** optional until ODY-932: a visually hidden "(coming soon)" or
  `aria-describedby`. Fine to leave as is if ODY-932 is close.

## Checked and fine

- **Schema ripple:** `schema.json` enum, `backend/types/generated/contentTypes.d.ts`,
  `AnnouncementType` union, `FEED_COLORS`, `FeedBlock.announcementConfig`,
  `AnnouncementTypeTitle.Reminder` and `FILTER_OPTIONS` (last). The only other
  type listing is `backend/src/lib/review-workflow.ts` (review types only).
  `draftAndPublish` untouched; no new relation.
- **Data fetching:** both new queries use `fetchAPI` (v4 header and
  flattening built in) with `next` only, never `cache`; tags are
  `CACHE_TAGS.enrollments(userId)` + `CACHE_TAGS.droplets` (viewing a lesson
  revalidates the former; lesson edits in `lesson.ts` revalidate the latter)
  and `CACHE_TAGS.allDueDates` (every due-date mutation in `groups.ts`
  revalidates it). Explicit `pageSize: 250` beats the `defaultLimit: 25`
  trap, and the input is at most the 25 droplets on one feed page. One batch
  per page, no N+1. Raw fetches in the diff keep `STRAPI_RESPONSE_FORMAT_HEADER`.
- **`reminderProgress`:** sorts by `orderIndex` (same as
  `droplet.ts:1108`), counts only viewed ids that are in the droplet (stale ids
  ignored, tested), next = first unviewed, `progress: null` when M = 0.
  `started` uses in-droplet views only, so a stale id doesn't flip
  "Start lesson 1" to "Resume".
- **Due chip maths:** calendar days in the browser zone via `useEffect`
  (no hydration mismatch), `Math.ceil` of start-of-day diff mirrors
  `droplet-tile.tsx`; > 3 days hidden, overdue shown as "One Day Late!" /
  "N Days Late!", "Due today/tomorrow/{ccc} · {group}".
- **Card vs decisions:** shows with no Up next and Resume → `/d/{slug}` for
  no enrollment / all viewed / 0 lessons; no bar when M = 0; headline from
  progress with `content` as fallback; progress bar has `role="progressbar"`,
  label and values; mark read/unread buttons have names; every colour has a
  dark variant.
- **feed-filter.tsx deletion:** `FeedFilter` had no importer outside its own
  test on develop; `feed-filter-params.ts` (still used by
  `feed-center-content.tsx` and `app/(general)/activity/page.tsx`) is kept.
