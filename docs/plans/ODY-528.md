# ODY-528: Resume where you left off

## Problem

A learner who is halfway through a droplet has no quick way back to where they stopped:

- **Continue goes to the first lesson.** `components/droplets/enroll-button.tsx:140-156` (`handleContinue`) pushes `droplet.lessons[0]`, whatever the learner has viewed. `enroll()` does the same at `:83`. `lessons[0]` is the order Strapi returns, not `orderIndex` order: the bottom button only gets sorted lessons because `page.tsx:197-198` sorts `droplet.lessons` in place first.
- **The button is at the bottom of the overview.** `app/(droplets)/d/[slug]/page.tsx:239-243` renders `<EnrollButton>` after "About the Authors". Nothing in the header (badges, title, description, `:60-121`) lets you start or continue.
- **Nothing on /activity takes you back to a lesson.** My Droplets tiles link to the overview (`components/droplets/droplet-tile.tsx:353`, `:386`), and the sort has no "recently active" option.
- The playlist page already does this ("Pick Up Where You Left Off").

## Where "viewed lessons" come from today

- **Server:** `enrollment.viewedLessons`, a manyToMany to `lesson` (`backend/src/api/enrollment/content-types/enrollment/schema.json`). `updateViewedLessons` (`lib/requests/enrollment.ts:621`) adds one lesson with `connect` and sets `isComplete`/`completionDate` when every lesson is viewed.
- **When a lesson counts as viewed:** when the learner leaves it with **Next** or **Mark as complete** (`components/droplets/footer.tsx:48-72`, `:102-122`). Opening a lesson does not mark it. So the first unviewed lesson is the one they opened and did not finish (or the next one), which is the right place to resume.
- **Client, in flight:** `stores/viewed-lessons-store.ts`. Next navigates first and saves in the background, so the footer adds the lesson to `pendingViewed[enrollmentId]` straight away. `useViewedLessonIds(enrollmentId, serverIds)` merges the pending ids with the server's. The sidebar, footer and lesson wrapper already use it.
- **Ordering:** `lesson.orderIndex` (`lessons.fields` includes it in `getCachedDropletBySlug`, `lib/requests/cached.ts:178`). The sidebar (`components/droplets/sidebar.tsx:333-334`) and the overview list sort by it. The `droplet_lesson` join type also has an `orderIndex`, but no frontend reader uses it, so this plan uses `lesson.orderIndex` like the sidebar.
- **Gating:** the lesson page uses `lessonGate` (`lib/lesson-gate.ts`, used by `droplet-lesson-wrapper.tsx` and `lesson-renderer.tsx`). It returns `enroll` with no enrollment, and `locked` when the lesson whose `orderIndex` is one lower isn't viewed (authors and admins skip both). The sidebar does the same by sorted position (`sidebar.tsx:336-345`). The first unviewed lesson by `orderIndex` is always open under both rules: any lesson with a lower `orderIndex` comes before it in the sort, so it is viewed by definition. That holds with gaps or repeated `orderIndex` values too. So Resume can never point at a locked lesson.
- **ODY-786 (feed read per user)** is not on develop: no commit, file or branch mentions it. From its title it tracks announcement read state in the feed, not lesson views, so it gives Resume nothing to use. It does touch the same page as the Continue learning row (`/activity`), so whoever lands second rebases the page layout.

## Acceptance Criteria

- [ ] For an enrolled learner, the overview's primary button goes to the first lesson by `orderIndex` that is not in their viewed lessons, and reads `Resume: {lesson name}`.
- [ ] An enrolled learner who has viewed nothing sees `Start: {first lesson name}` (see Q1). One who has viewed every lesson sees `Review` and goes to the first lesson (see Q2).
- [ ] Viewed ids that are not lessons of this droplet (lessons are shared between droplets) are ignored.
- [ ] Right after Next (save still in flight), opening the overview from the sidebar shows the following lesson, not the one just finished.
- [ ] A learner who is not enrolled still sees `Enroll and Continue`, and enrolling goes to the first lesson by `orderIndex` (not Strapi's return order).
- [ ] The overview header shows the Enroll/Resume button under the title and description. The bottom button stays.
- [ ] `/activity` shows a "Continue learning" row above the feed with up to 4 incomplete, unarchived enrollments, newest `updatedAt` first, each linking straight to `/d/{droplet}/{next lesson}`. With none, the row doesn't render.
- [ ] My Droplets has a "Recently Active" sort that orders by the enrollment's `updatedAt`, newest first. A-Z stays the default.
- [ ] No new cache tag. Resume and the row are fresh after a lesson is viewed, because they read `CACHE_TAGS.enrollments(userId)`, which `updateViewedLessons` already invalidates.
- [ ] No new export in any `"use server"` file. The server-action auth guard test passes with no allowlist changes.

- Signed-out visitors on the overview: the button behaves as today.

- Making "Recently Active" the default sort (Q4).
- Tracking "last opened lesson" separately from "viewed". `updatedAt` and viewedLessons are the only signals; no schema change.
- The odd author-enrollment check in `enroll()` (`enroll-button.tsx:61-68`).

## Design Decisions

1. **One pure helper decides the target: `lib/resume-lesson.ts`.** `resumeTarget(lessons, viewedLessonIds)` returns `{ kind: "start" | "resume" | "review", lesson }` or `null` when there are no lessons. It sorts a copy by `orderIndex`, then `id` for ties, and never mutates its input. It is a plain module with no server imports, so the client `EnrollButton` and the server Continue learning row both use it. Putting it in a `"use server"` file would make it a public endpoint that needs auth. It lives next to `lib/enrollment-completion.ts`, which is already the shared home for progress maths (`enrollmentProgressPercent`). Alternative rejected: computing the target on the server and passing a slug to the button. That can't see the in-flight store, so the overview would be one lesson behind right after Next.
2. **The button computes Resume on the client from server data plus the pending store.** The overview page passes `enrollmentId` and `viewedLessonIds` (from the enrollment it already fetches). The button runs `useViewedLessonIds(enrollmentId, viewedLessonIds)` and then `resumeTarget`. This is the same merge the sidebar uses, so the overview and the sidebar agree.
3. **Header button: the same component with a `placement` prop.** `placement: "header" | "footer"` (default `"footer"`) is added to the PostHog events, so we can see which button people use. The header copy hides Unenroll (`showUnenroll={false}`, see Q3) so the top of the page has one clear action. Two `EnrollButton`s on the page are safe: the PostHog init is guarded by `window.posthog`.
4. **No new cache tag.** The overview reads lessons from `getCachedDropletBySlug` (`CACHE_TAGS.droplets`, invalidated by `addLesson`/`updateLesson`/`deleteLesson`/`updateDroplet`) and viewed lessons from `getCachedEnrollmentsWithLessonIds` (`CACHE_TAGS.enrollments(userId)` + `allEnrollments`). The Continue learning read goes through the same `getEnrollmentsByAuthorizedUser`, so it carries the same two tags. `updateViewedLessons` calls `revalidateTag(CACHE_TAGS.enrollments(authorizedUser.id))` whenever a lesson is newly viewed or the droplet completes. Enroll, unenroll, archive and rating already invalidate the same tag. The client router cache can't serve stale pages here (`next.config` `staleTimes.dynamic: 0`).
   - **Known limit, unchanged by this ticket:** `revalidateTag` clears only the Next instance that served the write (`docs/agent/data-fetching.md`, ODY-881 note). With several ECS tasks, another instance can show Resume one lesson behind for up to 900 s. The sidebar's progress has the same exposure today. Within one tab, the pending store covers the common case (straight back from a lesson). We are not switching these reads to `no-store` (Q5).
5. **"Recently active" means the enrollment's `updatedAt`.** Every write to the enrollment updates it: a lesson viewed (`connect` is a PUT on the enrollment), first-time flag, rating, archive, completion. Opening a lesson without pressing Next does not. That is close enough to "last active" and needs no schema change. `updatedAt` is added to `getEnrollmentsByAuthorizedUser`'s default `fields` and to the `Enrollment` type. It's one column, and every preset needs it for the sort.
6. **The Continue learning row reads its own small query.** A new `ENROLLMENT_POPULATES.resume` preset (droplet `id,name,slug` + lessons `id,name,slug,orderIndex`, viewedLessons `id`) and a `getCachedContinueLearning(userId)` wrapper in `lib/requests/cached.ts` that calls `getEnrollmentsByAuthorizedUser` with `sort: ["updatedAt:desc"]`, `filters: { isComplete: { $eq: false } }` and `pagination: { page: 1, pageSize: 25 }`. Archived enrollments are dropped in JS (`isArchived !== true`, because old rows can hold `null` and `$ne: true` would skip them in SQL), along with enrollments whose `resumeTarget` is `null` or `"review"` (legacy rows with every lesson viewed but `isComplete` false). Then it takes the first 4. Not reusing the `dashboard` preset: it lacks `orderIndex` and pulls tags, authors and descriptions the row doesn't render.
7. **The row is on the feed tab only, above the feed.** It goes in `app/(general)/activity/page.tsx` in its own `<Suspense fallback={null}>`, so it never delays the feed. Not in `activity/layout.tsx`: it would repeat on My Droplets, Favorited and the other tabs. The feed tab is a fixed-height, `overflow: hidden` column (`components/feed/feed-container.tsx:91-94`) whose list scrolls inside `FeedCenterContent` (`flex h-full flex-col`). So the page wraps both in `flex h-full flex-col`: the row is `shrink-0` and the feed sits in `min-h-0 flex-1`. Otherwise the row pushes the feed's scroll area off screen.
8. **Server-action auth: nothing new to guard.** The new code is a plain helper module, a cached wrapper (`cached.ts` has no `"use server"`) and Server Components. `getEnrollmentsByAuthorizedUser` is already allowlisted (`PENDING_AUTH`, ODY-507). Calling it from a Server Component is a server-to-server call, and the user id comes from `getAuthorizedUserId(user)`, never from the client. Do not add an exported function to `lib/requests/enrollment.ts` for this. If one is ever needed, it must use `withAuth([])` and take the user from `gate.user.id`, with no `PENDING_AUTH` entry (`docs/agent/server-action-auth.md`).

## Open Questions for Awad

1. **Enrolled but nothing viewed: `Start: {lesson}` or `Resume: {lesson}`?** Recommend `Start:`. "Resume" for a droplet never begun reads wrong, and it's the same code path.
2. **Every lesson viewed: where does the button go?** Recommend `Review` → first lesson (today's behaviour, no new route). Alternative: `/d/{slug}/recap`.
3. **Header button: show Unenroll there too?** Recommend no. Keep one primary action at the top, and Unenroll stays at the bottom.
4. **Make "Recently Active" the My Droplets default?** Recommend not in this ticket. Ship it as an option and look at PostHog sort usage first. Changing the default is a one-line follow-up (reorder `sorting` or set `defaultSort`).
5. **Accept up to 900 s of staleness on other ECS instances?** Recommend yes. It's the same as the sidebar's progress today, and the pending store covers the same tab. `no-store` would put a Strapi round trip on every overview and /activity load.
6. **How many cards in Continue learning, and include enrolled-but-not-started droplets?** Recommend 4, and include not-started ones (labelled `Next: {first lesson}`), since enrolling shows intent and it's the same query.
7. **Should the row hide droplets that ODY-660 later hides?** Recommend yes, with ODY-660's predicate, as a small follow-up once ODY-660 is on develop. Jaylen owns the rule, so this plan doesn't guess it.
