# ODY-282: Incorporate logging (2 or 3 levels) into code base

Linear: ODY-282 · Infrastructure · 4 pts · **Blocked by ODY-499**

## TL;DR

- **What:** structured JSON logs in both apps. The frontend uses pino; the backend uses Strapi's winston, reconfigured.
- **Why:** today's logs are unstructured, leak PII, and can't link a frontend failure to the Strapi request behind it.
- **Where:** CloudWatch only (the existing 30-day retention). No S3, no terraform changes.
- **Correlation:** a W3C `traceparent` header, generated once per server render. Its trace-id is the `requestId` in both apps' logs.
- **Errors:** uncaught server errors are logged via `instrumentation.ts`. Users see an "Error ID". Browser errors go to PostHog.
- **PII:** emails, names, tokens and request/response bodies are never logged.
- **Prerequisite:** ODY-499 moves `fetchAPI` into server-only `lib/api.ts`, and must merge first.
- **Size:** 14 small tasks (one commit each). The backend and frontend groundwork can run in parallel.

## 1. Problem

**Frontend**

- About 382 unstructured `console.*` calls, 231 of them in `lib/requests/*`.
- `fetchAPI` logs the response **body**, then throws a generic error that drops the path.
- Uncaught server errors only reach Next's default stderr.
- Error boundaries only `console.error` in the browser. Users have nothing to quote in a bug report.
- Known PII leaks:
  - `lib/requests/authorized-user.ts:742` logs a user's email.
  - `lib/requests/droplet.ts:629-925` dumps full Strapi responses.
  - `lib/actions.ts:374, 567, 718` log raw Linear/Strapi response bodies.
  - `lib/actions.ts:206` returns a raw `Error` object to the client.

**Backend**

- Strapi's default logger (`level: "silly"`, colorized) drops all metadata and stack traces.
- The request line logs the full URL including the query string, which can contain emails.
- None of it is JSON.

**Correlation**

- Nothing links a frontend failure to the Strapi request behind it.
- Both apps already ship stdout to CloudWatch, but nothing there is searchable.

## 3. How correlation works

**Header format:** `traceparent: 00-{trace-id}-{span-id}-01`

- `trace-id` is 32 lowercase hex characters, never all zeros. It becomes the **`requestId`**.
- `span-id` is 16 lowercase hex characters, never all zeros.

**Frontend**

- `lib/api.ts` defines `getRenderTraceparent = cache(createTraceparent)`.
- fetchAPI and `strapiHeaders()` send it on every call, reads and writes alike.
- An existing valid `traceparent` is never overwritten; its trace-id is reused.

**Backend**

- The middleware parses `traceparent`. If it's missing or invalid, it generates a new id.
- It echoes the id back as the `x-request-id` response header.
- It stores `{ requestId, userId }` in AsyncLocalStorage, and every log line picks them up.

**Scope of one id**

| Context                                                     | One `requestId` per… |
| ----------------------------------------------------------- | -------------------- |
| RSC page render (layout, page, metadata, nested components) | render               |
| Server Action body, route handler, NextAuth callback        | Strapi call          |

The "per call" row is the expected behavior; Task 7 verifies it.

**What this gives us**

- Page-level grouping without making pages dynamic, because `cache()` reads no cookies or headers.
- The Next data cache still hits, because Next strips `traceparent` from its cache key.
- Identical fetches in one render are still de-duplicated, because they carry identical headers.

**Limits**

- Cache hits never reach Strapi, so those frontend lines have no backend twin. Failures are never cached, so every failed call has both sides.
- The span-id is fixed per render. That's a pragmatic use of the header: a correlation id, not real spans.
- `onRequestError` runs outside the render's `cache()` scope, so its line has no `requestId`. Join it by `digest`, `route`, `path` and time.

## 4. Log schema

The same field names are used in both apps, so one Logs Insights query covers both log groups.

| Field       | Type                                                                                                       | Frontend (pino)                                          | Backend (winston)                             |
| ----------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------------------- |
| `timestamp` | ISO-8601 string                                                                                            | custom `timestamp` function                              | `format.timestamp()`                          |
| `level`     | `error`/`warn`/`info`/`debug`                                                                              | `formatters.level` (outputs the label, not a number)     | default                                       |
| `message`   | short static string                                                                                        | `messageKey: "message"`                                  | default                                       |
| `service`   | `frontend` / `backend`                                                                                     | `base: { service: "frontend" }` (drops `pid`/`hostname`) | `service()` format                            |
| `requestId` | 32-hex trace-id                                                                                            | set in fetchAPI/actions lines                            | from AsyncLocalStorage                        |
| `userId`    | number (Strapi authorized-user id)                                                                         | when the caller passes it                                | parsed from `x-odyssey-user-id` (digits only) |
| `err`       | `{ type, message, stack }`                                                                                 | pino `err` serializer                                    | `normalizeError()` format                     |
| context     | `method`, `path`, `status`, `durationMs`, `route`, `routeType`, `digest`, `authStrategy`, `bytes`, `event` | ✓                                                        | ✓                                             |

**Conventions**

- `message` is static (e.g. `"strapi request failed"`).
- Variable data always goes in fields. Never interpolate values into `message`.
- Log errors as `{ err }`.
- Never log whole objects. Log ids and slugs instead.

## 6. Acceptance criteria

These are proposed. The user will copy them into Linear.

- [ ] A structured logger is integrated in the **frontend** (pino, server-only `lib/logger.ts`) and the **backend** (winston via `config/logger.ts`). Production uses `error`/`warn`/`info` and local dev uses `debug`, all controlled by `LOG_LEVEL`.
- [ ] **Logs are structured JSON in CloudWatch (existing 30-day retention) and searchable by requestId / userId in CloudWatch Logs Insights.** Both apps use the same field names.
- [ ] There's enough context to reconstruct a failure:
  - Every Strapi request produces one backend line: `{requestId, userId?, method, path, status, durationMs}`.
  - Every failed fetchAPI call produces a frontend line with the **same** `requestId`, plus `method`, `path`, `status`, `durationMs`.
  - Uncaught server errors are logged with `route`, `routeType`, `method`, `path`, `digest`, `err`.
- [ ] It fires on failure: a Strapi exception, a non-2xx fetchAPI response, a thrown Server Component error, and a browser exception (PostHog `$exception`) each produce a record.
- [ ] Error boundaries show `Error ID: <digest>`, and the same digest is in CloudWatch.
- [ ] No email, name, token, cookie, password or body appears in logs. Redaction is unit-tested in both apps.
- [ ] Cached fetches still hit, and identical fetches in one render are still de-duplicated (checked manually). Existing return values are unchanged. `/ci` passes.

### Task 1: Backend context store and log formats

**Goal:** the pure building blocks for backend logging.

**Files:** create `backend/src/lib/request-context.ts` and `backend/src/lib/logger-formats.ts`. Read `backend/src/lib/slack.ts` for style.

**Changes**

- `request-context.ts`:
  - `requestContext`: an `AsyncLocalStorage<{ requestId: string; userId?: number }>`.
  - `parseTraceparent(v)`: returns the trace-id, or `undefined` when the value is invalid. The rules are in Appendix A (strict W3C).
  - `generateTraceId()`: 32 hex characters from `randomBytes(16)`, never all zeros.
  - `sanitizeUserId(v)`: accepts only `/^\d{1,12}$/` and returns a number.
- `logger-formats.ts`: import `winston` from `@strapi/logger`. It's the official pattern, so don't add winston directly.
  - `REDACT_KEYS`, matched case-insensitively:
    - Exact keys: `email`, `name`, `username`, `firstName`, `lastName`.
    - Substring keys: `token`, `password`, `authorization`, `cookie`.
  - `redact()`: a deep walk (max depth 6, cycle-safe, including arrays) that replaces matches with `"[REDACTED]"`. It skips winston's Symbol keys.
  - `requestContextFormat()`: adds `requestId`/`userId` from the store.
  - `normalizeError()`: turns an Error, or `meta.err`, into `err: { type, message, stack }` and removes the top-level `stack`.
  - `service()`: adds `service: "backend"`.
  - `buildLogFormat()`: returns `errors({stack:true}) → requestContext → normalizeError → service → timestamp → redact → json`.

**Tests:** in Task 6.

**Done when:** it compiles and the Task 6 tests pass.

## Appendix A: Verified facts and sources

All versions below are the installed ones: Next 15.5.9, Strapi 4.25.24, winston 3.10, posthog-js 1.234.4.

### Next.js caching and trace headers

- **Data-cache key:** `next/dist/server/lib/incremental-cache/index.js:236-246` builds the key from all request headers, but deletes `traceparent` and `tracestate` first.
- **Per-render de-dupe:** `next/dist/server/lib/dedupe-fetch.js:66-75` keys on **all** headers and strips nothing. That's why the traceparent is generated once per render.
- **Concurrent identical cached fetches** are coalesced by the incremental-cache lock (`patch-fetch.js`, `handleUnlock`).
- `patch-fetch.js` never sets `traceparent` itself.
- `x-odyssey-user-id` **is** in both keys. That's why it must never go on shared fetches.

### Why Server Actions need `strapiHeaders()`

- `lib/actions.ts` has 0 fetchAPI calls and 15 raw `fetch()` calls (14 to Strapi, 1 to Linear).
- `.claude/rules/server-actions.md` requires raw fetch for mutations.

### User identity

- `getCurrentUser()` (`lib/auth/session.ts:27`) has no Strapi id.
- The id comes from `requireRole()` (`lib/auth/require-role.ts`) or from explicit arguments.
- It's the same id PostHog uses in `identify()` (`providers/PHProvider.tsx:25`).

### PostHog

- `components/providers/posthog-provider.tsx` is dead code.
- The live provider is `providers/PHProvider.tsx` (imported in `app/layout.tsx:3`).

  - So `userId` comes only from the header, and `authStrategy` is read after `next()`.

- `backend/tsconfig.json` excludes `**/*.test.*`.
- The backend has no test setup today. CI tests only the frontend.
