# ODY-660: Make droplet `isHidden` a real takedown (404 at URL, no listing leaks)

Branch: `feature/ody-660-make-droplet-ishidden-a-real-takedown-404-at-url-no-listing` (cut from `feature/strapi-v5`: Strapi 5.56, D&P off, frontend sends `Strapi-Response-Format: v4`). Related: ODY-659 (null droplet relations), ODY-633 (D&P off), ODY-603 (cutover), ODY-507 / ODY-503 (server-action auth).

**Comment rule for the implementer:** code comments and JSDoc are 1-2 lines max. No multi-paragraph blocks.

## Problem

With D&P off, the Strapi admin has no Unpublish. Odyssey's own fields (`isHidden`, `status`) only remove a droplet from _some_ listings:

- `/d/[slug]`, its lesson pages, recap and present never check either field. `getCachedDropletBySlug` (`frontend/lib/requests/cached.ts:179`) has no filter, and the routes only `notFound()` on a missing droplet.
- The lesson route never checks that the lesson belongs to the droplet in the URL.
- Several listings show hidden or unpublished droplets.
- `updateDroplet` doesn't clear every cache that holds droplet visibility.

`[EDIT]` copies (`duplicateDroplet`) are `status:"draft", isHidden:false`, so they are open at `/d/<slug>` to anyone signed in. Voyage-claim droplets are `status:"draft", isHidden:true`.

**This is not a cutover blocker (ODY-603).** `[EDIT]` copies and hidden droplets are already reachable by URL on production v4. Strapi v4.22's core create service sets `publishedAt = new Date()` when the request doesn't send it, and `duplicateDroplet` never sent it. So the cutover only removes the admin's Unpublish switch.

### Why this is deliberately weaker than Unpublish

On production (v4), droplet requests never send `publicationState=preview`. So Unpublish 404'd **everyone**, including authors and staff, and nulled the droplet inside enrollment relations. `isHidden` is mainly written by authors archiving their own droplets (my-content "Archive" → `setDropletHidden`, `components/droplets/droplet-tile.tsx:132`). Cutting enrolled students off would take away their recap notes every time an author archives. So enrolled users keep a hidden droplet, and true emergencies still use delete.

## Access rule (single source of truth)

A droplet is **listed** when `isHidden === false && status === "published"`.

A viewer may open `/d/[slug]` (and its lesson, recap and present pages) when any of these is true:

1. The droplet is listed.
2. The viewer is an author (`authorized_users` contains their id).
3. The viewer is staff (SysAdmin or ContentEditor).
4. The droplet is `status === "published"` and hidden, and the viewer is enrolled in it.

Unpublished droplets (`draft` / `edit` / anything not `"published"`) pass only for authors and staff.

**Which rule each listing uses:**

- **Full viewer rule** (`canViewDroplet`): the group page droplet list and due dates (G2), and voyage node links (G4).
- **Shown in full:** the group Progress tab shows every group droplet as unlinked columns (G3).
- **Kept on purpose:** the viewer's own enrollment-based dashboard grids keep hidden droplets. That's how enrolled users still reach them.
- **Listed only, for everyone:** every other listing.

- [ ] Authors and staff (SysAdmin, ContentEditor) can open hidden and unpublished droplets. Enrolled users can open published-but-hidden droplets.

## Design Decisions

- **D1. One pure rule module.** New file `frontend/lib/droplet-visibility.ts` (no `"use server"`, no fetches) holds the access rule, the Strapi filter constant and the viewer-aware group helper. Every route, listing and action uses it, so the rule lives in one place.
- **D2. Route gate = one cached helper.** `getCachedViewableDropletBySlug(slug)` goes in `cached.ts` and returns the droplet, or `null` when it's missing or the viewer isn't allowed.
  - Every route **and** every `generateMetadata` under `/d/[slug]` swaps `getCachedDropletBySlug` for it. Layout-only gating isn't enough: Next renders the layout and page in parallel, the layout doesn't re-run on soft navigation, and metadata would leak the name.
  - Enrollments are only fetched on the rare unlisted path. They dedupe with the routes' own `getCachedEnrollmentsWithLessonIds` call.
  - It lives in `cached.ts`, which already has the private `getUserIdForEmail`. Importing `lib/auth/current-user-id.ts` there would be a circular import (that file imports `cached.ts`).
- **D3. Roles source.** Pages read `getCurrentUser().roles` (session plus dev override), as the draft layout does (`app/(editing)/draft/d/[slug]/layout.tsx:59-69`). Server actions read `gate.user.roles` from `requireRole` (Strapi roles).
- **D4. `status` is strictly `"published"`.** Status is required, and `"draft"` is the default in the v5 schema. Explore already filters on `status: "published"` with no null branch. Recap's legacy `$or [published, $null]` is replaced. A null-status droplet would now be unlisted and author/staff-only; the manual check below confirms there are none.
- **D5. Where each listing filters.**
  - **In the Strapi query** when the query is used only by that page: recap, prerequisites, playlist page, profile "Created", add-droplet dialog, feed, voyage playlist-droplet counts.
  - **In page code** when an editor saves what it loaded:
    - Groups: `updateGroup` replaces the group's droplets with whatever list it's sent, so a filtered query would drop hidden droplets on save.
    - The playlist editor populate (`draft/p/[slug]/page.tsx`) is never filtered, for the same reason.
  - **In page code** for one-to-one relations: profile "Completed" filters `enrollment.droplet` in code rather than relying on populate filters.
- **D6. Feed** filters at the top level of the announcements query (`droplet` is null **or** listed), so hidden droplets don't leave blank feed items.
- **D7. Voyage nodes stay in the tree.**
  - A droplet node whose droplet fails `canViewDroplet` gets no link anywhere (tree map, journey list, "Continue Voyage"), and its subtitle reads "Unavailable".
  - The check is listed, author, staff, or enrolled in a published-but-hidden droplet. Enrollment comes from one cached `getCachedEnrollmentsWithLessonIds(userId)` call per page (G4).
  - Unclaimed nodes (no droplet) keep their `/unclaimed/` link.
- **D8. Enrollment writes check fresh data.** `createEnrollment` and `enrollUsers` read visibility with `cache: "no-store"` through a new non-`"use server"` module, `frontend/lib/requests/droplet-access.ts`.
  - It can't live in `enrollment.ts`: `droplet.ts` imports `enrollment.ts`, so importing `getDropletById` there would be circular.
  - It can't be exported from a `"use server"` file either: every export there becomes a public action the guard test would flag.
- **D9. ODY-507 collision avoidance (createEnrollment).** ODY-507 is still open:
  - All 15 `enrollment.ts` entries are still in `PENDING_AUTH` (`frontend/testing/security/server-action-auth-allowlist.ts:105-120`), and there's no ODY-507 plan in `docs/plans/`.
  - This ticket touches **only** `createEnrollment` and deletes **only** its line (`"lib/requests/enrollment.ts#createEnrollment": "ODY-507"`, line 108). The `// ODY-507` header and every other entry stay.
  - Use the canonical pattern from `docs/agent/server-action-auth.md`: `requireRole([])`, caller identity from `gate.user`, errors `"unauthenticated"` / `"forbidden"`. ODY-507 then has nothing to redo for this function.
  - Don't refactor shared helpers in `enrollment.ts`.
  - If ODY-507 lands first, keep its guard and add only the visibility check.
  - After merge, the user notes on ODY-507 (by hand) that `createEnrollment` was guarded in ODY-660.
  - `enrollUsers` (ODY-503) gets the visibility filter only, no guard, so its allowlist entry stays.
- **D10. Cache.**
  - **What gets swept:** when `data.isHidden !== undefined || data.status !== undefined`, `applyDropletUpdate` also sweeps `voyages`, `tags`, `announcements` and `users`.
  - **Bypassing the draft-save skip:** `isDraftSave` becomes false whenever `isHidden` is set, so `playlists`, `allGroups` and `allUserDashboards` are swept too.
  - **Why `users` rather than per-author tags:**
    - `users` is the default tag on the profile page's `getAuthorizedUserByEmail` read. Per-author `user(email)` would need author emails inside `applyDropletUpdate`.
    - Visibility flips are rare, so sweeping the global tag is cheap.
- **D11. Group page has two views of the same group** (G2, G3).
  - **Visible view:** the page builds `visibleGroup = withViewableGroupDroplets(group, viewer, enrolledDropletIds)`. That feeds the Droplets / Playlists / Voyages tabs and the due dates.
  - **Progress view:** the unfiltered `group` goes to `GroupProgressGrid` through a new optional `progressGroup` prop on `GroupDashboard`. Member enrollments are still fetched for every group droplet.
  - **Columns are already unlinked:** `GroupProgressGrid` renders droplet names as a plain `<span>` (`components/group/group-progress-grid.tsx:397-405`), so no link change is needed there.
  - **Viewer enrollment:**
    - If the viewer is a group member, take their rows from the `getEnrollmentsForGroupMembers` result the page already loads.
    - Otherwise call `getCachedEnrollmentsWithLessonIds(authorizedUser.id)`.
    - If the members' fetch fails (it's inside the existing try/catch), treat the viewer as not enrolled. This fails closed.
- **D12. Toast copy** (G1).
  - The copy changes only in the **creator** branch of `droplet-tile.tsx` `changeVisibility` (the `creatorArchive` → `setDropletHidden` path) and in the admin hide/show toggles.
  - The learner's own enrollment archive (`archiveDroplet`) keeps "is now archived!" / "is now unarchived!". "No new learners can enroll" would be wrong there.

## Edge Cases

- **`[EDIT]` copies:** author/staff-only. Authors previewing a copy still enroll and pass. `publishDraftToOriginal` moves those enrollments to the original.
- **Voyage-claim droplets** (draft + hidden): the claimer is an author, so they pass.
- **Legacy `status:"edit"` rows** count as unpublished.
- **A droplet that is published, then hidden, then unhidden** behaves normally again once the cache is swept.
- **An enrolled user of a hidden droplet:**
  - can open the overview, lessons, recap and present (present still needs `presentationEnabled`);
  - sees it on group pages and voyage nodes;
  - doesn't see it in other listings or the feed.
- **Group page, enrolled vs not:** a group creator or admin who isn't enrolled and isn't staff doesn't see a hidden droplet in the Droplets tab, but does see it as a Progress column.
- **Wrong droplet slug in a lesson URL:** `/d/<listed-droplet>/<lesson-of-another-droplet>` → 404, even for staff.
- **A lesson whose slug is `present`** is shadowed by the static `present` segment. That's pre-existing and not touched here.
- **"Continue Voyage" button:** if the first incomplete node is unavailable, `firstIncompleteHref` is `undefined` and the button hides. Accepted.
- **Enroll callers:** `EnrollButton` (`components/droplets/enroll-button.tsx:69`) and `components/first-time/first-visit-popup.tsx:124` must handle `{ ok: false, error: "forbidden" }` without crashing.
