# ODY-622: Publishing a droplet edit deletes and recreates every lesson, wiping student progress

Linear: https://linear.app/aiil/issue/ODY-622 · Urgent · Labels: Bug, Critical Functionality Issues
Branch: `bug/ody-622-bug-publishing-a-droplet-edit-deletes-and-recreates-every` (cut from `develop` @ 282c5e68)

Revised after planning with findings from two late research reports, each checked against the code. Those points are marked "verified after planning".

## Problem

When an author publishes an `[EDIT]` draft over a live droplet, `publishDraftToOriginal` (`frontend/lib/requests/droplet.ts:980`) does not update the live lessons. It deletes all of them and creates new ones from the draft, with new ids and new slugs. Every student enrolled in that droplet is affected:

- Their `viewedLessons` lose every link, because Strapi deletes the join rows along with the lessons. In-progress students drop to 0%, and "Continue" and the sidebar start over. `isComplete` survives.
- Saved lesson URLs return 404.
- Their notes and highlights (`note.lesson`, `highlight.lesson`) are orphaned.

This happens on every normal publish of an edit. It also happens through the "Review" button bug (ODY-521).

## Acceptance Criteria

- [ ] Publishing an `[EDIT]` draft keeps the **id and slug** of every live lesson that is still in the draft, including renamed and reordered lessons.
- [ ] **(Ticket test)** An enrollment's progress is identical before and after `publishDraftToOriginal` when the edit removes no lesson. Progress means `viewedLessons` ids ∩ the droplet's lesson ids.
- [ ] Notes and highlights on kept lessons stay attached. Lesson update payloads never contain `notes`, `highlights`, `enrollments`, `droplets`, `lockedBy`, `lockedAt` or `slug`, and never a truthy `regenerateSlug`.
- [ ] Changed lessons are updated in place. Only the fields that changed are sent (`name`, `type`, `orderIndex`, `blocksVersion`, content). Unchanged lessons get no write.
- [ ] A lesson added in the draft is created in the live droplet at the right `orderIndex`.
- [ ] A lesson removed in the draft is deleted from the live droplet, and only after every update and create has succeeded.
- [ ] If any write fails, publish returns `{ ok: false, error }`. The draft is kept and the draft's enrollments are not moved.
- [ ] Publishing again after a failure reaches the intended final state, with no duplicate lessons.
- [ ] Draft and original are read fresh (`cache: "no-store"`) during publish.
- [ ] Publishing a draft with **zero lessons** over a live droplet that has lessons is rejected before any write (assumption A2).
- [ ] New `[EDIT]` drafts record `originalLessonId` on each cloned lesson.
- [ ] Cache invalidation is unchanged; the existing `finally` block handles it.
- [ ] `publishDraftToOriginal` keeps its signature and its `{ ok, error, slug }` return shape. `droplet.ts` gains no new exports.

## Design Decisions

**D1. Update lessons in place instead of recreating them and remapping ids.**

- Recreating can never keep slugs, because `beforeCreate` regenerates them.
- Remapping would need a PUT for every enrollment, note and highlight in the droplet, and each of those writes can fail.
- In-place updates keep every id-keyed record without touching it.

**D2. Lineage field `Lesson.originalLessonId`, a nullable integer.**

- It mirrors `Droplet.originalDropletId`, which is a plain integer, not a relation.
- `duplicateDroplet` sets it to the source lesson's id.
- It is not private, so the REST read in publish returns it.
- Live lessons never get it. Update and create payloads never include it.
- This is a schema change, so Task 1 follows the schema-change checklist.

**D3. Match by lineage first, then by exact name. Never by position.** The matching lives in a pure function, `planLessonSync`:

1. Sort draft lessons by `(orderIndex ?? 0, id)`. A lesson's position in that order is its target `orderIndex` (0..n-1), the same as today.
2. **Lineage pass, over all draft lessons:** if `originalLessonId` names a live lesson that is still unclaimed, claim it.
3. **Name pass, over the still-unmatched draft lessons in draft order:** claim the first unclaimed live lesson whose `name.trim()` matches exactly. Live lessons are sorted by `(orderIndex ?? 0, id)`.
4. Draft lessons still unmatched are **created**. Unclaimed live lessons are **deleted**.

The name pass covers three cases:

- `[EDIT]` drafts created before this ships.
- A frontend running against a backend that lacks the field.
- Retries, which then converge: a lesson created by a failed earlier attempt is matched by name instead of being duplicated.

Two editor behaviors matter here (verified after planning). "Add Existing Lesson" names its copy `<name> (Copy)` (`lesson.ts:414`), so a copy never name-matches its source. A lesson deleted in the draft and re-created with the same name is matched by name and keeps its progress, the same as an in-place content edit.

Why not match by position: position matching silently attaches progress, notes and highlights to the wrong content as soon as an author inserts, deletes or reorders a lesson. Name matching only fails on a rename, and then that one lesson falls back to today's behavior.

| Edit in a draft with no lineage         | By position                            | By name                            |
| --------------------------------------- | -------------------------------------- | ---------------------------------- |
| Content edits / add at end              | correct                                | correct                            |
| Insert, delete or reorder in the middle | **wrong content mapped**               | correct                            |
| Rename                                  | correct                                | that lesson resets (same as today) |
| Rewrite everything                      | **progress kept on unrelated content** | resets (same as today)             |

**D4. Field-level diff.** For each matched pair, compare these fields and send only the ones that differ:

- `name`.
- `type`, only when the draft's value is defined.
- `orderIndex`, compared against the target index.
- `blocksVersion`, treating a missing value as `"v1"`.
- Content, using today's create rule:
  - If `blocksVersion === "v2"` and `blocksV2 != null`, compare `blocksV2` with `isEqual` and send it.
  - Otherwise, compare `blocks` with every `id` key stripped recursively on both sides, and send `cleanLessonBlocks(draft.blocks ?? [])`.

Comparisons use `lodash/isEqual`; `lodash` is already a direct dependency.

This has two effects:

- Unchanged lessons get no write, so they can't fail mid-publish.
- A reorder-only or rename-only change doesn't rebuild a v1 lesson's dynamic-zone components. That keeps the component ids that v1 highlights anchor to (verified after planning: a v1 highlight's `blockId` is that component id).

**D5. Write order: a failure never leaves students worse off.**

| #   | Step                                                                                                                                                                                  | On failure                                                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 0   | Read draft + original fresh, run the guards, build the plan. No writes.                                                                                                               | nothing written                                           |
| 1   | `updateDroplet(original)` with the existing metadata payload. This is the most likely validation failure, so it runs first. It remains raw fetch #2, after the draft-enrollments GET. | throw; no lesson touched                                  |
| 2   | PUT the changed fields on matched lessons, sequentially                                                                                                                               | throw; mixed old/new content, nothing deleted, draft kept |
| 3   | POST new lessons, sequentially                                                                                                                                                        | throw; same as above                                      |
| 4   | DELETE removed lessons via `deleteLesson(id, false)`. Attempt all, then throw if any failed.                                                                                          | throw; an extra lesson stays visible, draft kept          |
| 5   | Move the draft's own enrollments. The existing code moves from before the lesson writes to here.                                                                                      | logged (as today)                                         |
| 6   | `deepDeleteDroplet(draft)` (unchanged)                                                                                                                                                | logged (as today)                                         |

Publishing again after any failure is safe:

- Updates are idempotent.
- Lessons created in an earlier attempt are matched by name (D3).
- Deletes are recomputed from a fresh read.

Error messages tell the author to publish again, for example: `Publishing stopped partway (lesson "X": <Strapi message>). No lessons were removed. Publish again to finish.`

**D6. Fresh reads.** Add an optional third parameter `{ fresh?: boolean }` to `getDropletById`. This mirrors `getLessonBySlug(slug, params, { fresh })` (`lesson.ts:24-58`).

- `fresh: true`: pass `cache: "no-store"`.
- Otherwise: pass the existing `next`.
- Never pass both; Next 15 treats them as mutually exclusive.

Publish uses `fresh: true` for both reads. Without it, change detection could compare against cached draft content and silently skip the author's edits. (A first attempt usually misses the cache, because only publish builds that URL. A retry after an early failure, or an expired entry that Next serves stale while it refreshes, can still return old content.)

**D7. Guards before any write**, next to the existing difficulty guard:

- (a) The draft has 0 lessons and the original has at least 1. Error: `This draft has no lessons. Add at least one lesson before publishing.`
- (b) A planned update whose `changes.blocks` is an empty array. Error: `Lesson "<name>" has no content. Add content or delete the lesson before publishing.` Strapi's `beforeUpdate` would reject this anyway, but only mid-publish.

**D8. Code shape that avoids conflicts with ODY-504.**

- The pure planner and block helpers go in a new **`frontend/lib/lesson-sync.ts` with no `"use server"`**, the same way `lib/enrollment-completion.ts` is built. The auth guard test only scans files whose first statement is `"use server"`, so this module can export freely.
- The write side lives in `droplet.ts` as **non-exported** helpers. The guard ignores non-exported functions.
- Lesson PUT and POST use raw `fetch`, as the current code does. They do not go through the exported `updateLesson`/`addLesson`. This keeps ODY-622 independent of how ODY-504 gates those functions.
  - It is also required by the tests: both test files mock `@/lib/requests/lesson` as `{ deleteLesson: jest.fn() }` only, so any other import from `./lesson` would be `undefined` in tests.
- Removed lessons still go through `deleteLesson`, as today and as in `deepDeleteDroplet`. ODY-504's future gate on `deleteLesson` will therefore apply to publish; tell the ODY-504 owner.
- **Do not touch `droplet.ts:984-1001`** (the user lookup); ODY-504 will replace it. The return shape isn't `{ ok, error, data }`, so ODY-504 will most likely put `requireRole` at the top instead of wrapping the body in `withAuth`. That means no re-indentation.
- Keep the PENDING_AUTH entries for `publishDraftToOriginal` and `duplicateDroplet` (`frontend/testing/security/server-action-auth-allowlist.ts`). This ticket adds no guard and renames neither function.

**D9. Removed and added lessons.**

- A removed lesson is deleted, and Strapi drops its `viewedLessons` join rows. Progress (viewed ∩ current) can only go up.
- If the removed lesson was a student's last unviewed one, the existing completion backfill (`needsCompletionBackfill`) can mark them complete.
- Notes and highlights on a removed lesson keep `lesson: null`, as today.
- An added lesson starts unviewed. Students who already completed the droplet keep `isComplete`.
- New lessons are always appended; an author can then drag one into the middle. A student's next already-viewed lesson then stays locked, in the sidebar and in the lesson content, until they view the new one. The sequential gate is working as designed.
- The completion backfill is lazy: it runs only when the student opens a lesson page or the recap page. It never completes voyage nodes (`recordMissingCompletion` doesn't call `checkAndCompleteVoyageNode`). This is pre-existing; file a follow-up.

**D10. Cache invalidation is unchanged.**

- The `finally` block already revalidates `lesson`, `droplets`, `allEnrollments`, `playlists`, `authors`, `allGroups`, `allUserContent` and `allUserDashboards`.
- Lesson ids don't change, so the per-user `notes`/`highlights` tags need no revalidation.
- `dbWritesStarted = true` moves to just before step 1.
- The `cache-tags.ts` docblock needs no change.

### Assumptions (approve or override)

- **A1:** Lessons are matched by lineage, then by exact name. Position is never used (D3).
- **A2:** A draft with zero lessons can't be published over a live droplet that has lessons. This is a new guard.
- **A3:** A kept lesson keeps its slug even when renamed, so its URL may no longer match the new name.
- **A4:** Lessons removed in the edit are deleted, not detached.
- **A5:** The draft's own enrollments are handled as today, just later in the sequence.

- Strapi adds a nullable `original_lesson_id` column on boot. No data migration.
