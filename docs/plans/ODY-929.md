# ODY-929: Nudges: Reminder feed item (pill and card)

Part of ODY-927 (Nudges). Planned in a cloud session without Linear, Slack or
Figma: the Figma "Nudges / Reminders" Reminder Card was not opened, and
`/coord status` could not run. **Status: waiting for Jaylen's answers to the
design questions below. No code until the plan is approved.**

## Problem

Learners who stall on a droplet should see a reminder in their Activity feed
(`/activity`), and only their own. The feed has no reminder type today: it
shows announcement rows (`frontend/lib/requests/feed.ts` `fetchAnnouncements`)
plus the ODY-919 streak card (`components/streaks/streak-feed-card.tsx`).
This ticket adds the reminder item (its data, its card and its filter pill).
Which reminders exist and when is ODY-931; the actions are ODY-932.

## Acceptance Criteria

- [ ] With a reminder set up for a test learner (by hand or with a test helper,
      see Q8), it renders in that learner's feed only: not in another learner's
      feed, not on any profile feed (`fetchUserAnnouncements`), and not through
      any other announcement read path (see Q7).
- [ ] The card shows the bell, "Reminder · {droplet name}", the due chip when a
      due date is within 3 days (Q4), the progress bar with
      "N of M lessons · K to go", "Up next: {first unviewed lesson in droplet
      order}", **Resume** (or **Start lesson 1** when nothing is viewed) linking
      to `/d/{droplet slug}/{lesson slug}`, the existing mark-read check, and a
      **Remind me later** button that does nothing yet (Q6). No "About N min
      left".
- [ ] Progress and Up next are computed when the feed is fetched, from the
      learner's enrollment, not stored on the reminder.
- [ ] The Reminder pill shows and hides reminders; the "all" URL (no
      `?filters=`) includes them.
- [ ] Marking a reminder read moves it to the Read tab, and unread back.
- [ ] Jest covers the progress and next-lesson logic, the due-soon rule, the
      feed query's reminder branch, and the pill.

(UI strings above come from the ticket; no file renders them yet. Tests must
copy them from the component once written.)

## What the code says (checked on develop)

- Types: `backend/src/api/announcement/content-types/announcement/schema.json`
  `type` enum has 8 values; `frontend/types/index.d.ts:21` `AnnouncementType`
  mirrors it. `readAt` is a column on the row (one read state per row).
- Visibility: `fetchAnnouncements` builds an `$or` of per-type branches
  (`feed.ts` ~L130-170). `droplet` rows reach every enrollee; `system` and the
  review types are matched by `authorized_user = viewer`.
  `fetchUserAnnouncements` (profile) only takes `friend|kudos|droplet`, so a
  new type stays off profiles without changes.
- Filter: the live pills are `FILTER_OPTIONS` in
  `components/feed/feed-center-content.tsx`; `parseFilters`/`toFeedRoles`
  (`feed-filter-params.ts`) derive values from `AnnouncementTypeTitle`
  (`lib/globals.ts:9`, six values). `null` → all six; FeedClient sends them
  as `type $in` (`feed.ts` ~L178).
- Read state: `markAnnouncementRead/Unread` → `assertAnnouncementOwnership`
  (owner must be the viewer) → `revalidateReadState`, which only uses the
  per-user `CACHE_TAGS.userFeed(id)` for `system`; every other type sweeps the
  global `announcements` tag (`feed.ts` ~L770-790).
- Progress data: `Enrollment.viewedLessons` (manyToMany Lesson,
  `backend/src/api/enrollment/.../schema.json`); `updateViewedLessons`
  revalidates `CACHE_TAGS.enrollments(userId)` (`lib/requests/enrollment.ts`
  ~L743). Droplet lesson order is `Lesson.orderIndex`
  (`lib/requests/droplet.ts:96` sorts `lessons` by it; `lib/lesson-gate.ts`
  uses it; `docs/agent/backend-architecture.md:79`). Lesson URLs are
  `/d/{droplet.slug}/{lesson.slug}` (`components/droplets/footer.tsx:219`).
- Due dates: two sources. `Enrollment.dueDate` exists in the schema but no
  frontend code reads or writes it. Group-assigned dates are `due-date` rows,
  one per member per item (`getUserDueDates`, `lib/requests/groups.ts:1155`,
  tag `allDueDates`); a learner in two groups can have two rows for one droplet.
- Feed colours: `FEED_COLORS` is `Record<AnnouncementType, FeedColor>`
  (`lib/feed-colors.ts`), so adding a type to the union forces a colour entry.
  `review_published` already uses Tailwind teal; the Unread/Read tabs use
  `#2D7597` (`feed-client.tsx` `tabButtonClass`).
- Card: `FeedBlock` (`components/feed/feed-block.tsx`) picks icon/label from
  an `announcementConfig` keyed by type; an unknown type would make `config`
  undefined at render.

## Ticket premises the code contradicts or complicates

1. **`feed-filter.tsx` is dead code.** `FeedFilter` is imported only by
   `tests/components/feed/feed-filter.test.tsx`; the live pills are in
   `feed-center-content.tsx`. The plan wires the pill there and leaves
   `feed-filter.tsx` alone (deleting it needs approval; Q5).
2. **"Only the learner sees it" is not guaranteed by the feed alone.**
   `fetchAnnouncementById(id)` (`feed.ts:807`) is an exported Server Action
   (allowlisted under ODY-506 in `testing/security/server-action-auth-allowlist.ts`)
   with no session or owner check, so any signed-in client can read any
   announcement by numeric id, a reminder included. Nothing in `app/` or
   `components/` calls it. See Q7.
3. **"The due date" is ambiguous.** There are two due-date sources and possibly
   several rows per droplet (above). See Q4.
4. **For ODY-930: the existing unread count doesn't match the Unread tab.**
   `getUnreadAnnouncementCount` calls `fetchAnnouncements(1, undefined, …)`, so
   it applies no type filter and counts review rows the tab (six types) never
   shows. Nothing renders it yet (only `feed.ts` and the test catalogues use it).
5. "Don't reuse `type: droplet`" holds: those rows go to every enrollee and to
   profile feeds (`fetchUserAnnouncements`).

## Read state (for ODY-930)

With the recommended representation (Q1 option A), a reminder is an
announcement row owned by one learner, so its read state is that row's
`readAt`, set by the existing `markAnnouncementRead/Unread`, and the Unread tab
is `readAt IS NULL` like every other row. ODY-930's badge matches the tab if it
counts with the same `fetchAnnouncements` filter and the same type list the
Unread tab sends (today's `getUnreadAnnouncementCount` does not, premise 4).
Reminder read changes only revalidate the owner's `userFeed(id)` tag
(Task 2). The streak card is the one feed item whose read state lives in
`localStorage`; ODY-930 has to decide whether it counts. Whether ODY-931 shows
a resurfaced reminder as a new row or by clearing `readAt` is ODY-931's call;
both work with this design.

## Design questions (need Jaylen's answer)

**Q1. How a reminder is represented and reaches the feed.** (Tasks 1-8)
- **A. New announcement `type: "reminder"`** (recommended), with
  `authorized_user` = the learner and `droplet` = the stalled droplet. A new
  `$or` branch matches `type = reminder AND authorized_user = viewer`.
  Pagination, Unread/Read, mark-read and the type filter work unchanged;
  progress is attached at fetch time. Cost: one more enum value wired in ~6
  places (ODY-923's concern).
- **B. New `reminder` collection type** (learner, droplet, readAt, later
  snooze fields for ODY-932), merged into the feed. Clean model, but the feed
  paginates in Strapi; merging two sources breaks page counts, and mark-read
  and the ODY-930 count need a second path. Roughly doubles PR 2.
- **C. Derived, not stored** (like the streak card): computed from enrollments
  on page 1, read state in the browser. No schema change, but read state is
  per-browser (can't match a server-side badge, ODY-930) and ODY-932's Stop
  reminding me has nowhere to live.

**Q2. Which lessons count, and in what order.** (Task 3)
- A. `droplet.lessons` sorted by `Lesson.orderIndex` (what the droplet page,
  sidebar and lesson gate use). Recommended.
- B. `droplet_lessons` join rows by their `orderIndex`. Only if this table is
  the intended source; the frontend reads lessons via A today.
Also: M = all lessons in the droplet, and N = viewed lessons *of that droplet*
(viewedLessons can hold lessons later removed from it). OK?

**Q3. Card when there is no next lesson or no enrollment.** (Tasks 3, 6)
Every lesson viewed but `isComplete` false, the enrollment deleted, or a
droplet with 0 lessons.
- A. Hide the card (filter it out after the fetch; page totals then overcount
  by those rows).
- B. Show it with progress but no Up next, and Resume → droplet page
  `/d/{slug}`.
- C. Show a plain fallback ("Reminder · {droplet}" + mark-read only).

**Q4. Due chip.** (Tasks 3, 4, 6)
- Source: A. the learner's `due-date` rows for that droplet (group-assigned;
  earliest upcoming if several); B. `Enrollment.dueDate` (unused today);
  C. A, falling back to B.
- "Within 3 days": calendar days in the learner's time zone
  (`userTimeZone`) or 72 hours? Does an overdue date show (as "Overdue"?) or
  hide? Chip text (e.g. "Due in 2 days", "Due tomorrow", "Due today")? I
  can't see the Figma.

**Q5. Filter wiring and ODY-923.** (Task 7)
- A. Add a "Reminder" pill now (seventh value of `AnnouncementTypeTitle`);
  ODY-923 later decides how the review types join. Recommended: smallest, and
  the ticket names a pill.
- B. Wait for ODY-923 to settle a type-filter shape (unassigned, not started).
- C. Fix ODY-923 here too (add pills or always include unfiltered types). Out
  of this ticket's scope.
Also: pill position (first, after System, last?), label "Reminder" or
"Reminders", and may I delete the dead `feed-filter.tsx` and its test?

**Q6. Visual details I can't settle without Figma.** (Tasks 6, 7)
- Colours: the design's teal `#2D7597` for card border/accent and pill, as
  arbitrary Tailwind values with a dark-mode variant (what dark value?), or a
  Tailwind palette colour? `review_published` is already teal-700/teal-500, so
  the two may look alike.
- Bell icon (lucide `Bell`?), progress bar style (height, colours), button
  styles for Resume vs Remind me later, whether the card shows the
  timestamp like other feed blocks.
- Remind me later: A. rendered `disabled` (clear it does nothing; screen
  readers say "dimmed"); B. enabled, no-op click (looks real, does nothing);
  C. enabled with a "Coming soon" toast.

**Q7. Closing the `fetchAnnouncementById` leak.** (Task 5)
- A. Delete it (no callers) and its allowlist entry. Needs approval (file
  content deletion).
- B. Gate it: session user must own the row, or the row must be of a
  broadcast-visible type.
- C. Leave it; ODY-506 owns server-action auth. Then "only the learner sees
  it" holds in the UI but not against a crafted call.

**Q8. Setting up a test reminder for the acceptance check.** (Task 8)
- A. By hand in the Strapi admin (Announcement → type reminder,

  no code.
- B. A script under `backend/scripts/` or `initdb/` that creates one for a

- C. Only Jest fixtures; manual QA via A.

**Q9. Card text in `content`.** (Task 4)
The schema requires `content` (minLength 1). With Q1 A, the card ignores it

"Pick up {droplet} where you left off." Agree that `content` is fallback text
only?

## Design Decisions (pending Q1 = A)

- Reminders are announcement rows of a new type `reminder`, owned by one
  learner, linked to one droplet.
- Progress, Up next and the due date are computed per fetch in
  `fetchAnnouncements`, from a second query tagged
  `CACHE_TAGS.enrollments(userId)` and `CACHE_TAGS.droplets` (lesson edits),
  plus the due-date query (`allDueDates`). Viewing a lesson already revalidates
  `enrollments(userId)`, so the next feed fetch is current. Only rows of type
  `reminder` trigger it, so feeds without reminders do no extra work.
- The pure logic lives in `lib/reminder-progress.ts` so it's unit-tested
  without Strapi.
- The card is a new `components/feed/reminder-card.tsx`, rendered by
  `FeedBlock` for `type === "reminder"` so the list, keys and mark-read stay in
  one place.
