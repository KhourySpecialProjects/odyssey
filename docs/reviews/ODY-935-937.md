## Branch 1: ODY-935 PR A (personalization toggle)

**Verdict: ship after fixes**

### What holds

- **Self-only.** `updateUserInfo` refuses `mentorPersonalization` when `!isSelf`, before the admin check, so admins can't set it (tested, no PUT sent). `UpdateUserInfoSelfSchema` stays `.strict()`.
- **No leak.** The field is only in `USER_POPULATES.profile`, used only by `getCachedUser`, whose 23 callers all pass the session user's email. Other presets and friendship fields omit it.
- **Cache.** Counted in `SELF_ONLY_FIELDS`, so only `user(email)` is revalidated; that tag is on every `getAuthorizedUserByEmail` read, and no list selects the field.
- **Reader.** `server-only`, not `"use server"`, so not client-callable. `no-store` without `next`, format header spread, numeric `id` filter. False on non-OK, missing row or throw; undefined or null counts as on (all tested). Unused until ODY-934.
- **Notice.** Matches ODY-934's contract (finished, in progress, prerequisites, viewed lessons); the key moved to `mentor-notice-v2` (tested).

### Major

**935-M1. The toggle reports success even when Strapi refuses the save.** `frontend/lib/requests/authorized-user.ts:698`
- **What's wrong:** the PUT's response is never read. Any 4xx or 5xx from Strapi still returns `{ ok: true }`, so the toggle never rolls back or shows its error toast.
- **Failure scenario:** a student turns personalization off while Strapi returns 500, or 400 "Invalid key" because the frontend deployed before the backend schema. The switch stays off and no error shows. On the next ask, ODY-934 reads `true` (or the old value) and sends their history.
- **Why it matters:** this is a privacy control that looks saved when it isn't. The behaviour predates this branch, but this branch is what makes it matter.
- **Smallest fix:** keep the response. If `!res.ok` and the user is not a `StrapiEntryNotFoundError` case, return `{ ok: false, error: "failed" }`. At minimum do this when `data.mentorPersonalization` is set. Add a test where the PUT returns 500 and the toggle reverts.

### Minor

**935-m1. The switch isn't announced as a switch and has no visible focus.** `frontend/components/settings/mentor-personalization-toggle.tsx:42` (uses `components/ui/switch.tsx`)
- **What's wrong:** the switch is a plain `sr-only` checkbox with no `role="switch"`, and the visible `div` has no `peer-focus-visible` ring.
- **Failure scenario:** a keyboard user tabbing through Settings can't see where focus is, and screen readers announce "checkbox" rather than "switch, on".
- **Smallest fix:** add `role="switch"` to the input and `peer-focus-visible:ring-2 peer-focus-visible:ring-offset-2` to the track. Both go in `ui/switch.tsx`, which fixes every switch in the app.

**935-m2. Settings explains less than the notice does.** `mentor-personalization-toggle.tsx:54`
- **What's wrong:** the help text mentions only finished and in-progress droplets. The notice also lists prerequisites and the lessons viewed in this droplet.
- **Failure scenario:** a student who only reads Settings doesn't learn that prerequisites and viewed lessons are sent too.
- **Smallest fix:** reuse the notice's wording.

### Nit

- **935-n1.** `mentor-notice.tsx:27` "It never sends your name, email or grades from instructors" is a promise that ODY-934 has to keep. ODY-934 should add a test that the learner block contains none of these.
- **935-n2.** `social-forms.tsx:344` puts the auto-saving toggle under "Save Changes". Give it its own section or say "Saved automatically".

## Branch 2: ODY-937 PR 1 (chat history backend)

**Verdict: ship after fixes** (do not deploy to production before M1 is fixed)

### What holds

- **Session user only.** All four actions use `requireRole([])` and `gate.user.id`; none takes a user id.
- **Owner checks.** `get` and `delete` go through `ownedChat` (filters `documentId` and `authorizedUser.id`; null for a malformed id). `deleteAll` filters on the caller's id only.
- **Foreign `chatId`.** The route starts a new chat instead (tested) and never reads another user's messages.
- **Quiz hints never saved.** The Zod `refine` rejects a `chatId` on a quiz hint; the route skips create and save (both tested).
- **Logging.** All 4 new `console.*` calls log only `errorName(error)`; no `strapi.log`. A sentinel-text test spies on every console method.
- **`after()` save.** Runs after the response in `try/catch`, saves only `done` answers; a failed chat start drops the header and still streams (tested).
- **Strapi v5.** No `entityService`; documentIds for relation writes, numeric `id` filters; `cache`/`next` never combined. `mentorChats(userId)` is revalidated on save, delete, deleteAll and a purge that deleted something.
- **Deleting removes messages first**, then the chat.

### Major

**937-M1. The 30-day retention isn't enforced for most chats.** `frontend/lib/requests/mentor-chats.ts:55`, `frontend/lib/mentor/chat-history.ts:205`
- **What's wrong:** the purge only runs inside `listMentorChats`. Nothing in PR 1 calls that function (no UI yet). The global `purgeExpiredMentorChats()` has no caller and the backend has no cron. `getMentorChat` and the route's `ownedChat` don't check age either.
- **Failure scenario:** a student asks Mentor 20 questions after PR 1 deploys and never opens a history view. Their words stay stored forever. A student who does have the history UI can still open an expired chat directly by id, and if they keep asking in it, the expired chat gets new messages and is no longer due for deletion.
- **Smallest fix:**
  1. Add a daily Strapi cron (`config/server.ts` `cron.enabled` plus `config/cron-tasks.ts`) that deletes, using `strapi.db.query(...).deleteMany` (Query Engine, not entityService), messages and then chats where `lastMessageAt` (or `createdAt` when null) is older than 30 days.
  2. In `ownedChat`, treat a chat older than the cutoff as not found.

**937-M2. Message text is now returned by the REST API, and the source can't guarantee who reaches it.** `backend/src/api/mentor-message/content-types/mentor-message/schema.json:26`, both `routes/*.ts`
- **What's wrong:** without `private`, `GET /api/mentor-messages` and `GET /api/mentor-chats/:id?populate=messages` return `text` to anyone with `find` on those routes.
- **What the source does guarantee:**
  - No bootstrap or `initdb` grants roles permissions (I grepped).
  - In a fresh DB, a request without a token gets 401 or 403 (backend test).
  - `authorized-user`, `droplet` and `lesson` have no inverse relation to `mentor-chat`, so a populate from other types can't reach the text.
- **What the source can't guarantee:** role permissions live in the DB.
- **Failure scenario:** someone ticks "find" for Public or Authenticated on Mentor Message in the Strapi admin, for example while granting a whole plugin. Every student's questions can then be read without being signed in. Separately, any Strapi admin-panel user with Content Manager access can read every message in the admin UI, which works against "instructors never see chats" if any instructor or TA has a Strapi admin account.
- **Smallest fix:** put `private: true` back on `text` (and on `title`). Read and write through a custom controller using the Document Service, as `mentor-feedback`'s `custom-mentor-feedback.record` already does, and drop `find`/`findOne` from the core routers.
- **If the author keeps the current design, a reviewer must check in the Strapi admin on each environment:**
  1. Users & Permissions → Public and Authenticated have nothing ticked for Mentor-chat or Mentor-message.
  2. Settings → Administration panel → Roles: only Super Admin has Content Manager access to both types.
  3. The API token in `STRAPI_ACCESS_TOKEN` is the only token with access to them.

### Minor

**937-m1. The message schema isn't valid JSON.** `mentor-message/schema.json:27` (`"type": "text",`)
- **What's wrong:** there is a trailing comma. Tests pass only because the TypeScript build rewrites the JSON into `dist/`.
- **Failure scenario:** anything that `JSON.parse`s `src/**/schema.json` throws, such as the Content-Type Builder, a schema script, or a test like `lesson-populates.test.ts` pointed at this type. `**/*.json` is in `.prettierignore`, so CI never catches it.
- **Smallest fix:** remove the comma (or restore `"private": true`, see M2).

**937-m2. Delete-all and the purge can leave orphaned messages behind.** `chat-history.ts:151-170`
- **What's wrong:** `deleteChatRows` deletes at most 20×100 messages, then deletes the chat anyway. It also sends up to 100 DELETEs in parallel per batch.
- **Failure scenario:** a chat with more than 2,000 messages leaves the rest with `chat = null`. Their text survives every later delete and purge, because both look messages up through the chat.
- **Smallest fix:** delete the chat only if the last batch came back empty, and otherwise throw. Better, use one custom backend route with `db.query().deleteMany({ where: { chat: { documentId } } })`.

**937-m3. A save can race a delete and leave orphaned messages (plausible, not reproduced).** `app/api/mentor/route.ts:151`
- **Failure scenario:** the student presses "delete all chats" while an answer is streaming. Then `after()` POSTs both messages to the deleted chat's documentId. If Strapi accepts a dangling relation (or the first POST succeeds and the PUT returns 404), the messages stay with no chat and are never purged.
- **Smallest fix:** in `saveMentorExchange`, re-check `ownedChat` before writing. When the PUT returns 404, delete the messages just created.

**937-m4. A chat can be continued from another lesson.** `route.ts:122`
- **What's wrong:** `ownedChat` doesn't check that the chat's lesson or kind match the request.
- **Failure scenario:** a client keeps its `chatId` across lessons (the panel isn't keyed by lesson; it remounts today only because the page segment does). The exchanges then go into a chat labelled with the first lesson.
- **Smallest fix:** add `lesson: { id: { $eq: lessonId } }` and `kind` to the `ownedChat` filter when it's called from the route.

**937-m5. Long chats and long lists are silently cut off.** `mentor-chats.ts:74`, `:107`
- **What's wrong:** messages are read with `pageSize: 100`, sorted ascending. The list also stops at 100.
- **Failure scenario:** in a chat with 51 or more exchanges, the newest answers never come back.
- **Smallest fix:** cap the number of messages per chat at save time (refuse or start a new chat past 100), or page with `withCount`.

**937-m6. Creating the chat delays the answer.** `route.ts:120-135`
- **What's wrong:** `ownedChat`, then 3 `resolveDocumentId` calls, then the POST all run before the response is returned.
- **Failure scenario:** every first question waits two to three more Strapi round trips before the first token appears (the stream is already buffering, so nothing is lost).
- **Smallest fix:** start the chat in parallel with `streamMentorAnswer`. Better, mint the chat id first and create the row in `after()`.

**937-m7. The purge in `listMentorChats` can fail when PR 2 renders the list.** `mentor-chats.ts:55`
- **What's wrong:** the purge calls `revalidateTag`. If PR 2 calls `listMentorChats` from a Server Component render, Next 15 rejects `revalidateTag` during render.
- **Smallest fix:** call it only from actions or route handlers, or move the purge to the cron (M1).

### Nit

- **937-n1.** `errorName` throws away the status, so every failure logs as `MentorChatRequestError` and can't be debugged. Log `error.message` from `chatApi` errors (method, path, status): it never contains text.
- **937-n2.** `mentor-message.text` has no `maxLength`. The answer is bounded by the model's tokens, but add `maxLength: 20000` as `mentor-feedback` does.
- **937-n3.** Overlap with ODY-890: `mentor-feedback` keeps its own copy of shared answer text. Later, a feedback row could point at its `mentor-message` instead. This doesn't need to happen here.
- **937-n4.** A first question the student stops creates an empty chat (`lastMessageAt` null). It's hidden from the list and purged by `createdAt`, but only once M1's cron exists.
