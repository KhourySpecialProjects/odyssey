## Problem

NextAuth puts a Strapi id into the JWT, and the auth code reads it back. On v5, core REST single-item routes (`/api/<plural>/:id`) treat `:id` as a `documentId`, and a numeric id gets a 404. The ticket worried that sign-in and role lookup break for everyone.

### What research found (2026-10-02)

**Sign-in and role lookup don't break on v5.**

- `requireRole` ignores the session id. It re-fetches the user by **email** through `getCachedUser` (`require-role.ts:42`) and returns that record's `id` as `gate.user.id`.
- The `jwt` callback and `signIn` (`fetchIsAuthorizedUser`) also use email filters, and filters work on v5.

**The session holds one Strapi id:** `token.user.id`, the numeric `authorized-user` id, set in the `jwt` callback (`options.ts:125-137`). Roles are stored as **titles**, not role ids.

**The numeric id is stable on v5.** Draft & Publish is off on all 23 API types, so each document has one row. The v4→v5 boot only added columns; ids are unchanged (ODY-597.md:446-447).

**Where the session id goes.** The ~20 `getAuthorizedUserId` callers, `getUserIdForEmail` and `PHProvider` use it only for filter values, cache-tag keys (`userSocial/userContent/userDashboard(id)`), numeric compares, and the PostHog `distinct_id` (`PHProvider.tsx:24,49`). It never goes into a URL path.

**`gate.user.id` goes to** ownership compares (`assertOwner`), cache-tag keys, the lesson-lock custom routes (backend parses `Number(body.userId)`, so it must stay numeric), relation values (v5 accepts numeric relation ids), and one URL path: `setTimeZone`.

**The two auth-owned URL paths are already fixed by #1074.** Both `syncAzureProfilePhoto` and `setTimeZone` now build their URL with `strapiEntryUrl("authorized-users", ref)`:

- `syncAzureProfilePhoto` already receives the fetched `authorizedUser` (with `documentId`), so it does no lookup. **No ODY-600 change.**
- `setTimeZone` passes `user.id`, so `strapiEntryUrl` does one cached `id → documentId` lookup. ODY-600 makes it pass the gate user (with `documentId`) so the lookup is skipped.

**users-permissions (the ticket's "check separately").** On 5.56.0, `/api/users/:id` and `/api/users/me` still look the user up by **numeric id** (`services/user.js` `fetch` → `findOne({ where: { id } })`). The frontend never calls `/api/users*` or `/auth/local`, and `up_users` has 0 rows, so it's irrelevant to Odyssey auth. No change.

**`documentId` is already in responses.** With `Strapi-Response-Format: v4`, v5 returns `{ id, documentId, attributes }`, and `flattenAttributes` keeps top-level `documentId`. v5 returns it even with `fields: [...]`.

**Session mechanics** (next-auth 4.24.15):

- JWT strategy, `maxAge` 30 days. The `jwt` callback only enriches on sign-in; later calls return the token unchanged.
- **RSC `getServerSession` can't write cookies.** A re-encoded or cleared JWT is silently dropped there; only `/api/auth/session` writes cookies.
- **`middleware.ts` only decodes the cookie** and redirects signed-in users (`token.user` present) from `/auth/login` to `/explore`. That's the loop hazard for any forced sign-out.

## Decisions (settled 2026-10-02)

1. **Keep the numeric `id`; add `documentId`** to the session `User` and to the `requireRole` user. The numeric `id` stays for filters, compares, cache tags, relation values, the lesson-lock routes and PostHog. Replacing it would be most of ODY-601's work and would split PostHog history.
2. **Old sessions: accept both formats, no token rewrite, no forced sign-out.** Old tokens keep working until they expire. `requireRole` gets `documentId` from its email lookup, and `strapiEntryUrl` resolves a numeric id when `documentId` is missing. A lazy backfill in `jwt` was rejected (RSC can't persist the cookie, so it would refetch on every render). A forced sign-out was rejected (redirect-loop risk via the middleware).
3. **`documentId` is optional on both `User` and the `requireRole` user.** Old tokens lack it, and requiring it on the gate would churn gate fixtures in ~10 test files. A missing value is safe because `strapiEntryUrl` falls back to the numeric `id`.
4. **No `getAuthorizedUserDocumentId` helper.** `strapiEntryUrl` already covers the old-session fallback.
5. **Leave the `session` callback's `throw "No user data"` alone.** Nothing new triggers it.
6. **Boundary:** ODY-600 owns the session contents, the `requireRole` return, and passing `documentId` into the two auth-owned writes. Every other `/api/authorized-users/:id` call (`approveCreationRequest`, `updateUserInfo`, `deleteAuthorizedUser`, `playlist-enrollment.ts`, `friends.ts`, `scripts/update-users.ts`) is ODY-601's. `friends.ts` gating is ODY-506's.
7. **Verification:** Jest for each role plus old sessions, and a manual check on `ody597`.

## Edge Cases

- **Tokens with no `id`** (pre-ODY-555) still work: `getAuthorizedUserId` falls back to email, and the gate looks up by email.
- **A `getCachedUser` record cached from before the v5 boot** (no `documentId`): `setTimeZone` passes `{ id, documentId: undefined }`, and `strapiEntryUrl` resolves the numeric id. No failure.
- **Dev role override** changes roles only, never `id`, `email` or `documentId`.
- **#1074's rule "never use a client-supplied `documentId`"** doesn't apply here: the gate's `documentId` comes from Strapi via `getCachedUser`, not from the client or the session.
