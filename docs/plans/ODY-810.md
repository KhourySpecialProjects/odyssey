## Problem

Submitting a droplet only sets `droplet.inReview: true` (`components/draft/metadata/content-action-button.tsx`). After that:

- The creator can still edit lessons and the Overview.
- Publish copies whatever is saved in Strapi at that moment, so an edit made during review goes live without anyone reviewing it.
- A reviewer who opens a lesson takes its edit lock, which locks the creator out of their own lesson.
- An author with a reviewer role can review and publish their own droplet.

None of the write actions involved check auth today:

- `updateLesson`, `addLesson`, `deleteLesson` and `duplicateLessonToDroplet` (`lib/requests/lesson.ts`).
- `updateDroplet`, `updateDropletLearningObjective`, `updateDropletFunFact` and `publishDraftToOriginal` (`lib/requests/droplet.ts`).
- `createDataset` and `deleteDataset` (`lib/requests/dataset.ts`).

They are all in `PENDING_AUTH` (ODY-504). Any logged-in user can call them on any droplet, including `updateDroplet({ status: "published" })` and `publishDraftToOriginal(...)`.

**Decision (2026-10-23, refined 2026-10-26):**

- While a droplet is in review, every one of its authors can read the draft but not change it, review it or publish it.
- Only a reviewer who isn't an author reviews it.
- Editing reopens when the reviewer sends it back (Request changes, which sets `inReview: false`), when it's published, or when an author withdraws it.

## How the code works now (verified on e6754c59; the tasks rely on these facts)

**Who opens the draft editor.** `app/(editing)/draft/d/[slug]/layout.tsx:59-69` lets in SysAdmin, Content Editor and authors (`droplet.authorized_users`). Everyone else gets `notFound()`.

- The layout already computes `isAuthor`, but doesn't pass it on.
- `shellDroplet` carries no `authorized_users`.

**Who reviews today.** `components/draft/sidebar.tsx:376-389`. None of these rules look at authorship:

- `canPublish = isDraft && (isAdmin || isFaculty || (isEditor && inReview))`. Admin and Faculty can publish any draft, their own included, without review.
- `canRequestChanges = isDraft && inReview && (isAdmin || isFaculty || isEditor)`.
- `canRequestReview = isDraft && !inReview && isCreator && !canPublish`. Admin and Faculty authors never see Submit.

**Status payloads.** All go through `updateDroplet` with `{ regenerateSlug: false }`, and all include `name`:

- Publish: `{ name, status: "published", inReview: false }`.
- Submit: `{ name, inReview: true }`, then `window.location.reload()`.
- Request changes: `{ name, inReview: false, afterReview }`, then `router.push("/review")`.
- Publish of an `[EDIT]` draft calls `publishDraftToOriginal(draftId, originalId)`.
  - That only checks for a session.
  - Then it calls the private `applyDropletUpdate` on the original.

**Lock.** `hooks/useEditingLock.ts` acquires the lock on mount.

- While it holds the lock, it only sends a heartbeat (every 30 s).
- While someone else holds it, it polls `getLessonLockStatus` every 10 s and auto-acquires when the lock is free.
- `LessonRenderer` is its only consumer: `isReadOnly = lockLoading || !isOwnLock`.
- Backend: `backend/src/api/lesson/controllers/custom-lesson.ts`. A lock expires after 60 s without a heartbeat. `lock-status` returns nothing about droplets.

**Relations.**

- `lesson.droplets` is manyToMany (`mappedBy: "lessons"`).
- `dataset.droplet` is manyToOne.
- No helper loads a lesson's droplets or a dataset's droplet.

**Lesson editor gaps.** Read-only mode covers the title, Change URL, Delete, the Classic/BlockNote toggle and the BlockNote editor (`editable` can change after mount).

- Classic (v1) blocks and `AddLessonBlock` are never gated.
- The v1 autosave effect (`lesson-renderer.tsx:205-211`) and the "auto-set blocksVersion v2" effect (`:116-133`) write on mount even when read-only.
- Save failures are silent. The one exception is Change URL, which shows "A lesson with that slug already exists" for any failure.

**Overview editors.**

- Most save through `components/draft/metadata/hooks/useDropletUpdate.tsx`: a 1 s debounce, and inline text for every error. Apart from one description error, that text is always "A droplet with a similar title is in progress or already exists."
- There's no droplet URL editor.

**Fun fact.** It is saved by the Overview page's inline closures (`page.tsx:78-142`), which call `updateDropletFunFact`.

- `generateFunFact` ignores the save result.
- `deleteFunFact` ignores errors.

**Datasets.** Handled by `components/draft/metadata/datasets/datasets.tsx`.

- Upload calls `lib/actions.ts#uploadDataset`, which writes only a file to S3 or local disk and takes no droplet. Then it calls `lib/requests/dataset.ts#createDataset`, which writes the Strapi record. If that fails, it deletes the file again.
- Remove calls `lib/requests/dataset.ts#deleteDataset` (the record) first, and calls `lib/actions.ts#deleteDataset(fileUrl)` (the file) only if that succeeds.
- `components/draft/dataset/dataset-upload.tsx` and `dataset-list.tsx` are not imported anywhere.

**Internal callers.**

- `deleteLesson` is called by `deepDeleteDroplet` (which ignores the result) and `applyLessonSync` (publish, on the live lessons).
- `updateDroplet` is called by `togglePresentationEnabled` and `setDropletHidden`, both already owner-gated.

## Design Decisions

- **D1. One reviewer rule, shared by the sidebar and the server, with authorship as an input.** It lives in `lib/review-roles.ts`, which is client-safe and imports only `@/lib/globals`. (43 test files mock `@/lib/utils` wholesale.)
  - **`isReviewerFor(roles, inReview, isAuthor)`:**
    - **In review:** `!isAuthor && (SysAdmin || Faculty || ContentEditor)`. No author reviews their own droplet.
    - **Not in review:** `SysAdmin || Faculty`. This is today's direct publish, kept unchanged and flagged as Open Question 1. The rule only matters for status changes, because nothing is frozen outside review.
  - **`isFrozenFor(roles, inReview, isAuthor)`** = `!!inReview && !isReviewerFor(roles, true, isAuthor)`.
  - **The sidebar uses these helpers:**
    - `canPublish = isDraft && isReviewerFor(roles, inReview, isAuthor)`
    - `canRequestChanges = isDraft && !!inReview && isReviewerFor(roles, true, isAuthor)`
    - `canWithdrawReview = isDraft && !!inReview && isAuthor`
    - `canRequestReview` keeps today's `isDraft && !inReview && isCreator && !canPublish`.
- **D2. Self-review is blocked (the user's decision, reversing the first draft).**
  - **Explicit for SysAdmin:** a System Admin who is an author is frozen too, with no Edit toggle and no publish during review. Another reviewer has to review it.
  - **Why:** the freeze exists so that what's published is exactly what someone other than the author reviewed. An admin exception would bring back the hole the ticket closes.
  - **To change their own in-review droplet,** a SysAdmin author withdraws it, like any author.
- **D3. The server guard also checks write rights, not only the freeze.**
  - **Why:** calling `requireRole` makes each export count as guarded, so its `PENDING_AUTH` entry must go (the guard test fails stale entries).
  - **Who may write:** an author (`assertOwner`), or SysAdmin, Faculty or Content Editor. That matches who can open the draft editor, plus Faculty, who can already publish any draft.
  - **Fresh reads:** the droplet is loaded with `cache: "no-store"`, so a droplet that was just submitted is never missed.
- **D4. There is no role shortcut.** Authorship decides the freeze for every role, so every check loads the droplet (one read per write).
  - **Existing request tests** mock the `@/lib/auth/review-freeze` checks to `{ ok: true }`. Their fetch assertions stay as they are.
  - **The query catalog** gets responders for the new lookup reads, so the curated writes still happen and the lookups are recorded.
- **D5. How `updateDroplet` classifies a payload.**
  - Keys whose value is `undefined` are ignored.
  - Review keys are `inReview`, `status` and `afterReview`.
  - `name` counts as unchanged when it equals the stored name.
  - Every other key is content.

  The rules:
  - **A reviewer** (D1, computed from the stored `inReview` and authors) may do anything.
  - **Anyone else** gets `forbidden` for `status` or `afterReview`.
  - **In review:** content gets `in_review`. `inReview: false` alone (Withdraw) is allowed for an author. `inReview: true` is a harmless repeat.
  - **Not in review:** an author may write content and `inReview: true` (Submit).

- **D6. Settings toggles aren't frozen.** `togglePresentationEnabled` and `setDropletHidden` already do their own owner check, so they switch to the private `applyDropletUpdate`.
- **D7. Lessons in several droplets.**
  - **Write rights:** a lesson write needs write rights on every droplet the lesson is in.
  - **Freeze:** it is frozen if any of those droplets is in review and the caller isn't a reviewer for that droplet. That includes being one of its authors.
  - **No droplet:** a lesson with no droplet is `forbidden` for everyone except SysAdmin and Faculty.
  - **Missing lesson:** a lesson that doesn't exist gives `"Not Found"`.
  - **Failed lookup:** the check fails closed with `"Could not verify edit access."`.
- **D8. `deleteLesson` is split.**
  - The raw DELETE moves to `lib/requests/lesson-delete.ts` as `deleteLessonRecord`, in a file without `"use server"`, so it isn't a public action.
  - `deepDeleteDroplet` and `applyLessonSync` call it directly.
  - Otherwise, deleting an in-review droplet would leave orphan lessons, because `deepDeleteDroplet` ignores lesson-delete results.
- **D9. The lock poll carries the review state.**
  - `getLessonLockStatus` becomes guarded and returns `review: { inReview, isReviewer } | null`. `isReviewer` is computed on the server, with authorship.
  - `acquireLessonLock` refuses a caller who is frozen (`"in_review"`) or has no write rights (`"forbidden"`).
  - The hook polls every 10 s in every state, including while it holds the lock (the heartbeat stays at 30 s).
- **D10. No auto-acquire while the droplet is in review.**
  - Creators are frozen.
  - Non-author reviewers take the lock only through `startEditing()` (the Edit button).
  - A frozen creator tab that still holds the lock releases it.
- **D11. When the review ends in an open tab,** the hook sets `reviewEnded` and never takes the lock again during that mount. The renderer offers Reload. This avoids ODY-811's stale copy.
- **D12. A new error code, `"in_review"`, joins `"unauthenticated"` and `"forbidden"`.**
  - The constant `REVIEW_FROZEN_ERROR` lives in `lib/review-roles.ts`, because a `"use server"` file must not export constants.
  - **`LessonRenderer`** handles it like this:
    - one info toast, using `{ id: "review-frozen" }`;
    - cancel every debounced save;
    - call `markFrozen()`;
    - no retry.
  - **`useDropletUpdate`** shows the freeze sentence inline.
  - **`generateFunFact`** throws with the freeze sentence, which `FunFactEditor` already shows inline.
  - **Other Overview editors** are hidden while frozen. They keep their generic toasts for a stale tab, which is accepted.
- **D13. While frozen, the Overview renders a separate read-only view** (`components/draft/metadata/frozen-overview.tsx`). It does not thread `readOnly` through 10 editors.
  - The tiptap inputs have no `editable` prop.
  - `inert` would hide the content from screen readers.
  - Non-author reviewers keep today's Overview editors.
- **D14. Classic (v1) lessons when read-only.** `AddLessonBlock` is hidden, and the block list is wrapped in a div that has `inert`.
  - React 18.2 doesn't type `inert`, so spread `{ inert: "" }` with a cast.
  - This is accepted for legacy v1 lessons.
- **D15. Withdraw sends only `{ inReview: false }`,** with no `name`, then reloads. `afterReview` is kept. It is offered to authors only: `isAuthor` now reaches the sidebar from the layout.
- **D16. The fun fact and datasets are frozen.**
  - **`updateDropletFunFact(fact, dropletId)`** calls `requireRole([])` (its shape is `{ success }`), then `checkDropletContentWrite`.
  - **`createDataset(data)`** uses `withAuth`. After the Zod parse, it calls `checkDropletContentWrite(user, validated.droplet)`.
  - **`deleteDataset(datasetId)`** calls `requireRole([])` (its shape is `{ ok, error }`), then `checkDatasetWrite(user, datasetId)`. That check loads the dataset's droplet: a dataset with no droplet is `forbidden` for everyone except SysAdmin and Faculty, and a missing dataset gives `"Not Found"`.
  - **The UI flow is safe as written.** A refused `createDataset` already deletes the uploaded file. A refused record delete stops before the file is deleted.
- **D17. `lib/actions.ts#uploadDataset` and `#deleteDataset` stay unfrozen and stay in `PENDING_AUTH` (ODY-510).**
  - They only write or delete a file, and take no droplet id. On their own they never change what a droplet publishes.
  - Freezing them would need a droplet argument, which would be a client-supplied target, or a lookup by `fileUrl`. That lookup fails in the normal remove flow, because the record is already gone by then.
  - The remaining gap is that `deleteDataset(fileUrl)` can delete any dataset's file by URL. That's an ODY-510 issue (see Open Question 2).
- **D18. `publishDraftToOriginal` gets a reviewer check.**
  - Without one, any logged-in user, including an author during review, can call it directly. That would get around both the freeze and the self-review block.
  - **Before any read or write:**
    - `requireRole([])`;
    - `loadDropletForWrite(draftDropletId)`, with `originalDropletId` added to its fields;
    - refuse unless `draft.originalDropletId === originalDropletId`;
    - refuse unless `isReviewerFor(roles, draft.inReview, isAuthor(draft))`.
  - **Result shape:** a refusal returns `{ ok: false, error, slug: null }`, the shape this function already returns.

### v5 gotchas that apply here

- **Read by numeric id through the list endpoint** (`/droplets?filters[id][$eq]=`, and the same for lessons and datasets), the way `getDropletById` does.
  - `review-freeze.ts` calls `fetchAPI` itself. Importing `lib/requests/droplet` would create a cycle.
  - Pass `cache: "no-store"` alone. It and `next` are mutually exclusive.
- **Strict REST:** an unknown query key returns 400.
  - Nested populate is `droplets: { fields: [...], populate: { authorized_users: { fields: ["id"] } } }` for lessons, and `droplet: {...}` for datasets.
  - The catalog responders record these lookups. Check them once against local Strapi (Task 12).
- **Response handling:**
  - `fetchAPI` adds `Strapi-Response-Format: v4` and flattens the response.
  - The moved raw DELETE keeps `...STRAPI_RESPONSE_FORMAT_HEADER` and `readJsonOrNull` (DELETE returns an empty 204).
- **Single-entry URLs** come from `strapiEntryUrl`, given a numeric id or an entity the server itself fetched. Never use a client documentId.
- **Lock routes stay on numeric ids on purpose** (`strapi-entry-url-guard.test.ts`). Don't "fix" them.
- **`droplet.inReview` has no default** and can be `null`. Use `!!inReview`.
- **The guard test** only accepts a bare `requireRole(` or `withAuth(` call in each export's own body.
  - `withAuth` doesn't catch errors thrown by its handler, so the freeze helpers return results and never throw.
- **Every new or moved `lib/requests/*.ts` function** is registered in `testing/contract/strapi-query-catalog.ts`, in `MODULE_PATHS` plus either `CAPTURED` or `SKIPPED`.
