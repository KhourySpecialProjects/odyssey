# ODY-282: Incorporate logging (2 or 3 levels) into code base

Linear: ODY-282 · Infrastructure · 4 pts · **Blocked by ODY-499**

**Verified against `feature/strapi-v5`, Strapi 5.56.0, Next 15.5.26 on 2026-10-06.**

Earlier revisions were based on `develop` (Strapi 4.25.24). Which branch ODY-282 targets is an **open question** ([Section 6](#6-related-work-and-sequencing)).

## TL;DR

- **What:** structured JSON logs in both apps.
  - Frontend: pino.
  - Backend: Strapi's own winston logger, reconfigured.
- **Why:** today's logs are unstructured, leak PII, and can't tie a frontend failure to the Strapi request behind it.
- **Where:** CloudWatch only, with the existing 30-day retention. No S3 and no terraform changes.
- **Correlation:** a W3C `traceparent` header, generated once per server render.
  - Its trace-id is the `requestId` in both apps' logs.
  - On v5 the backend stores it in Strapi's built-in `strapi.requestContext`, so we don't run our own AsyncLocalStorage.
- **Identity:** `userId` is the numeric Strapi authorized-user id, not the `documentId`.
  - Server Actions take it from `gate.user.id`.
  - Server Components take it from `session.user.id`.
  - `fetchAPI` never reads the session.
- **Security signal:** denied authorization attempts are logged once, centrally, in `withAuth`/`assertOwner`.
- **Errors:**
  - Uncaught server errors are logged via `instrumentation.ts`.
  - Users see an "Error ID".
  - Browser errors go to PostHog.
- **PII:** emails, names, tokens and request/response bodies are never logged.
- **Prerequisite:** ODY-499 moves `fetchAPI` and its helpers into server-only `lib/api.ts`. The helpers are `withoutPaginationCount` and, on the v5 branch, `STRAPI_RESPONSE_FORMAT_HEADER`. ODY-499 has **not** landed.
- **Size:** 15 small tasks, one commit each. Backend and frontend groundwork can run in parallel.

## 1. Problem

**Frontend**

- There are about 380 unstructured `console.*` calls, most of them in `lib/requests/*`.
- `fetchAPI` logs the response **body**, then throws a generic error that drops the path.
- Uncaught server errors only reach Next's default stderr.
- Error boundaries only `console.error` in the browser, so users have nothing to quote in a bug report.
- Denied Server Action authorization attempts leave no trace.
- Known PII leaks:
  - `lib/requests/authorized-user.ts:865, 868` log a user's email.
  - `lib/requests/droplet.ts` has 38 debug `console.log`s: 25 in `duplicateDroplet` and 13 in `publishDraftToOriginal`. Some dump full Strapi request/response payloads.
  - `lib/actions.ts:401, 662, 836` log raw Linear/Strapi response bodies.
  - `lib/actions.ts:220` returns a raw `Error` object to the client.

**Backend (Strapi 5.56.0)**

- Strapi's default logger prints only timestamp, level and message (colorized `printf`), so all metadata and stack traces are dropped.
- The `strapi::logger` request line logs `ctx.url`, query string included, at `http` level. Queries can contain emails.
- Nothing is JSON.

**Correlation**

- Nothing links a frontend failure to the Strapi request behind it.
- Both apps already ship stdout to CloudWatch, but nothing there is searchable.

## 3. How correlation works

**Header format:** `traceparent: 00-{trace-id}-{span-id}-01`

- `trace-id`: 32 lowercase hex characters, never all zeros. This is the **`requestId`**.
- `span-id`: 16 lowercase hex characters, never all zeros.

**Frontend**

- `lib/api.ts` defines `getRenderTraceparent = cache(createTraceparent)`.
- fetchAPI and `strapiHeaders()` send it on every call, reads and writes alike.
- They never overwrite an existing valid `traceparent`; they reuse its trace-id instead.

**Backend**

- The middleware parses `traceparent`, or generates an id if it's missing or invalid.
- It echoes the id back as the `x-request-id` response header.
- It stores `{ requestId, userId }` on `ctx.state.logContext`.
  - Strapi's built-in `strapi.requestContext` already holds the Koa `ctx` in AsyncLocalStorage for the whole request.
  - So a winston format can read the context back for every log line during the request, including `strapi::errors`' error line.

**Scope of one id**

| Context                                                     | One `requestId` per… |
| ----------------------------------------------------------- | -------------------- |
| RSC page render (layout, page, metadata, nested components) | render               |
| Server Action body, route handler, NextAuth callback        | Strapi call          |

The "per call" row is the expected behavior; Task 7 verifies it.

**Where `userId` comes from**

| Caller            | Source                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Server Action     | `gate.user.id` from `withAuth`/`requireRole`, per `docs/agent/server-action-auth.md`.                                     |
| Server Component  | `getAuthorizedUserId(await getCurrentUser())`, which reads `session.user.id` (cheap).                                     |
| `fetchAPI` itself | Never reads the session: `cookies()`/`headers()` would force dynamic rendering. It only forwards the `userId` it's given. |
| `onRequestError`  | None, because it has no session access.                                                                                   |

**What this gives us**

- Page-level grouping without making pages dynamic, because `cache()` reads no cookies or headers.
- The Next data cache still hits, because Next strips `traceparent` from its cache key.
- Identical fetches in one render are still de-duplicated, because they carry identical headers.

**Limits**

- Cache hits never reach Strapi, so their frontend lines have no backend counterpart. Failures are never cached, so every failed call has both sides.
- The span-id is fixed per render. That's a pragmatic use of the header: it's a correlation id, not a real span.
- `onRequestError` runs outside the render's `cache()` scope, so its line has no `requestId`. Join it on `digest`, `route`, `path` and time instead.
- On v5, the `documentId` lookups inside `strapiEntryUrl` (ODY-601) are separate `fetchAPI` calls. Inside a Server Action, each one gets its own `requestId`, distinct from the mutation that follows it.

## 4. Log schema

Both apps use the same field names, so one Logs Insights query covers both log groups.

| Field       | Type                                                                                                                                                            | Frontend (pino)                                          | Backend (winston)                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| `timestamp` | ISO-8601 string                                                                                                                                                 | custom `timestamp` fn                                    | `format.timestamp()`                               |
| `level`     | `error`/`warn`/`info`/`debug`                                                                                                                                   | `formatters.level` (label, not number)                   | default                                            |
| `message`   | short static string                                                                                                                                             | `messageKey: "message"`                                  | default                                            |
| `service`   | `frontend` / `backend`                                                                                                                                          | `base: { service: "frontend" }` (drops `pid`/`hostname`) | `service()` format                                 |
| `requestId` | 32-hex trace-id                                                                                                                                                 | set in fetchAPI/actions lines                            | `ctx.state.logContext` via `strapi.requestContext` |
| `userId`    | **number** (numeric Strapi authorized-user id, not `documentId`)                                                                                                | when the caller passes it                                | parsed from `x-odyssey-user-id` (digits only)      |
| `err`       | `{ type, message, stack }`                                                                                                                                      | pino `err` serializer                                    | `normalizeError()` format                          |
| context     | `method`, `path`, `status`, `durationMs`, `route`, `routeType`, `digest`, `authStrategy`, `bytes`, `event`, `reason`, `requiredRoles`, `action`, `targetUserId` | ✓                                                        | ✓ (where applicable)                               |

**Conventions**

- `message` is static, e.g. `"strapi request failed"`. Variable data always goes in fields; never interpolate values into `message`.
- Log errors as `{ err }`.
- Never log whole objects. Log ids and slugs instead.
- `userId` is always the **caller**. A client-supplied user id that the action targets is logged as `targetUserId`.
- `authStrategy` is the string Strapi reports. For frontend API-token traffic on v5 it's `"content-api-token"`.

## 5. Scope and constraints

### Constraints

- **No `"use server"` export changes.** ODY-502's CI guard test (`testing/security/server-action-auth-guard.test.ts`) fails if a `"use server"` export is unguarded and not allowlisted, or if an allowlist entry is stale. So ODY-282 must not add, rename or remove exports in `"use server"` files (`lib/actions.ts`, `lib/requests/*.ts`). Logging changes inside existing function bodies are fine.
- **New modules aren't `"use server"`.**
  - `lib/api.ts`, `lib/logger.ts`, `lib/trace-context.ts` and `lib/log-request-error.ts` start with `import "server-only"`.
  - `lib/auth/guards.ts` and `lib/auth/require-role.ts` have no directive, and that stays true.
- **Don't re-export `withAuth`** from a `"use server"` file.
- **Preserve ODY-554's list-count optimization**: `withoutPaginationCount` and `shouldFlatten`.
- **Preserve the v4 response-format header (ODY-607)** on every Strapi call: `STRAPI_RESPONSE_FORMAT_HEADER` (`{ "Strapi-Response-Format": "v4" }`). `strapiHeaders()` must include it. Raw fetches in `lib/actions.ts` spread it today, and dropping it would break v4-shaped parsing.
- **Preserve `strapiEntryUrl` URLs (ODY-601).** Task 11 changes only how headers are built, never the URLs.
- **Keep `strapi::compression`** in `backend/config/middlewares.ts` (Task 3).
- **Don't set `server.logger.config`.** Strapi 5 spreads it _after_ `config/logger`, so it would override us (`Strapi.js:218-222`).
- **No Entity Service or Document Service calls.** None are needed, and `backend/tests/no-entity-service.test.js` guards against Entity Service.

## 7. Acceptance criteria

These are the proposed criteria; the user will copy them into Linear.

- [ ] A structured logger is integrated in the **frontend** (pino, server-only `lib/logger.ts`) and the **backend** (winston via `config/logger.ts`). Prod logs `error`/`warn`/`info` and local logs `debug`, controlled by `LOG_LEVEL`.
- [ ] **Logs are structured JSON in CloudWatch (existing 30-day retention) and searchable by requestId / userId in CloudWatch Logs Insights.** Both apps use the same field names.
- [ ] There's enough context to reconstruct a failure:
  - Every Strapi request produces one backend line: `{requestId, userId?, method, path, status, durationMs}`.
  - Every failed fetchAPI call produces a frontend line with the **same** `requestId`, plus `method`, `path`, `status`, `durationMs`.
  - Uncaught server errors are logged with `route`, `routeType`, `method`, `path`, `digest`, `err`.
  - Denied `withAuth`/`assertOwner` checks are logged at `warn` with `reason`, plus `userId` when known.
- [ ] It fires on failure: a Strapi exception, a non-2xx fetchAPI response, a thrown Server Component error, and a browser exception (PostHog `$exception`) each produce a record.
- [ ] Error boundaries show `Error ID: <digest>`, and the same digest appears in CloudWatch.
- [ ] No email, name, token, cookie, password or body appears in logs. Redaction is unit-tested in both apps.
- [ ] Cached fetches still hit, and identical fetches in one render are still de-duplicated (checked manually). Existing return values are unchanged, and every Strapi call still sends `Strapi-Response-Format: v4` (on v5).
- [ ] `/ci` passes, including the Server Action auth guard test, and `cd backend && npm test` passes.

### Task 1: Backend log-context helpers and formats

**Goal:** the pure building blocks for backend logging, aligned with v5's `strapi.requestContext`.

**Files:**

- Create `backend/src/lib/request-context.ts` and `backend/src/lib/logger-formats.ts`.
- Read `backend/src/lib/slack.ts` for style.

**Changes**

- `request-context.ts`. It has **no own AsyncLocalStorage**, because v5 provides one.
  - `type LogContext = { requestId: string; userId?: number }`
  - `getLogContext()` returns `(globalThis as any).strapi?.requestContext?.get?.()?.state?.logContext`. The guard returns `undefined` during boot, before `strapi` exists.
  - `parseTraceparent(v)` returns the trace-id, or `undefined` if invalid. Strict W3C rules are in Appendix A.
  - `generateTraceId()` returns 32 hex characters from `randomBytes(16)`, never all zeros.
  - `sanitizeUserId(v)` accepts only `/^\d{1,12}$/` and returns a number.
- `logger-formats.ts` imports `winston` from `@strapi/logger`, the official pattern. Don't add winston directly.
  - `REDACT_KEYS`, matched case-insensitively:
    - Exact keys: `email`, `name`, `username`, `firstName`, `lastName`.
    - Substring keys: `token`, `password`, `authorization`, `cookie`.
  - `redact()` does a deep walk (max depth 6, cycle-safe, arrays included) and replaces matches with `"[REDACTED]"`. It skips winston's Symbol keys.
  - `requestContextFormat()` adds `requestId`/`userId` from `getLogContext()`.
  - `normalizeError()` turns an Error, or `meta.err`, into `err: { type, message, stack }` and removes the top-level `stack`.
  - `service()` adds `service: "backend"`.
  - `buildLogFormat()`: `errors({stack:true})` → `requestContext` → `normalizeError` → `service` → `timestamp` → `redact` → `json`.

**Tests:** in Task 6.

**Done when:** it compiles (`npm run build`) and the Task 6 tests pass.

**Changes**

- The middleware is a `(_config, { strapi }) => async (ctx, next) => {…}` factory, loaded as `global::request-context` from `dist/src/middlewares/request-context.js`. It:

```sql
fields @timestamp, service, level, message, method, path, status, durationMs, userId, err.message
| filter requestId = "<32-hex id>"
| sort @timestamp asc
```
