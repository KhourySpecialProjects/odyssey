# ODY-633: Turn off Draft & Publish on all content types before Strapi v5

Parent: ODY-597. Blocks ODY-597 and ODY-602. Related: ODY-599 (lifecycle tests + D&P migration for v5), which gets simpler once D&P is off.

**Approach changed.** The human chose to turn off Draft & Publish (D&P) instead of renaming `status`. The rename plan is kept, unchanged, as the documented fallback: [ODY-633-rename-fallback.md](./ODY-633-rename-fallback.md). Use it only if D&P has to stay on.

**Related:** [ODY-659](https://linear.app/aiil/issue/ODY-659) (null-droplet guards; blocks the prod switch), [ODY-660](https://linear.app/aiil/issue/ODY-660) (make `isHidden` a real takedown; non-blocking). Prod steps live in the [migration-day playbook](../playbooks/strapi-prod-migration-day.md).

## Problem

Strapi v5 reserves the attribute name `status`, but only on content types that have D&P turned on:

- `RESERVED_ATTRIBUTE_NAMES_DRAFT_PUBLISH = ['status']` in `packages/core/utils/src/content-types.ts`.
- The boot check in `core/src/domain/content-type/index.ts` returns early when `draftAndPublish !== true`.

`droplet` and `voyage` both have a `status` enum and D&P on. Odyssey never uses D&P on purpose:

- REST create on a D&P type sets `publishedAt = now` (`@strapi/strapi/dist/core-api/service/collection-type.js:10-11,47`).
- No frontend or backend code sends or reads `publishedAt`. The only frontend reference is `publicationState: "preview"` in `voyage.ts`.
- The backend has no `entityService.create` calls.

So rows with no `published_at` come only from the admin panel or seeds. Turning D&P off on all five D&P types (droplet, voyage, lesson, playlist, creation-request) removes the conflict and keeps `status` exactly as it is.

**The catch: turning D&P off deletes data on the first boot.** Verified in installed `@strapi/strapi` 4.25.24:

1. `dist/migrations/draft-publish.js` `disable` is registered on `strapi::content-types.beforeSync` (`Strapi.js:337`) and called at `Strapi.js:398`.
   - It runs `queryBuilder(uid).delete().where({ published_at: null })`. This is a hard delete that skips lifecycles.
   - It fires once per database, the first time the stored schema (`strapi_core_store_settings` key `strapi_content_types_schema`) says D&P was on and the code says it is off.
2. The delete runs **before** `db.schema.sync()` (`Strapi.js:402`), and schema sync is what runs user migrations. So a knex migration in `backend/database/migrations/` cannot back-fill first.
   - A custom `beforeSync` handler would not help either: the hook is `createAsyncParallelHook` (`Strapi.js:335`), so it would race the delete.
3. `*_links` rows for deleted rows cascade.
   - Enrollments, due-dates, voyage_nodes, droplet_lessons and datasets that pointed at a deleted row survive with a null relation.
   - Component rows (e.g. droplet `learningObjectives`) are orphaned.
4. Schema sync then drops the `published_at` column on all five tables.
5. `cleanPermissionsInDatabase` removes every `plugin::content-manager.explorer.publish` admin permission. In the local seed that is 11 rows:
   - droplet: 248, 96, 133, 167
   - lesson: 250, 104, 138, 172
   - playlist: 271
   - voyage: 510
   - creation-request: 485
6. **Visibility change.** Today the "live" filter also applies inside `populate` (`@strapi/database/dist/index.js:3390-3391`). Rows that are unpublished but linked from published content (for example a lesson inside a published droplet, or a droplet inside a public playlist) are hidden today. They will **appear** after the switch unless they are handled.

So every row with `published_at IS NULL` must be dealt with **before** code with D&P off boots against that database.

## Scripts (`scripts/ody-633/`)

Run each with `psql -v ON_ERROR_STOP=1 -f <file>` and save the output **outside the repo** (for example `~/ody-633/<env>-<step>-<date>.txt`). The output from `01` query 4 is needed for the rollback runbook.

### `01-audit.sql`: read-only; run before handling, again after handling, and again right before cutover

1. **Unpublished vs total per table.** For `droplets`, `lessons`, `playlists`, `voyages`, `creation_requests`:

   ```sql
   SELECT 'droplets' AS t, count(*) FILTER (WHERE published_at IS NULL) AS unpublished, count(*) AS total FROM droplets
   ```

   `UNION ALL` the same query for the other four tables. The cutover gate is: every `unpublished` value is 0.

2. **Unpublished rows with identifying columns.**

   - droplets: `id, slug, name, status, is_hidden, created_at, updated_at`
   - lessons: `id, slug, name, created_at`
   - playlists: `id, slug, name, is_public, is_archived`
   - voyages: `id, slug, name, status, is_archived`
   - creation_requests: `id, created_at`
   - Each is `WHERE published_at IS NULL ORDER BY id`.

3. **What points at each unpublished row.** One `UNION ALL` query per parent type, returning `(parent, parent_id, via, count)`. It follows this pattern:

   ```sql
   WITH d AS (SELECT id FROM droplets WHERE published_at IS NULL)
   SELECT 'droplet' AS parent, droplet_id AS parent_id, 'enrollments' AS via, count(*)
     FROM enrollments_droplet_links WHERE droplet_id IN (SELECT id FROM d) GROUP BY droplet_id
   UNION ALL
   SELECT 'droplet', droplet_id, 'due_dates', count(*)
     FROM due_dates_droplet_links WHERE droplet_id IN (SELECT id FROM d) GROUP BY droplet_id
   -- ...one branch per link table below
   ORDER BY 2, 3;
   ```

   Link tables to cover (the names come from the seed dump; run `\d <table>` to confirm the column names before finalizing):

   | Parent (FK column)                       | Link tables                                                                                                                                                                                                                                                                                                                                                                      |
   | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | droplet (`droplet_id`)                   | `enrollments_droplet_links`, `due_dates_droplet_links`, `voyage_nodes_droplet_links`, `droplet_lessons_droplet_links`, `datasets_droplet_links`, `groups_droplets_links`, `playlists_droplets_links`, `droplets_lessons_links`, `announcements_droplet_links`, `authorized_users_droplets_links`, `droplets_postrequisites_links` (check both `droplet_id` and `inv_droplet_id`) |
   | lesson (`lesson_id`)                     | `droplets_lessons_links`, `droplet_lessons_lesson_links`, `enrollments_viewed_lessons_links`, `notes_lesson_links`, `highlights_lesson_links`                                                                                                                                                                                                                                    |
   | playlist (`playlist_id`)                 | `playlists_droplets_links`, `groups_playlists_links`, `due_dates_playlist_links`, `voyage_nodes_playlist_links`, `announcements_playlist_links`, `authorized_users_created_playlists_links`, `authorized_users_playlists_archived_links`, `playlists_authorized_users_links`                                                                                                     |
   | voyage (`voyage_id`)                     | `voyage_nodes_voyage_links`, `voyage_enrollments_voyage_links`, `groups_voyages_links`, `voyages_authors_links`                                                                                                                                                                                                                                                                  |
   | creation_request (`creation_request_id`) | `creation_requests_user_links`, `creation_requests_voyage_node_links`                                                                                                                                                                                                                                                                                                            |

   Also list **the published parents that link to each unpublished child**. These are the rows that become visible after the switch:

   - published droplets → unpublished lessons (`droplets_lessons_links`, `droplet_lessons_lesson_links`)
   - published playlists / groups / voyage-nodes → unpublished droplets
   - groups → unpublished playlists / voyages

4. **Publish permissions the switch will remove.** Save this output for rollback:

   ```sql
   SELECT p.id, p.action, p.subject, p.properties, p.conditions, r.id AS role_id, r.name AS role
     FROM admin_permissions p
     LEFT JOIN admin_permissions_role_links l ON l.permission_id = p.id
     LEFT JOIN admin_roles r ON r.id = l.role_id
    WHERE p.action = 'plugin::content-manager.explorer.publish'
    ORDER BY p.id;
   ```

5. **Baseline orphan counts,** to compare after the switch:

   - enrollments with no `enrollments_droplet_links` row
   - due_dates with neither a droplet nor a playlist link
   - voyage_nodes with no `voyage_nodes_voyage_links` row
   - droplet_lessons missing a droplet or lesson link
   - datasets with no droplet link

   Use `NOT EXISTS` subqueries.

### `02-handle-unpublished.sql`: the only script that writes; one transaction

This is a template. Fill in the id lists from `01`, one explicit decision per row, and put a 1-line comment per row naming the decision. The committed version has the local-seed decisions filled in as the worked example. For dev and prod, make a copy outside the repo with that environment's ids. Always run it with `psql -v ON_ERROR_STOP=1 -v expected_db=<db> -f ...` (no default; the script fails without it).

```sql
BEGIN;
-- (b) keep: hide with Odyssey fields first...
UPDATE playlists SET is_public = false WHERE published_at IS NULL AND id IN (/* ids */);
-- droplets/voyages already status='draft' need nothing; demote others only by explicit decision:
-- UPDATE droplets SET status = 'draft' WHERE published_at IS NULL AND id IN (/* ids */);
-- lessons linked from a published droplet: unlink or accept (decision per row):
-- DELETE FROM droplets_lessons_links WHERE lesson_id IN (/* ids */) AND droplet_id IN (/* ids */);
-- ...then back-fill so Strapi's disable step keeps the row.
UPDATE droplets          SET published_at = created_at WHERE published_at IS NULL AND id IN (/* ids */);
UPDATE lessons           SET published_at = created_at WHERE published_at IS NULL AND id IN (/* ids */);
UPDATE playlists         SET published_at = created_at WHERE published_at IS NULL AND id IN (/* ids */);
UPDATE voyages           SET published_at = created_at WHERE published_at IS NULL AND id IN (/* ids */);
UPDATE creation_requests SET published_at = created_at WHERE published_at IS NULL AND id IN (/* ids */);
-- (a) delete: only rows with zero dependents in 01 section 3a; link rows cascade. Every delete needs a matching guard.
-- DELETE FROM <table> WHERE published_at IS NULL AND id IN (/* ids */);
COMMIT;
```

**How to hide each type under option (b):**

| Type             | Hiding rule                                                                                                                                                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Droplet          | `status='draft'` already keeps it out of every listing filter. It stays reachable by URL, like any app-created draft (`/d/[slug]` and the draft editor filter on slug only). If a D&P-unpublished droplet has `status` of `published` or `edit`, a human decides: demote it to `draft`, or set `is_hidden = true`. |
| Voyage           | `status='draft'` is enough. `getVoyages` filters on published, and drafts are staff-only.                                                                                                                                                                                                                          |
| Playlist         | Set `is_public = false`. Explore, add-playlist-dialog and the voyage builder filter on `isPublic`/`isArchived`, and the slug page requires `isPublic` or enrollment.                                                                                                                                               |
| Lesson           | There is no hide field. If a published droplet links to it (01 section 3), it will show in that droplet's lesson list after the switch. Unlink it or accept it.                                                                                                                                                    |
| Creation request | Back-fill only.                                                                                                                                                                                                                                                                                                    |

**Warning:** after `02` commits, the old D&P-on backend serves these rows as live immediately. That is why the hide updates come before the back-fill in the same transaction. After this point, the visibility is the same as after the switch.

### `03-post-switch-verify.sql`: after the first D&P-off boot

1. Row totals per table. They must equal the totals from `01` query 1, minus the deliberate (a) deletes.
2. `SELECT table_name FROM information_schema.columns WHERE column_name = 'published_at' AND table_name IN ('droplets','lessons','playlists','voyages','creation_requests');` must return 0 rows.
3. `SELECT count(*) FROM admin_permissions WHERE action = 'plugin::content-manager.explorer.publish';` must return 0.
4. The orphan counts from `01` query 5 must be unchanged.

### `04-reenable-check.sql`: rollback rehearsal only

For each of the 5 tables:

```sql
SELECT count(*) FILTER (WHERE published_at IS NULL), count(*) FILTER (WHERE published_at = created_at), count(*)
```

Expected: 0 nulls, and every row has `published_at = created_at`. Also re-run `01` query 4 to see which publish permissions came back. Super Admin should resync; the other roles are expected **not** to come back.
