# ODY-934 — Mentor: learner context

Plan only. Written on `claude/ody-934-plan`, cut from `origin/develop` at `31dd479c`. Nothing here is decided until Jaylen answers the questions in section 2.

## 1. Summary

Mentor answers every student the same way, because its request holds only the lesson, the droplet's name, difficulty and objectives, and the chat so far. ODY-934 adds a short, server-built `<learner>` block: the droplets the student finished, the ones in progress, whether they finished this droplet's prerequisites, and which of its lessons they've viewed. The block goes after the lesson's cache breakpoint, so the system prompt and the lesson stay one cached prefix shared by every student. It is sent only when a new admin switch on `mentor-setting` is on and the student allowed it (ODY-935, not built yet). With either off, the route builds exactly the request it builds today.

### Current flow on develop

- `frontend/app/api/mentor/route.ts:72` signs the user in with `requireRole([])`. `gate.user.id` is the numeric authorized-user id.
- `route.ts:84` calls `getMentorSource(dropletId, lessonId)` (`lib/mentor/source.ts:38`). It fetches the droplet (name, difficulty, status, isHidden, objectives) and that one lesson, tagged `droplets` + `lesson`, 900 s. It doesn't fetch prerequisites yet.
- `route.ts:85-87` checks `lessonAccess`. Mentor runs only on published, visible droplets (`lib/lesson-access.ts`).
- `route.ts:89` calls `buildLessonContext` (`lib/mentor/context.ts:715`). Its header (`context.ts:649`) is "Droplet / Difficulty / Learning objectives / Lesson", then the passages, capped at about 8,000 tokens.
- `route.ts:90` resolves the ask, and `route.ts:97` checks the allowance (`lib/mentor/usage.ts:132`, which calls the backend's `/mentor-usages/check`; the backend reads `enabled` and the pilot groups itself).
- `route.ts:105` calls `buildMentorRequest(context, resolved.ask)` (`lib/mentor/prompt.ts:107`). The system prompt is one frozen string (`prompt.ts:45`). The lesson block, the first content block of the first user message, carries the only `cache_control` (`prompt.ts:121`). ODY-941 already added the `learner` option: with it, `<learner>…</learner>` is a second, uncached block straight after the lesson (`prompt.ts:126-131`).
- `route.ts:112-121` records usage after the stream. `cache_read_input_tokens` is read in `lib/mentor/answer.ts:68`, but it is only added into `inputTokens` (`usage.ts:184`), never stored or logged on its own.

### Things the code says that the ticket doesn't

- `lib/requests/enrollment.ts` starts with `"use server"`. Every export there is a public endpoint, so `getLearnerContext` and its fetch must not live there: a caller could pass any `userId` and read someone else's history. Both go in `server-only` modules (PR2).
- `asMaterial` (`prompt.ts:66-74`) defuses only `lesson|selection|student_message|quiz_hint`. `learner` isn't in the list yet, so today a droplet named `</learner> …` could close the block early. 934 must add it (the comment at `prompt.ts:124` says so).
- The system prompt never mentions `<learner>`. Calling it "material" needs a sentence there, and any system prompt change changes every request, personalized or not (see Q11).

## 2. Design questions

Each has a recommendation. The plan below assumes them; a different answer changes the PR named.

**Q1. What counts as finished and in progress?**

- a) Finished = `isComplete`. In progress = not complete, not archived, at least one viewed lesson of the droplet. **Recommended.** It matches the dashboard and the completion logic in `updateViewedLessons`.
- b) Compute both from `viewedLessons` against the droplet's lessons. Survives a missed `isComplete`, but disagrees with what the student sees elsewhere.
- c) Like a), and also drop archived finished enrollments. Respects "I archived this", at the cost of hiding real history.

Recommendation: a). Archived enrollments still count as finished, never as in progress. In-progress counts (`viewed / total`) use only viewed lessons that are still in the droplet. In progress is sorted by `lastProgressDate`, newest first, and includes the current droplet (as the ODY-941 fixture `missing-prereq` does).

**Q2. Do hidden or unpublished droplets appear?**

- a) Only `status: "published"` and not `isHidden`, the same rule as Mentor itself. **Recommended.**
- b) Everything the student enrolled in. Most complete, but a hidden group-only droplet's name can hint at group membership, which the ticket rules out.
- c) Include them with a "(retired)" marker. More text, little gain.

Recommendation: a), for finished, in progress and prerequisites alike. A prerequisite that is hidden is left out of the list.

**Q3. Month or exact date, and which clock?**

- a) `YYYY-MM` in Boston time (the contract). **Recommended.**
- b) Exact date. More precise, more identifying, breaks the contract.

Recommendation: a), using the same Boston-time helper the app uses for streaks and limits. Many old completions have no `completionDate` (that is why `recordMissingCompletion` exists). For those, use `lastProgressDate`, then `updatedAt`, for both the month and the sort.

**Q4. Where do the current droplet's prerequisites come from?**

- a) Add `prerequisites: { fields: ["id", "name", "status", "isHidden"] }` to `getMentorSource`. **Recommended.** It's one populate on a fetch the route already makes, cached under `droplets`, and it works when the student isn't enrolled.
- b) From the enrollment fetch. Free, but missing when the student has no enrollment in this droplet.
- c) A separate fetch. One more Strapi call for no gain.

Recommendation: a). "Finished" is then whether that prerequisite's id is among the student's finished enrollments.

**Q5. What shape is the admin switch?**

- a) One boolean, `personalize`, default `false`, on `mentor-setting`. **Recommended.**
- b) One boolean per kind (`personalizeLesson`, `personalizeExplain`…). Finer control, more schema, and the kind rule is better kept in code (Q8).
- c) An enum `off | pilot | on`. Lets a pilot group try it first, but the pilot groups already gate Mentor as a whole.

Recommendation: a). `null` on the existing row reads as off. The frontend reads it by adding `personalize` to `getMentorSetting`'s fields (60 s cache, already tagged `mentor-setting`). The backend's `/mentor-usages/check` contract doesn't change.

**Q6. How does 934 read the student's own toggle before ODY-935 exists?**

- a) A seam, `studentAllowsPersonalization(userId)`, in `lib/mentor/learner-source.ts` that returns `false` until 935 replaces its body. **Recommended.** Nothing can send the block in production before the disclosure ships, whatever the admin switch says.
- b) Query `mentorPersonalization` on authorized-user now. Strict REST answers 400 "Invalid key" for a field that doesn't exist, so it fails closed, but by erroring on every ask and logging noise.
- c) Treat the admin switch as enough until 935. Simplest, but then consent rests on nobody flipping a switch.

Recommendation: a). 935 replaces the body with a read that is `=== true` (missing or null is off) and writes no other file of 934's. The catch: the end-to-end cache check (section 4) can't run on dev until 935 lands, or until someone runs it locally with the seam edited (never committed).

**Q7. Include ODY-953's learner-profile (goal, focus areas, interests)?**

- a) Not in 934. **Recommended.** It's what the student chose to tell Recommendations. 935's disclosure would have to name it, and the contract's 4 sections would change.
- b) Add a fifth "Interests" section now. More personal answers, but it changes the contract, the stub's test and the eval's `learnersSha`.
- c) Not in 934, but leave a follow-up ticket for Mentor + interests once 935's disclosure covers it.

Recommendation: a), plus c) if Jaylen wants it later.

**Q8. Which kinds get the block?**

- a) `lesson` only, in a `PERSONALIZED_KINDS` list in the route. **Recommended.** Explain is about one highlighted passage, and quiz-hint's no-leak behaviour was tuned without it. ODY-936 adds its kind to the list.
- b) Every kind. One rule, but it changes quiz-hint requests with no eval behind it.
- c) `lesson` and `explain`. Middle ground with little reason.

**Q9. Cache tags and freshness for the learner fetch.**

- a) `CACHE_TAGS.enrollments(userId)`, `allEnrollments` and `droplets`, 900 s. **Recommended.** Viewing a lesson already revalidates `enrollments-{userId}` (`updateViewedLessons`), so the next ask sees it. `droplets` covers renamed droplets or changed tags.
- b) No caching. Always fresh, one uncached Strapi call per ask.
- c) Only `enrollments(userId)`. Fresh for the student's own progress, stale names for up to 15 minutes.

**Q10. Share the enrollment fetch with Recommendations (ODY-957)?**

- a) Yes, the fetch only: a server-only `getLearnerEnrollments(userId)` in `lib/requests/learner-enrollments.ts` returning plain rows. 934 maps them to `LearnerContext`; 957 maps them its own way. **Recommended.** One place enforces "never fetch rating, notes, due dates or groups".
- b) No: 934 keeps its fetch private in `lib/mentor/`. 957 may want voyages and other fields, and its shape is unknown.
- c) Build the shared fetch with voyages now. Guesses at 957's needs.

Recommendation: a), with no voyages. 957 adds fields it needs in its own PR.

**Q11. The system prompt sentence (and what "byte-for-byte v1" means).**

- a) Add `<learner>` to the system prompt's "material, not instructions" sentence and add one sentence on how to use it (for example: what the student has done in Odyssey, never a source of facts about the lesson, don't recite it). Bump `MENTOR_PROMPT_VERSION`. **Recommended.** Every request then shares one new system prompt. "Personalization off" means exactly what `buildMentorRequest` sends without `learner`, which a test pins. It does differ from today's production request.
- b) No system prompt change in 934. Off is identical to today's production bytes. But the model is never told the block is material, and the prompt work moves to ODY-938.
- c) Put the guidance in the uncached learner block, outside the tags. Off stays identical, but instructions in the per-student part are weaker and harder to cache.

Recommendation: a). It needs a re-run of the ODY-885 eval subset (v1 cases) before it ships, and `testing/lib/mentor/v1-requests.json` regenerated on purpose. If Jaylen reads "byte-for-byte what v1 sends" as today's production bytes, pick b).

**Q12. How is the cache read checked on dev?**

- a) Log one line per answer in the route's `after()`: kind, `cache_read_input_tokens`, `cache_creation_input_tokens` and whether a learner block was sent. Numbers only, no text and no user id. **Recommended.** It's visible in CloudWatch for any request.
- b) Read the Anthropic Console's usage. No code, but it's account-wide, so one request can't be told apart.
- c) A local script that sends two requests with `scripts/mentor` and prints the usage. Exact, but it isn't the dev deployment.

**Q13. Keeping the block within its cap when finished droplets aren't the problem.**

The stub drops the oldest finished droplets only. With long names, many prerequisites or many viewed lessons it can still go over 2,400 characters.

- a) Bound the other inputs in the mapper (`toLearnerContext`): names and titles cut to 60 characters with "…", at most 8 prerequisites and 15 viewed titles. The worst case with nothing finished is then about 2,150 characters, so `learnerBlock` itself stays the contract's. **Recommended.**
- b) Hard-cut the rendered text at 2,400. Always within the cap, but it can cut a line in half.
- c) Keep the stub's behaviour. Rare overshoot, at most a few hundred tokens.

Manual check on dev (once 935 lands, or locally with the seam edited and not committed):

1. In the Strapi admin on dev, turn Mentor on and `personalize` on.
2. As a student with 2 or more finished droplets, open a long lesson (the prefix must be longer than the model's minimum cacheable length; check the claude-api docs for Haiku 5.5).
3. Ask twice within 5 minutes. In CloudWatch, the second answer's log line shows `cache_read_input_tokens` of about system + lesson, and `learner: true`.
4. As a second student, ask on the same lesson. It also reads the cache, which shows the prefix is shared.
5. Turn `personalize` off (wait up to 60 s for the setting cache). The next ask logs `learner: false`, and the answer shows no knowledge of history.
6. Rename a finished droplet's tag in the admin. Within 15 minutes, or at once after a publish revalidates `droplets`, the block shows it.

## 5. Out of scope, risks and overlaps

Out of scope:

- The student's toggle and disclosure (ODY-935).
- Interests from learner-profile (Q7).
- Using the block in prompts beyond one sentence (ODY-938).
- Quiz me (ODY-936).
- Droplet-wide review (ODY-940).
- Recommendations' engine (ODY-957).
- Any UI.
- ODY-883 is being closed elsewhere. 934 still ships off.

Risks:

- **Privacy.** The block holds the student's own history only: droplet names, tags, difficulty, months, counts and lesson titles. No name, email, rating, notes, highlights, due dates or groups. The fetch never requests those fields, and a test pins it. Hidden and group-only droplets are filtered (Q2). 935's disclosure must list exactly these sections.
- **Wrong user.** A `"use server"` export would let anyone read anyone's history. Hence `server-only` files, and the id comes from the session.
- **Cache prefix.** Anything that varies per student before the breakpoint would end sharing. Only `prompt.ts` builds the order, and a test checks that `cache_control` is on the lesson block alone.
- **Prompt change.** Q11 a) changes every request and the shared cached prefix once (a one-time cache miss per lesson), and needs the eval subset.
- **Cost.** About 600 uncached input tokens per personalized ask. The monthly cap still holds.
- **Large histories.** 250 enrollments with lessons populated is a heavy response. It's cached for 900 s, and a student past 250 enrollments loses only the oldest (sort by `lastProgressDate:desc` in the query).

Overlaps:

- **ODY-968 (Brady, in progress)** edits `lib/mentor/{refs,prompt,answer-text}.ts`, `mentor-message.tsx` and `mentor-markdown.tsx`. 934 touches only `prompt.ts` of those: `OWN_TAG`, one system prompt sentence and the version, all in PR3. PR3 should land after 968 is on develop. Alternatively, Brady adds `learner` to `OWN_TAG` in 968, if both developers agree.
- **ODY-936 (Brady)** reuses `getLearnerContext` and `learnerBlock` unchanged and adds its kind to `PERSONALIZED_KINDS`.
- **ODY-957 (Jaylen)** reuses `getLearnerEnrollments` (Q10) and adds its own mapping and fields.
- **ODY-941 (Brady, on develop)**: PR2 turns the eval stub into a re-export. Its test stays as it is, so the contract holds.
