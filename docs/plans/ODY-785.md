# ODY-785: Lesson highlighting drops selections, removes the wrong highlight and only works with a mouse

Linear: https://linear.app/aiil/issue/ODY-785 · Medium · Label: Bug
Branch: `bug/ody-785-bug-lesson-highlighting-drops-selections-removes-the-wrong` (cut from `develop` @ ffb2041d)
Related: ODY-153 (overlapping highlights), ODY-198 (highlights after lesson edits, out of scope), ODY-508 (auth for notes and highlights actions), ODY-544 (hover-only controls)

## Problem

Highlighting in the lesson reader (`GenericBlockRenderer`) is unreliable:

1. Selections disappear when the mouse crosses into another block.
2. A highlight in a colour other than the selected one disappears until the save returns.
3. Remove deletes the wrong record when the same words are highlighted twice. Recolouring a highlight that crosses bold text, a link or inline code saves a second, partial highlight.
4. Keyboard and touch selections get no toolbar. The toolbar buttons ignore Enter and Space. The toolbar doesn't follow the text when the page scrolls.
5. A failed save or delete looks like it worked.
6. "Add note" can attach the note to the wrong highlight, or to none.

1 to 5 were reproduced in Jest against the real components before planning. The scratch test is in "Test harness facts" below.

## Acceptance Criteria

- [ ] Moving the mouse over another block keeps the selection and the block's DOM (same text nodes).
- [ ] A block's DOM is rebuilt only when its content or this lesson's highlights change. It is not rebuilt on hover, on toolbar state, on colour choice, or on parent re-renders.
- [ ] A new highlight shows immediately in the chosen colour and stays while the save is pending. If the save fails, it disappears and the error toast shows.
- [ ] A removed highlight disappears immediately. If the delete fails, it comes back and the error toast shows.
- [ ] Every drawn piece of a highlight has `data-highlight-id`. Nothing selects highlights by inline style.
- [ ] Remove and recolour act on the highlight that was clicked, by id. With two highlights on the same words, removing the second deletes the second.
- [ ] Recolouring calls `updateHighlight(id, { color })` and creates nothing.
- [ ] A selection that overlaps existing highlights in the block merges them into one highlight (ODY-153). The earliest one is updated to cover the union, in the chosen colour, and the others are deleted.
- [ ] "Add note" links the note to the highlight it was made from: the one just created, the merged one, or the clicked one. `getHighlights` is removed.
- [ ] Selecting with the keyboard, mouse or touch opens the toolbar (`selectionchange`).
- [ ] The toolbar is rendered inside the block, after the content, so Tab reaches it and it scrolls with the text. It sits above the selection, or below when above would be under the site header.
- [ ] The toolbar's buttons are `type="button"` with labels and work on click, Enter and Space. The toolbar has `role="toolbar"`, Left/Right arrows move between buttons, and Esc closes it.
- [ ] `createHighlight`, `updateHighlight` and `deleteHighlight` use `withAuth`. They take no user id from the client and return `{ ok, error, data }`. Update and delete load the record and call `assertOwner(..., { bypassRoles: [] })`. Their `PENDING_AUTH` entries are removed, along with `getHighlights`'s.
- [ ] Full Jest suite passes. `npm --prefix frontend run lint` reports nothing new in the touched files. `tsc --noEmit` passes.

## Out of Scope

- Re-anchoring highlights after a lesson is edited (ODY-198). Don't change how text offsets are counted: existing saved positions depend on it, line-number gutters and KaTeX markup included.
- The other ODY-508 actions (notes, and highlight *reads*). Only the three highlight writes and `getHighlights` move off the allowlist here.
- `createNote`'s signature and auth (ODY-508).
- Highlighting in block types other than `droplets.generic` (ODY-33).
- Strapi schema changes. None are needed.

## Design Decisions

1. **Draw only from state.** `LessonRenderer` owns the highlight list, and the DOM is always derived from it. No component wraps the selection by hand any more. A new highlight is added to state at once with a temporary negative id (from a counter ref, starting at -1). When the save returns, the server record replaces it. If the save fails, it's removed.
2. **Drawing effect deps: `[nonTableContent, blockHighlights]`.** `blockHighlights = useMemo(filter, [highlights, block.id, sourceIdsKey])`, where `sourceIdsKey` is `block.sourceBlockIds?.join(",") ?? ""`. Every block redraws when the lesson's highlights change. That's acceptable: it only happens after a toolbar action, when the selection is being cleared anyway. It keeps lint clean, with no `exhaustive-deps` disables (the codebase has none).
3. **Pending highlights (negative id) are inert.** Clicking them doesn't open the toolbar, and merges ignore them.
4. **Overlap = merge (ODY-153).** For a new selection `[s, e)`, take this block's saved highlights (id > 0) with `h.start < e && s < h.end`.
   - None: create a new highlight.
   - Some: keep the one with the smallest `start`. Update it to `[min starts, max ends)`, with `text` read from the block's DOM over that range and the chosen colour. Then delete the rest.
   - A selection *entirely inside* one highlight is treated as that highlight (recolour, note, remove), as today.
   - Only strict overlap merges, not adjacency.
5. **Find "the highlight under the selection" by offsets, not DOM ancestry.** Use the block's highlights and the selection's `[s, e)`.
6. **Action signatures** (`frontend/lib/requests/highlights.ts`, all `withAuth([])`):
   - `createHighlight(input: { text: string; position: { start: number; end: number }; color: HighlightColor; blockId: number; lessonId: number })`. `authorized_user` is `user.id`.
   - `updateHighlight(id: number, changes: { color?: HighlightColor; position?: { start: number; end: number }; text?: string })`.
   - `deleteHighlight(id: number)`.
   - Update and delete read the record first: `fetchAPI` `/highlights` filtered by id, `populate: { authorized_user: { fields: ["id"] } }`, `next: { tags: [CACHE_TAGS.highlights(user.id)], revalidate: 0 }`. Then `assertOwner(h.authorized_user?.id, user, { bypassRoles: [] })`, so private study data isn't editable even by admins (ODY-508's recommendation).
   - Writes use raw `fetch` with `STRAPI_RESPONSE_FORMAT_HEADER`, `flattenAttributes` the response, and `revalidateTag(CACHE_TAGS.highlights(user.id))`.
   - Failures return `{ ok: false, error: "Failed to save highlight" | "Failed to update highlight" | "Failed to delete highlight" | "Highlight not found" | "forbidden" | "unauthenticated", data: null }`. They never throw; a network error is caught and returned the same way.
7. **Component callbacks.**
   - `onHighlight(h, isWithNote?) => Promise<Highlight | null>`.
   - `onUpdateHighlight(id, changes) => Promise<Highlight | null>` (new).
   - `onDeleteHighlight(id) => Promise<boolean>`.
   - `onNote(notePos: number, highlight: Highlight)`.
   - `LessonRenderer` does the optimistic state change and rollback, and owns the toasts. Keep today's success strings ("Highlight saved", "Highlight removed", "Note created"). Errors: "Failed to save highlight", "Failed to update highlight", "Failed to remove highlight", "Failed to create note".
8. **Note position.** Today it's `mousePositionY`: the mouse-down Y relative to the content div. From Task 3.1 it's `selectionRect.top - contentRect.top`, the same meaning without a mouse. For a clicked highlight, use that piece's rect.
9. **Toolbar placement.**
   - `GenericBlockRenderer`'s outer div becomes `relative`, and the toolbar is rendered inside it, after the content, `absolute`.
   - Above the selection: `top = rect.top - wrapper.top - toolbarHeight - 8`.
   - Below the selection: `rect.bottom - wrapper.top + 8`. Use it when `rect.top - toolbarHeight - 8 < headerBottom`, where `headerBottom` is the bottom of the site header (`document.querySelector("header")?.getBoundingClientRect().bottom ?? 0`).
   - `left` is the selection's centre, clamped inside the wrapper.
   - Before relying on this, check that no ancestor of the lesson content has `overflow: hidden` that would clip it. If one does, stop and report.

## Test harness facts (verified; read before writing tests)

- `jest.setup.ts:23-25` replaces `document.createRange` so every range's `getBoundingClientRect` is a bare `jest.fn()` returning `undefined`. Tests that open the toolbar must set `range.getBoundingClientRect = () => ({ top: 200, left: 100, bottom: 220, right: 160, width: 60, height: 20, x: 100, y: 200, toJSON: () => ({}) })` on their range, *and* on any range the component builds. The simplest way is to also stub `Range.prototype.getBoundingClientRect` in `beforeEach` and set it per range.
- jsdom implements real `Selection`/`Range` and live ranges. Select with `range.setStart/setEnd` plus `getSelection().addRange(range)`. After `innerHTML` is replaced, the old text nodes have `isConnected === false` and `getSelection().toString() === ""`. That's how test 1 detects a rebuild.

- `selectionchange` must be dispatched by hand: `act(() => document.dispatchEvent(new Event("selectionchange")))`, then advance timers past the debounce with `jest.useFakeTimers()` / `act(() => jest.advanceTimersByTime(200))`.
- The scratch reproduction that confirmed problems 1 to 5 is in `ody-785-repro.test.tsx`, next to this plan's source in the session scratchpad.
