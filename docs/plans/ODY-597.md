## CKEditor stand-in design

`@ckeditor/strapi-plugin-ckeditor@0.0.11` only works with Strapi v4. It is listed as a dependency, but it has no entry in `config/plugins.ts`.

Uninstalling the package is not enough. If an attribute has `type: customField` and its plugin is missing, v5 throws `Could not find Custom Field: plugin::ckeditor.CKEditor` at boot (`packages/core/core/src/registries/custom-fields.ts`). So the 5 attributes are switched to a plain core type for now.

**Chosen type: `richtext`.** Reasons:

1. It is the plugin's own underlying type, in both 0.0.11 and the v5 line (1.1.2 registers `{ name: 'CKEditor', plugin: 'ckeditor', type: 'richtext' }`).
   - The generated types already say `Attribute.RichText & Attribute.CustomField<…>` (`backend/types/generated/contentTypes.d.ts:954-961`, `components.d.ts:42-50, 63-71, 164-171, 186-194`).
   - So the DB column stays `text`. There is no ALTER, and no data is touched.
2. The REST value stays a string. The frontend (`frontend/types/index.d.ts`: `overview?: string`, `content: string`) is unaffected.
3. Reverting it in ODY-598 only means adding things back. The v5 plugin keeps the uid `plugin::ckeditor.CKEditor`, so ODY-598 can restore the original JSON almost exactly as it was. Only the `options` keys need checking against 1.x.

`text` was rejected. It is also a `text` column, but it would change the declared base type twice (richtext → text → richtext/customField) for no benefit.

## Constraints discovered

- **Node:** v5 needs `>=20.0.0 <=26.x.x`. Local v24.12.0 and CI's 20.14.0 are both fine. The `backend/package.json` engines field (`<=20.x.x`) must be updated.
- **Postgres:** v5 documents PG 14 as the minimum (17 recommended), but **does not check the version at boot**. Locally, `strapiDB` is PG 12.0 (`docker-compose.yml:33`), so `ody597` boots on PG 12. That is enough for build and boot; supported-version testing is ODY-602's job, on PG 18. AWS shows prod on PG 18 and dev on 16.13, but terraform still says `13.20` (a separate drift ticket). Agents must not change docker-compose or terraform.
- **The `strapi` container must stay stopped for the whole ticket.** It mounts `backend/src`, `config`, `types` and `package.json`, and runs `strapi develop` against `strapiDB`. If it starts, it runs the one-way v5 migration on `strapiDB`.
- **`DATABASE_URL`:** `config/database.ts` reads it first, so the boot script exports `DATABASE_URL=` as empty.
- **Upgrade tool requirements:**
  - Being on the latest v4 (4.26.2) is a hard requirement. We meet it.
  - The clean-git-tree check is _optional_. The tool prompts "Ignore optional requirement…", and `--yes` ignores it silently. But `--yes` answers yes to **every** prompt, so prefer a clean tree (Task 2) and answer the prompts by hand.
- **Codemod behaviour, confirmed in the source:**
  - `comment-out-lifecycle-files` **will** comment out all 5 lifecycle files.
  - `entity-service-document-service` **will** rewrite Entity Service calls and insert `documentId: '__TODO__'`. It is the only codemod that writes `__TODO__`.
  - `dependency-upgrade-react-router-dom` sets `^6.0.0`, but the v5 peer dependency is `^6.30.3`, so pin it to that.
- **S3 keys:** the `s3-keys-wrapped-in-credentials` codemod should move the keys at `config/plugins.ts:46-49` into `s3Options.credentials`. The docs and the source disagree on whether this case is handled. Keys left at the root still work, with a deprecation warning, and don't block boot. Leave that for ODY-598.
- **`admin.ts`:** no change needed. `apiToken.secrets.encryptionKey` is optional; without it, a token is shown only once.
- **The v5 first-boot DB migration is one-way.** It runs, in order:

  1. identifier shortening for names over 55 characters (`links` becomes `lnk`, `morphs` becomes `mph`, plus a hash suffix);
  2. adds `document_id`;
  3. adds `locale`;
  4. adds `published_at`;
  5. drops the slug unique index;
  6. adds document_id indexes;
  7. the core data migrations (draft-publish, i18n, first-published-at).

  Some link-table names may change, which matters for the SQL in ODY-633 and ODY-598. Tasks 1 and 8 capture the table list before and after.

- **Reserved names:** `status` (used on droplet and voyage) is **not** in v5's general `RESERVED_ATTRIBUTE_NAMES`. It is only in `RESERVED_ATTRIBUTE_NAMES_DRAFT_PUBLISH`, and that check only warns, and only when D&P is on. With D&P off, boot shows no warning and no error. Task 7 confirms this against the installed source.
  - Admin caveat: the Content-Type Builder refuses to _create_ a new attribute named `status` on any type. Editing the existing ones still works.
- **users-permissions extension:** the extra `info.name` in the user extension is harmless, because the v5 validator doesn't use `.noUnknown()`. The extension has no custom fields.
- **Repo rules still say v4.** `CLAUDE.md`, `.claude/rules/strapi-backend.md` and the `strapi-v4-patterns` skill all say "v4 only", but on this branch the backend **is v5**.
  - Implementer: follow this plan and Context7 (v5) for backend config. Don't change code back to v4.
  - Task 5 adds a short v5 branch note to all three (approved). Rewriting them fully for v5 is a follow-up for after ODY-606.

## Risks

- **DB migration safety (high impact).** The first v5 boot is one-way: it renames identifiers and adds columns. Booting against `strapiDB` or `ody633` destroys the v4 baseline that ODY-598 and others need.
  - Boot only through `boot-ody597.sh`. It hardcodes `ody597`, refuses v4 code, and refuses to run while the `strapi` container is up.
  - Check `pg_stat_activity` after every boot.
  - Re-cloning (Task 9) is the only undo.
- **Codemods silently disable behaviour (certain).**
  - Commented-out lifecycles disable the Slack alerts, slug generation and the lesson blocks guard.
  - Entity Service calls get `__TODO__` document ids, which break at runtime.
  - Mitigation: take a checkpoint, then review in Task 4. By default, **restore** the lifecycles and **revert** the Entity Service rewrites. Entity Service still exists in v5, so this keeps today's behaviour. ODY-606 and ODY-599 own the real migration.
- **TS build blockers (high).** The `Strapi` type import in `custom-lesson.ts`, and the generated types in v4 style. Task 5 fixes the import and Task 6 regenerates the types.
- **Typegen fails on `develop` (high).** v5 runs typegen automatically for TS projects, and Prettier fails on the root ESM plugin.
  - Task 6 adds `backend/.prettierrc.json` so that Prettier stops at `backend/`. This has no effect on the frontend.
  - `autogenerate: false` is **not** a fallback: v5 ignores it for TS projects (`develop.ts:271-287`).
- **A plugin fails to load (medium)**: documentation, upload aws-s3 or users-permissions. (cloud is removed.)
  - documentation and provider-upload-aws-s3 both exist at 5.56.0.
  - If one fails, fix its config shape first. As an approved last resort, set `documentation: { enabled: false }` in `config/plugins.ts` and flag it for ODY-598.
  - Never disable users-permissions or upload.
- **`overrides` conflict with v5 dependencies (medium).** The tool runs the install itself, so a conflict can make its install step fail. Task 7 does a clean reinstall, runs `npm ls`, and decides whether to keep or drop each override.
- **Postgres 12 is below the v5 minimum (low, locally).** Boot isn't gated, but queries that need newer PG would only fail at runtime. Record anything odd for ODY-602, which rehearses on PG 18.
