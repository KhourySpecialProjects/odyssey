# ODY-481: `getAdminDashboardStats` Server Action has no role check

Linear: https://linear.app/aiil/issue/ODY-481 — Priority High (2), Backlog
Related: ODY-474 (unrelated cause, same branch), ODY-482 (the general audit — see "Deferred to ODY-482" below)

## Problem

`frontend/lib/requests/admin-stats.ts` begins with `"use server"` (line 1). Every exported
async function in such a file is compiled into an independently callable POST endpoint with a
stable action ID. `getAdminDashboardStats` (line 73) performs **no authorization check** before
querying Strapi for platform metrics.

The `/admin` **pages** are gated correctly — `app/(general)/admin/layout.tsx:12-13` runs
`getCurrentUser()` + `isAuthorizedUserAdmin(user.roles)` and returns `notFound()`. But **a layout
only runs while rendering a page; it does not run when a Server Action is invoked.** The action is
therefore reachable independently of the layout that protects the page it was written for.

### Verified evidence

| Layer         | File                                            | Check                                                 |
| ------------- | ----------------------------------------------- | ----------------------------------------------------- |
| Middleware    | `frontend/middleware.ts:3-9`                    | `return !!token` — **authentication only, no role**   |
| Admin layout  | `frontend/app/(general)/admin/layout.tsx:12-13` | ✅ `isAuthorizedUserAdmin(user.roles)` → `notFound()` |
| Admin page    | `frontend/app/(general)/admin/page.tsx`         | none — relies on the layout                           |
| Server Action | `frontend/lib/requests/admin-stats.ts:73`       | ❌ **none**                                           |

- The only in-app caller is `frontend/app/(general)/admin/page.tsx:94`, inside `StatsAndPageviews()`
  (`Promise.all([getAdminDashboardStats(), fetchUniquePageview()])`). It dereferences `stats.users.current`
  etc. immediately — **it does not handle `undefined`.** This constrains the rejection mechanism (see
  Design Decisions).
- `AuthorizedUserAdminRoles` (`frontend/lib/globals.ts:26`) is `[AuthorizedUserRoleTitle.SysAdmin]` —
  a single role. So "admin" here means System Admin only.
- A purpose-built guard already exists: `frontend/lib/auth/require-role.ts` → `requireRole(allowed[])`,
  docstring "Guard for Server Actions". It never throws; it returns
  `{ ok: true, user } | { ok: false, error: "unauthenticated" | "forbidden" }`. Already used by
  `lib/requests/voyage.ts:11`, voyage-enrollment, lesson-lock, and authorized-user update paths.
- `requireRole` depends on exactly `getCurrentUser` (`@/lib/auth/session`) and `getCachedUser`
  (`@/lib/requests/cached`) — **the two modules the failing test already mocks.** The test was written
  anticipating this helper.
- No import cycle risk: nothing imports `admin-stats.ts` except `admin/page.tsx` and the test.

### The failing test (already exists — do not rewrite it)

`frontend/testing/auth/admin-stats-authorization.test.ts`

```
✕ denies a signed-out caller without querying protected data
✕ denies a signed-in non-admin without querying protected data
✓ allows a System Admin and returns statistics
```

The primary assertion is `expect(protectedDataWasQueried()).toBe(false)` — it inspects the
data-access mocks (`fetchAuthorizedUsersMetadata`, `fetchEnrollmentMetadata`, and `global.fetch`,
which `fetchDropletCount` uses directly). **Rejection must happen before any data access**, not
merely before returning. A guard placed after the `Promise.allSettled` block would still fail.

Secondary assertion: `expect(result.threw ? undefined : result.value).toBeUndefined()` — the test
accepts **either a throw or an `undefined` return**. It does **not** accept a
`{ ok: false, error }` envelope.

These 2 tests are the entire reason CI is red on
`bug/ody-474-bug-groups-not-being-removed-from-groups-page-when-deleting`. The failure is unrelated
to ODY-474 — the test imports nothing from the groups module.

### Impact

`getAdminDashboardStats()` returns **aggregates only**: total users, droplet count, enrollment and
completion counts, retention rate, 30-day trends. No per-user PII. Combined with the working layout
gate, exploitation requires a caller who can invoke a Server Action directly, and the payoff is
business metrics. High, not Urgent.

## Design Decisions

### 1. Use the existing `requireRole` helper, not a hand-rolled check

The ticket's suggested fix (`getCurrentUser()` + `isAuthorizedUserAdmin(user.roles)`) mirrors the
layout literally, but `frontend/lib/auth/require-role.ts` already exists for exactly this job and is
the pattern ODY-482 will apply across ~25 files. Two guard idioms for the same problem is worse than
one. Both satisfy the test.

Two known consequences, accepted deliberately:

- **Role source differs from the layout.** `requireRole` resolves roles from Strapi via
  `getCachedUser`, while the layout reads session/JWT roles. Strapi is the source of truth, so the
  action is _stricter_: a revoked role takes effect on the next `CACHE_TAGS.users` invalidation or
  after at most 15 minutes (`getAuthorizedUserByEmail` fetches with `revalidate: 900` —
  `lib/requests/authorized-user.ts:57`), rather than waiting for the next JWT refresh. Stricter,
  but not instant.
- **Dev role-override divergence.** `getCurrentUser` applies the `dev-role-override` cookie
  (`lib/auth/session.ts:33-50`, requires `NODE_ENV=development` **and**
  `ENABLE_DEV_ROLE_OVERRIDE=true`); `requireRole` ignores it because it re-reads roles from Strapi. A
  developer who overrides _up_ to System Admin while their Strapi record is not admin will pass the
  layout but be rejected by the action, producing an error page on `/admin`. This divergence already
  exists for every `requireRole` caller (e.g. `voyage.ts`), so this change does not introduce a new
  class of problem. If it bites, the fix is a one-liner in the guard — not in this file.

### 2. Reject by throwing, keeping the return type `Promise<AdminDashboardStats>`

Considered and rejected:

- **Return `undefined`** → the signature becomes `Promise<AdminDashboardStats | undefined>`, which
  breaks `admin/page.tsx:100-123` (`stats.users.current` on a possibly-undefined value) and forces
  caller churn for a branch that is unreachable behind the layout gate.
- **Return `{ ok: false, error }`** (the `voyage.ts`/`droplet.ts` envelope convention) → fails the
  test's `toBeUndefined()` assertion, and would require reshaping every call site.
- **`notFound()` inside the action** → would mirror the layout most precisely and does satisfy the
  test, but its behavior when the action is POSTed directly (outside a render pass) is not verified
  here. Not worth the uncertainty for an unreachable path.

A plain `throw` keeps the diff to one file, leaves the happy path byte-identical, and satisfies the
test (`invokeAction()` catches it → `threw: true` → value `undefined`). In production Next.js
replaces the thrown message with an opaque digest, so nothing leaks to the caller.

### 3. Guard placement: the first statement of the function

Before `const cutoff = daysAgo(30)` and before the `Promise.allSettled` block. The test asserts on
data-access mocks, so any guard placed after the fetches fan out fails regardless of return value.

### 4. Do not log the caller's identity

Keep the rejection silent or log a constant string. Writing caller emails to logs on a security-reject
path creates a PII sink. (The test spies on `console.error`, so logging would not fail the suite —
this is a deliberate choice, not a constraint.)

## Deferred to ODY-482 (investigated, intentionally not fixed here)

An audit of every data function the `/admin` tree renders. Only functions in files whose **line 1**
is `"use server"` are independently callable; the rest are ordinary modules reachable only through
the guarded layout.

| Function                                                                  | File                                 | `"use server"` | Role check | Returns                                                                 |
| ------------------------------------------------------------------------- | ------------------------------------ | -------------- | ---------- | ----------------------------------------------------------------------- |
| `fetchAuthorizedUsers`                                                    | `lib/requests/authorized-user.ts:96` | **Yes**        | **No**     | **PII — whole user table: email, first/last name, bio, socials, roles** |
| `fetchCreationRequests`                                                   | `lib/actions.ts:682`                 | **Yes**        | **No**     | **PII — populates `user: {firstName, lastName, email, id}`**            |
| `getVoyagesAdmin`                                                         | `lib/requests/voyage.ts:203`         | **Yes**        | **No**     | Unpublished voyages + author emails (partial PII)                       |
| `getPlaylists`                                                            | `lib/requests/playlist.ts:20`        | **Yes**        | **No**     | Content metadata                                                        |
| `getAdminDashboardStats`                                                  | `lib/requests/admin-stats.ts:73`     | **Yes**        | **No**     | Aggregates — **fixed by this plan**                                     |
| `fetchDroplets`, `fetchGroups`, `fetchAccessRequests`, `fetchReports`     | `lib/requests/data.ts`               | No             | No         | Not independently callable — no action endpoint                         |
| `fetchDailyActiveUsers`, `fetchUniquePageview`, `fetchAvgSessionDuration` | `lib/requests/posthog.ts`            | No             | No         | Not independently callable — no action endpoint                         |

**`fetchAuthorizedUsers` is more severe than ODY-481 itself**: no arguments, no gate, and it
paginates the entire user directory with emails. It is _not_ folded into this plan because (a) it
has no failing test to anchor the change, (b) unlike `getAdminDashboardStats` it likely has
non-admin call sites (author pickers, mention/search UIs) that an admin-only guard would break, so it
needs its own call-site survey, and (c) bundling it would stop this branch from going green on a
narrow, reviewable diff.

**Recommended follow-up for the human (not an agent task):** raise ODY-482's priority to Urgent and
paste this table into it. Do not create sub-issues from this plan.
