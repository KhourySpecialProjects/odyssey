## Blocking

### B1 — The client-boundary test covers only one of the two server-only files, and nothing guards a `"use server"` wrapper (Important)

**Where:**

- `frontend/testing/lib/mentor/client-boundary.test.ts:26-27` on PR2: `LESSON_MODULE` gains `learner-source`, but `@/lib/requests/learner-enrollments` isn't in it. The regex only matches `@/lib/mentor/…`.
- `frontend/lib/requests/learner-enrollments.ts:1` and `frontend/lib/mentor/learner-source.ts:1`.

**Why:**

- A client import is already a build error, thanks to `server-only`. The review brief asks for the boundary test to cover both files, and today it covers only `learner-source`.
- The bigger risk is the one the plan names under "Wrong user": somebody later adds `export async function x(id: number) { return getLearnerEnrollments(id); }` to a `"use server"` file. The Server Action auth guard would accept it once that function calls `requireRole`, because `requireRole` doesn't tie the argument to the session. The new fetch sits in `lib/requests/`, next to `enrollment.ts`, which _is_ `"use server"`, so this is an easy mistake.

**Smallest fix:**

- In `client-boundary.test.ts`, widen the module regex to also match `["']@/lib/requests/learner-enrollments["']`, and add one `it.each` row for it.
- Add one scan test: no file whose first statement is `"use server"` imports `@/lib/mentor/learner-source` or `@/lib/requests/learner-enrollments`. The test can reuse `clientFiles` with the directive regex swapped.
- About 10 test lines, no code change.

## Non-blocking

### N1 — Sorting by `lastProgressDate:desc` puts nulls first in Postgres (Important)

**Where:** `frontend/lib/requests/learner-enrollments.ts:37`

**Why:** Postgres sorts `DESC` with NULLS FIRST. Old enrollments with no `lastProgressDate` (the same rows Q3's fallback exists for) come before recent ones. For a student with more than 250 enrollments, the newest ones are dropped, not the oldest as the plan intended. It's rare today, and it gets more likely once ODY-957 reuses this fetch.

**Smallest fix:** `sort: ["updatedAt:desc"]`. `updatedAt` is never null, and `toLearnerContext` re-sorts anyway. Update the expected params in `learner-enrollments.test.ts`.

### N2 — The number of tags per finished droplet isn't bounded, so tags can push out the finished history (Important)

**Where:** `frontend/lib/mentor/learner.ts:153`

**Why:** Each tag is cut to 60 characters, but every tag is kept. In the worst case above, the rest of the block takes 2,091 characters, and one finished line with 10 long tags is about 700. **No** finished droplet survives `learnerBlock`'s trimming, and with 1-3 tags at most one does. The cap holds, but the section the block exists for is the one that goes. Q13 bounded names, prerequisites and viewed titles, not tags.

**Smallest fix:** `.slice(0, 3)` on the tags before `cut`. Add a `TAGS_MAX = 3` const beside the others and one test assertion.

### N3 — The worst-case test leaves viewed lessons out (Important)

**Where:** `frontend/testing/lib/mentor/learner.test.ts:196`

**Why:** The current droplet `99` has no enrollment in the fixture, so `viewedLessons` is empty. The "everything else still fits" assertion never exercises the 15 × 60-character titles that Q13's bound is about. The bound does hold (2,091 characters with them, per my check), but no test pins it.

**Smallest fix:** Add an in-progress enrollment for droplet 99 with 20+ long viewed titles. Assert that `rest.length <= LEARNER_MAX_CHARS` and that `ctx.viewedLessons.length === 15`.

### N4 — Missing Q2 cases for in progress and prerequisites (Nit)

**Where:** `frontend/testing/lib/mentor/learner.test.ts:76` and `:142`

**Why:**

- Hidden and unpublished droplets are tested for finished. For in progress, nothing tests them. For prerequisites, only `isHidden: true` is tested, not `status: "draft"` or `isHidden: null`.
- The code is right, because both paths go through `visible`, but a refactor that filters only finished would pass.

**Smallest fix:**

- Add one hidden in-progress row and assert `inProgress` is empty.
- Add prerequisites with `status: "draft"` and with `isHidden: null`, and assert both are dropped.

### N5 — Viewed-lesson titles come in relation order, not lesson order (Nit)

**Where:** `frontend/lib/mentor/learner.ts:185`

**Why:** `viewedLessons` comes in the order the enrollment's relation stores it. For a droplet with more than 15 viewed lessons, `slice(0, 15)` keeps an arbitrary 15, and the block lists them out of course order.

**Smallest fix:** Sort them by their index in `here.droplet.lessons`, which is already fetched and ordered, before slicing. Or accept this and say so in the docblock.

### N6 — The prerequisite type is declared twice (Nit)

**Where:** `frontend/lib/mentor/source.ts:9` (`Prerequisite`) and `frontend/lib/mentor/learner.ts:85` (`LearnerCurrentDroplet.prerequisites`)

**Why:** They are the same shape, written twice. They can drift apart, because `learner-source.ts` passes one into the other only by structural typing.

**Smallest fix:** Export `LearnerPrerequisite` from `learner.ts`, the module with no server-only import, and use it in `source.ts`. That removes about 6 lines.

### N7 — `getLearnerContext` swallows the error silently (Nit)

**Where:** `frontend/lib/mentor/learner-source.ts:24`

**Why:** Failing closed to `null` is right. But once PR3 wires this in, a Strapi 400 (for example, strict REST rejecting a key) means personalization never fires, and there's no trace of why.

**Smallest fix:** `console.warn("mentor learner context failed", (e as Error).message)`, with no user id. Or leave it for PR3's log line (Q12) to report `learner: false`.

### N8 — The backend doesn't pin that strict REST accepts `personalize` (Nit)

**Where:** `backend/tests/lib/mentor-settings.test.js:126` on PR1

**Why:** The frontend's contract catalog mocks the response. Nothing on the backend proves that `GET /api/mentor-setting?fields[0]=enabled&fields[1]=personalize` returns 200 and the field.

**Smallest fix:** Extend "can be read with the service token" with that query, and assert `res.body.data.personalize === false`.
