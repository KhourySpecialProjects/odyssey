# ODY-939 — Mentor: save lesson quiz attempts

Plan only. Written on `claude/ody-939-plan`, cut from `origin/develop` at `8f08f16e`. Nothing here is decided until Jaylen answers the questions in section 2.

## 1. Summary

Quiz results are the best signal of what a student knows, but today they live only in the browser's sessionStorage and in PostHog. ODY-939 adds a `quiz-attempt` content type with one row per lesson quiz submit: the student, lesson, droplet, question, whether it was right, the attempt number and the time, never the answer. A guarded Next server action writes the row, fired from both quiz blocks without blocking the UI. A second PR reads the student's last 30 days and adds one line to ODY-934's learner block: "Recently missed: {lesson} ({n} questions)". Nobody else reads the rows in this ticket.

### Current submit flow on develop

Multiple choice and true/false (`frontend/components/droplets/lessons/quiz-question.tsx`):

- `quiz.tsx:28-42` renders one `QuizQuestionBlock` per question with `lessonId`, `dropletId`, `userId` from `lesson-renderer.tsx:591-609`.
- Grading is on the client: `onSubmit` (`quiz-question.tsx:131`) calls `areAnswersCorrect` (`:189-196`), which compares the picked option ids with `answerOptions[].isCorrect`. The browser already has the answer key.
- PostHog: `quiz_answer_submitted` (`:136-150`, with `is_correct`, `question_id`, the first 100 characters of the question, `user_id`) and `quiz_answered_correctly` (`:153-168`). No attempt number on this path.
- ODY-890's `mentor_hint_next_try` fires in the same `onSubmit` (`:170-178`) when a hint came before this try. ODY-888's "Explain my answer" reads `showResult` and the picked ids after submit (`:198-233`). There's no shared submit hook; `onSubmit` itself is the hook.
- sessionStorage: `saveQuizAnswer` (`lib/quiz-storage.ts:7-20`) on every change (`quiz-question.tsx:109-121`) and on `showResult` (`:124-129`), key `quiz-{lessonId}-{questionId}`. It restores on mount (`:95-106`). Per tab only; nothing reaches the server.

Open-ended (`frontend/components/droplets/lessons/open-ended-quiz-question-block.tsx`):

- `open-ended-quiz.tsx:29-45` renders one block per question. `lessonId` is optional here.
- Grading is on the client too, and it is exact: `checkAnswer` (`:59-63`) compares the normalized typed text with `stripHtmlTags(question.correctAnswer)`. There is no AI grading, so "correct" is known at submit.
- `numTries` (`:40`, `:65-67`) counts only wrong tries and resets on reload.
- PostHog: `quiz_answer_submitted` with `attempt_number` (`:70-85`) and `quiz_answered_correctly` with `attempts_taken` (`:88-104`). No sessionStorage on this path.

### Question ids (what the ticket says vs the code)

- BlockNote lessons: `convert-blocks.ts:328` sets a question's id to `blockNoteIdToNumber(block.id)`, a 32-bit hash of BlockNote's own block id. That id survives edits, moves and new blocks above it. It changes only when the block is deleted and recreated (or pasted as a copy). Position is used only for a block with no id (`blockIndex`). Option ids, on the other hand, are positional (`blockIndex * 100 + optionIndex`, `:407`; true/false `:425-430`).
- Classic lessons: the id is the Strapi component's id. Open-ended and choice questions live in different component tables, so their ids can collide in one lesson (`lib/mentor/quiz.ts:42-46` says so). The stored key must include the quiz type.
- So the ticket's "ids come from block position" is mostly not true for questions, which helps. They still aren't permanent, and the plan treats them as a 30-day signal.

### Precedent to copy

ODY-890's `saveMentorFeedback` (`lib/requests/mentor-feedback.ts:33-86`) is the closest pattern: `requireRole([])`, a Zod parse, `getMentorSource` + `lessonAccess` to check the lesson is in the droplet, then a POST with the service token to a Strapi custom route (`backend/src/api/mentor-feedback/routes/custom-mentor-feedback.ts`), whose controller parses strictly (`lib/route-body.ts`) and calls a lib function that uses the Document Service. `mentor-usage` shows a read-only core router (`only: ['find']`).

## 2. Design questions

Each has a recommendation, and the tasks in section 3 assume it.

**Q1. Which question id to store?**

- a) The id the learner page renders (`question.id`), plus `quizType` (`choice` | `open-ended`). **Recommended.** It's what the client and Mentor's `findQuizQuestion` already use, and for BlockNote it's the stable hashed block id.
- b) The BlockNote string block id. More stable, but Classic lessons don't have one, and the rendered tree doesn't carry it to the quiz components today.
- c) A hash of the question text. Survives recreate, but changes on every typo fix and needs the text at write time.

Recommendation: a). The column is `biginteger` (or `string`), not `integer`: `Math.abs` of a 32-bit hash can be 2^31, one past Postgres `integer`.

**Q2. One row per submit or per question?**

- a) One row per submit (per question, per Check Answer). **Recommended.** It's what the ticket asks, retries stay visible, and the "since got it right" rule reads the latest row.
- b) One row per question, updated with a count. Fewer rows, but loses the history and needs an upsert.

Recommendation: a). A quiz block in BlockNote holds one question, so "submit" and "question" coincide there anyway.

**Q3. Open-ended grading.**

- a) Store the client's exact-match result at submit. **Recommended.** That's the only grading the app has (`open-ended-quiz-question-block.tsx:59-63`).
- b) Wait for an AI grade. There is none today; it would be a new feature.

**Q4. Who decides "correct"?**

- a) The client sends `correct`. **Recommended.** Lying only skews the student's own Mentor; the server still checks the question exists in the lesson.
- b) The server grades choice questions from the picked option ids (`choiceQuestionById` already has the key) and trusts the client for open-ended. Tamper-proof for choice, one more lesson read per write, and option ids reach the server (ids, not text).
- c) The server grades both. Open-ended would need the typed text sent to the server, which the ticket rules out storing and we'd rather not send.

**Q5. Next server action vs Strapi custom route.**

- a) Both, like ODY-890: a guarded server action `recordQuizAttempt` in `lib/requests/quiz-attempt.ts` takes the user from `gate.user.id` and POSTs with the service token to `POST /quiz-attempts/record`. No core create/update/delete routes. **Recommended.**
- b) The action writes with core `create` over REST. One fewer backend file, but the attempt number and dedupe then need a read-then-write from Next, and core `create` stays open to the token for any user id.
- c) A Strapi route called straight from the browser with the user's JWT. There's no per-user Strapi auth in this app; everything goes through the service token.

**Q6. How enrollment is checked.**

- a) In the backend route, in the same handler that counts attempts: one Document Service `findFirst` on `api::enrollment.enrollment` with `authorizedUser.id` and `droplet.id`. 403 when missing, and the action drops it quietly. **Recommended.** One round trip, always fresh, and no new frontend reader.
- b) In the action, via `getEnrollmentByUserAndDroplet`. It's an unguarded `"use server"` export (`PENDING_AUTH` ODY-507), cached by `fetchAPI`, so it is the wrong thing to lean on.
- c) A new server-only frontend helper. Fine, but an extra Strapi call on every submit.

The action still runs `getMentorSource` + `lessonAccess` first (cached 900 s), so the lesson must belong to the droplet and the question must exist in it (Q1). Unlike ODY-890 it doesn't require `access.mentor`: a published-but-hidden droplet still records, and the read side filters (Q11).

**Q7. Idempotency and double submit.**

- a) The client sends a `submitId` (`crypto.randomUUID()`) per Check Answer. The backend returns the existing row when `(user, submitId)` exists. The attempt number is `count(user, lesson, quizType, questionId) + 1`, set in the backend. **Recommended.**
- b) No dedupe. A double click makes two rows with the same attempt number at worst.
- c) A unique `(user, lesson, quizType, questionId, attempt)` constraint. Strapi schemas can't declare it; it needs a raw migration.

Recommendation: a). Two truly concurrent submits can still share a number; that's harmless for a "latest row wins" read. Add a per-user daily cap (500 rows, 429), like ODY-890's, so a script can't fill the table.

**Q8. Retention and deletion.**

- a) Delete rows older than 30 days, with the same job ODY-937 adds for mentor chats. **Recommended.** The only use is a 30-day signal, so keeping more is just risk.
- b) 90 days. Room for a later feature, but nothing in this ticket needs it.
- c) Keep forever, delete only with the account.

The catch: the backend has no scheduler today (no cron config, no `cron-tasks`). If ODY-937's job isn't on develop when PR A lands, PR A adds the row type only and a follow-up (or 937) adds `quiz-attempt` to its sweep. The read in PR B filters by 30 days regardless. There's no account deletion in the app either: deleting an authorized-user in the admin leaves rows with a null `user`. The sweep should also delete rows with no user.

**Q9. "Hasn't since got it right": computed on read or stored?**

- a) On read: fetch the last 30 days' rows, keep the newest per `(lesson, quizType, questionId)`, count those that are wrong. **Recommended.** No extra writes, and a student who gets it right clears it automatically.
- b) A stored `resolved` flag updated on a correct answer. Cheaper read, but a second write path and a consistency risk.

**Q10. Do authors or instructors read attempts?**

- a) No. No core `find` route, and the only reader is a `server-only` function that takes the user id from the Mentor route's session. **Recommended,** per the ticket.
- b) A read-only core `find` like mentor-usage, token-only. Simpler fetch, but it opens a read path anyone with the token or a later careless action can use.

Recommendation: a). PR B adds a custom `GET /quiz-attempts/recent` (token only, `userId` param, returns ids, `correct` and the lesson's id and name) that a later ticket can't mistake for a public list.

**Q11. What the Recently-missed line covers and how it renders.**

- a) All droplets, last 30 days, at most 5 lessons, newest miss first. Published, visible droplets only (ODY-934 Q2). One line, left out entirely when empty: `Recently missed: Loops (2 questions), Recursion (1 question)`. Lesson names cut to 40 characters with "…". **Recommended.**
- b) Only the current droplet's lessons. Shorter and more relevant, but misses the prerequisite struggling the ticket is about.
- c) A section in 934's format ("Recently missed quiz questions:" then `- ` lines, "none" when empty). Consistent, but every existing eval profile's text changes, so `learnersSha` changes.

Recommendation: a). Leaving the line out when empty keeps every existing eval profile's block and `learnersSha` unchanged. It goes last, after "Lessons of this droplet already viewed". Worst case is about 18 + 5 × 60 = 320 characters. With 934 Q13's worst case of about 2,150 that can pass 2,400, so `learnerBlock`'s trim loop drops the oldest finished droplets first (as now), then the oldest missed lessons, and a test pins the worst case at or under 2,400.

**Q12. PostHog: keep, replace or both?**

- a) Keep both events unchanged, and add the server write beside them. **Recommended.** Product analytics and ODY-890's dashboards read them; this ticket only adds a server record.
- b) Replace PostHog with the server rows. Removes the question text from PostHog, but breaks existing funnels; a separate privacy ticket if wanted.

**Q13. Write before ODY-935's disclosure ships?**

- a) Write from PR A on, for everyone. **Recommended.** It's the student's own data, PostHog already records the same result with their id, and nothing reads it until the 934 switch and the student's 935 toggle are both on.
- b) Write only while `mentor-setting.personalize` is on. Less stored, but the first personalized asks have no history.
- c) Write only after the student opts in (935). Strictest, and it ties PR A to 935.

If Jaylen or Awad read 935's disclosure as covering collection too, pick b) until 935 lands.

## 5. Out of scope, risks and overlaps

Out of scope: author, instructor or admin views of attempts; storing answers; AI grading of open-ended answers; changing PostHog events; moving sessionStorage to the server; the disclosure text (ODY-935); account deletion as a feature; the ODY-953 learner-profile quiz, which is a different "quiz".

Risks:

- **Privacy.** New per-student learning data on the server. Ids, a boolean, a number and a time only; the backend rejects unknown keys and the schema has no text field. The user always comes from the session. Retention per Q8; until a sweep exists, rows accumulate.
- **Ids drifting.** A recreated BlockNote block or a Classic save that renumbers components orphans old rows. The effect is a stale "missed" line for up to 30 days, and only if the student never answers the new question right. Acceptable per the ticket.
- **Write volume.** One small row per submit, plus three cheap reads (count, dedupe, enrollment). Even 10,000 submits a day is about 300,000 rows over 30 days; fine for Postgres without an index. The daily cap bounds abuse.
- **Fire-and-forget.** A failed write is lost, so the line can under-report. Acceptable: it's a hint to Mentor, not a grade.
- **Spoofed `correct`** (Q4 a) only changes the student's own Mentor context.

Overlaps: see section 3. ODY-934 PR 2 must be on develop before PR B; PR B updates the eval stub test in the same PR as the ticket asks.
