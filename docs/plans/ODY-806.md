## Problem

A reviewer reads a droplet that is in review and has no way to say what is wrong with a particular sentence. Today the only channel is one text box on Request changes (`droplet.afterReview`). ODY-799 and ODY-802 added the storage and the server actions. ODY-806 is the screen on top of them: comment on a whole block or on a few words, see the comments in the margin, open, resolve, edit and delete them.

The design is the Figma file "Inline Review Comments" (five screens). ODY-812 added numbering, margin tags that say what they are about, and a shared `lib/selection` module. ODY-836 (a drawn caret between letters) is **not** part of this ticket.

## What exists now (verified at bb161b2a)

**Server actions** (`frontend/lib/requests/reviews.ts`, PR #1144):

- `getOrOpenReview(dropletId)`, `addComment(input)`, `editComment`, `deleteComment`, `resolveComment`, `getReviewForDroplet(dropletId)`. Reviewer roles are System Admin and Content Editor. Results are `{ ok, error, data }`.
- `getReviewForDroplet` returns the **latest review of the droplet by anyone**: it filters on the droplet only and sorts `round:desc, id:desc`, page size 1. With two reviewers, a reviewer can get the other one's review. Nothing returns "my review with my comments". `getOrOpenReview` returns the caller's review but without comments.
- `addComment` checks that the review is open and belongs to the caller. It does not check that the caller isn't an author of the droplet (ODY-810 blocks self-review).

**Types and validation** (PR #1143):

- `ReviewAnchor = { v: 1; field: "blocks" | "description" | "overview" | "objective"; blockId?; start?; end?; quote; prefix; suffix }`, validated by a **strict** Zod schema.
- `quote` must be 1 to 2000 characters, so a whole-block anchor cannot be "just `blockId`" as ODY-801 says.
- There is no `point` field (ODY-801 now specifies it).
- `reviewCommentInputSchema` requires `lessonId` for `blocks` comments and null for the others.

**Learner highlights** (PR #1142, `components/droplets/lessons/generic-block-renderer.tsx`): the code to extract into `lib/selection`.

- `SELECTION_DELAY_MS = 150`, a `selectionchange` listener that debounces `readSelection`.
- `textNodes`, `offsetOf` (a boundary point to a character offset inside one block), and `anchorIn` (a rect relative to a parent).
- `selection-toolbar.tsx` places the toolbar above the selection, or below it under the site header (`.sticky.top-0.z-50`), clamped to the lesson column.
- It draws highlights by wrapping text nodes in `span.lesson-highlight[data-highlight-id]`. That is fine in read-only HTML and **not** usable inside an editor.

**Draft lesson page:**

- `app/(editing)/draft/d/[slug]/[lessonSlug]/page.tsx` fetches the lesson fresh and renders `components/draft/lesson/lesson-renderer.tsx`.
- That client component shows BlockNote through `blocknote-editor-client.tsx` (`editable` and `onChange` props) when `blocksVersion` is v2, and per-block TipTap editors (`blocks/*.tsx`) for Classic lessons.
- The Overview is `components/draft/metadata/*` (CKEditor HTML and plain fields).
- There is no review data on these pages and no comment layer.

**Anchors** (`frontend/lib/anchors/`, PR #1145):

- `createAnchor(Range | { blockId }, { field, root? })` returns an `Anchor` or null. A selection inside one BlockNote block gets `blockId`, `start`, `end`, `quote` and 30 characters of `prefix` and `suffix`. A selection in a Classic lesson or the Overview is anchored by quote within `root`. A **whole block** is `{ v: 1, field, blockId }` only.
- `resolveAnchor(content, anchor)` returns an `AnchorRange` (`field`, `blockId`, `start`, `end`, `exact`) or `"outdated"`. `blockNoteContent(blocks)` and `htmlContent(html)` build the content to resolve against.
- **Drawing:** `drawAnchor(root, range, id)` wraps text in `span[data-anchor-id]` for read-only HTML (the lesson view, a read-only Overview). In the BlockNote editor, `anchorsPlugin(getAnchors)` draws the same spans as ProseMirror decorations (register it with `editor._tiptapEditor.registerPlugin`, then call `refreshAnchors(view)`). Nothing covers the Classic lesson's per-block TipTap editors.
- No `point` field.
- **It doesn't fit the merged schema.** `Anchor` has `field: string` and optional `quote`, `prefix` and `suffix`. `ReviewAnchor` and the strict `reviewAnchorSchema` from #1143 require all three strings and limit `field` to four values. So `addComment` rejects every whole-block anchor with `invalid_input`, and passing an `Anchor` where a `ReviewAnchor` is expected doesn't type-check.

**Not present:** `frontend/lib/selection/`. ODY-810's `lib/review-roles.ts`, the reviewer read-only view, the Edit button and `FrozenOverview` are present through the stack.

## Design decisions

- **D1. Draw marks with ODY-801's tools, never by editing an editor's DOM by hand.**
  - **BlockNote:** register `anchorsPlugin` on the draft editor and call `refreshAnchors` when comments change. The plugin draws decorations, which ProseMirror owns, so they survive re-renders and typing in Edit mode.
  - **Read-only HTML** (a read-only Overview, and Classic blocks if the D12 spike picks the learner renderer): `drawAnchor` and `removeAnchor`.
  - **Classic blocks left as TipTap editors:** neither tool works, because each block is its own ProseMirror editor without the plugin. That is part of the D12 spike: register a TipTap version of the plugin per block, or render Classic blocks read-only in Comment mode.
  - **Styling** goes on `[data-anchor-id]`: a dashed amber underline for pending comments and a tint for sent ones. Tags and the whole-block wash sit in an overlay layer positioned from each span's `getClientRects()`.
- **D2. Comment mode is read-only plus a comment layer.** Reviewers get three states in the lesson bar: **Read** (no layer), **Comment** (layer on, the default while the droplet is in review) and **Edit** (ODY-810's lock, layer hidden, no new comments). Figma's toggle is Comment/Read; Edit is ODY-810's button, shown beside it.
- **D3. Who sees it.** The droplet is in review and the caller is a reviewer for it: System Admin or Content Editor, and not an author of the droplet (the ODY-810 rule, `isReviewerFor`). Authors never see Comment mode; their view is ODY-807. This needs `lib/review-roles.ts` from ODY-810 (Open Question 1).
- **D4. The review opens on the first Post, not on page load.** Opening a lesson in Comment mode only reads. `getOrOpenReview` then `addComment` run when the first comment is posted, so looking at a lesson never creates an empty review.
- **D5. One new read for the caller's own review.** Add `getMyReview(dropletId)` to `reviews.ts`: the caller's review for the current round, with its comments (paged like `getReviewForDroplet`), or null. Reviewer roles only, plus the non-author check from D3. It is not a change to `getReviewForDroplet`, which ODY-805 and ODY-807 use for other purposes. Coordinate with Jaylen Zeng (ODY-802's author).
- **D6. Anchors, and fitting them to the schema.**
  - `createAnchor` and `resolveAnchor` come from ODY-801.
  - **Fix the schema in this ticket (Task 2).** `reviewAnchorSchema` must accept what `createAnchor` makes. Proposed: `quote`, `prefix` and `suffix` are required when `start` and `end` are set, and absent for a whole-block anchor. `ReviewAnchor` gets the same shape, and a `toReviewAnchor(anchor)` helper narrows `field` to the four review fields. ODY-806 is the first caller, so it owns the fix. Agree it with Jaylen and Brady (Open Question 2).
  - **`point` isn't needed yet.** Anchors saved without it stay valid. ODY-836 adds it as an optional field, with no migration.
  - Classic-editor blocks have no stable ids, so they anchor by `quote` plus context only. The Overview uses `field` plus `quote`.
- **D7. Numbering.** Open comments are numbered 1, 2, 3 in the order written (by `id`), per lesson, and per Overview field group. A new comment always gets the next number. Resolving removes it from the count and the rest close up. Resolved comments keep their place with a ✓ and no number. Computed on the client from the loaded comments.
- **D8. Tags.** A small rectangle in the right margin: the number, then about 24 characters of the quote, or the words around a spot, or "Check-in · …". Where the margin is under about 160 px, or on a phone, only the number shows and the tag opens on hover or focus. Hovering a tag lights its text and the other way round. A tag is a button with an `aria-label` that reads the whole snippet.
- **D9. `lib/selection`** (ODY-785's code, extracted not copied): the 150 ms `selectionchange` debounce, `textNodes`, `offsetOf`, the selection-to-range read with "ignore collapsed and ignore outside the container", popover placement above or below under the header, and the Esc rule. The learner renderer is refactored to import it with no behaviour change, and its tests stay green. This goes first so the two features can't drift.
- **D10. Keyboard.** Opening the comment box from a Shift+arrow selection works through the same `selectionchange` path as learner highlights. The composer is a small dialog: focus moves into it, Esc cancels and returns focus to the selection, Ctrl/Cmd+Enter posts. Each margin tag is reachable by Tab in reading order.
- **D11. Outdated comments.** `resolveAnchor` returning `outdated` means the text changed since the comment. The comment gets no mark and appears in a short "Outdated" list in the strip, still readable and resolvable. Never dropped.
- **D12. Classic blocks need selectable read-only text.** ODY-810 makes Classic blocks read-only with `inert`, and an inert subtree can't be selected. So Comment mode needs the block editors in a real non-editable state (TipTap `editable: false`), which the block components do not take today. Task 7 is a spike to decide between adding an `editable` prop to `generic`, `callout`, `expandable` and the quiz blocks, or rendering Classic blocks in Comment mode with the learner renderer's block components.
- **D13. The Overview** is rendered as read-only text in Comment mode (ODY-810's `FrozenOverview` can be reused), because CKEditor is not a good place to hang marks.

## Acceptance criteria

- [ ] A reviewer can comment on a whole block or on a few words, in a BlockNote lesson, a Classic lesson and the Overview.
- [ ] Opening a lesson never creates a review; the first Post does.
- [ ] A reviewer sees only their own comments in Comment mode, and an author of the droplet never sees Comment mode.
- [ ] The comment box opens from a Shift+arrow selection, and can be completed and cancelled with the keyboard alone.
- [ ] Open comments are numbered in the order written, close up when one is resolved, and a new one gets the next number.
- [ ] A tag shows its number and a few words, collapses to the number where the margin is tight, and opens on hover or focus.
- [ ] Marks in the BlockNote editor are ProseMirror decorations, not hand-made DOM edits, and survive the editor re-rendering.
- [ ] A whole-block comment saves: `addComment` accepts the anchor `createAnchor` makes.
- [ ] A comment whose text was edited away appears in the Outdated list, not silently dropped.
- [ ] Learner highlights behave exactly as before after the `lib/selection` extraction.
- [ ] No new export goes on the PENDING_AUTH allowlist, and `/ci` passes.
