## Checklist results

- **Count = Unread tab.** The count calls the same `fetchAnnouncements(1, roles, { archived: false })` the tab uses. It adds `excludeBroadcasts: true`, which only drops the `authorized_user $null` arm of the system branch, so the viewer's own system rows are still counted. The default roles are `toFeedRoles(FILTER_VALUES)`, the same list in the same order that `parseFilters(null)` gives the page, so `sameRoles(roles, DEFAULT_ROLES)` holds on a default load. Review outcomes are left out because they aren't in `FILTER_VALUES`. Reminders are included. Empty filters give 0, and the tab is empty too. With no filters the streak card still renders, and the badge's +1 matches it. Mismatches remain only with broadcasts (by design) and in the races in N2 and N3.
- **Optimistic ±1.** Unread tab → −1. Read tab, mark unread → +1. Broadcast → 0. A failed action reverts by `-delta`. `mutations.current` drops any recount started before a mutation. Unmounting `FeedClient` hands the value back to `serverCount`. Concurrent clicks each apply their own delta, and only the last recount is applied. I found no double counting.
- **Caching.** The count fetch carries `announcements` and `userFeed(userId)` with `next` only (no `cache`). `revalidateReadState` hits one of those two tags for every type, so the layout count and the recount are fresh after a mark read or mark unread.
- **Auth.** `getUnreadAnnouncementCount`'s allowlist key (`ODY-506`) is unchanged, and the security suite passes. `roles` is untrusted, but `fetchAnnouncements` filters out non-strings, and every branch is still scoped to the session user. `excludeBroadcasts === true` is a strict check and can only narrow results. See N5 for one edge.
- **Streak card.** The localStorage key is still `streak-card-read:{userId}`. Before storage is read, the initial value is `undefined` where it used to be `null`, and both mean "not read", so the first render is the same as before (the card is on the Unread tab until the effect runs). The store is a module singleton, but every hook instance reloads the key in an effect keyed on `userId`. The behaviour is unchanged, and the nav badge now follows the card.
- **Hydration.** On the server, the store is never written (effects only). `FeedLeftNav` falls back to the `unreadCount` prop, and `streakUnread` is false until the effect runs, on both server and client. So there's no mismatch. The documented N → N+1 jump for the streak card is expected (Q5a).
- **Badge.** It's right-aligned (`flex-1` label). Light mode is `#287697` with white `text-xs font-semibold`, rounded-full, a contrast ratio of about 5.1:1. Dark mode is `#4AABCF` on slate-900 text, about 6.8:1. It stays visible on the active row (`#287697/10`). The visible pill is `aria-hidden`, and sr-only text gives "My Feed, N unread" with the exact N, even when the pill shows 99+. It's hidden at 0, and there's no badge on mobile because the nav is `hidden md:block`.

## Findings (most severe first)

### N1. The badge's count is a second full feed query on every Activity page and after every click. Non-blocking (PR 1 / PR 2)

- **Where:** `frontend/lib/requests/feed.ts:911-926` and `frontend/app/(general)/activity/layout.tsx:15-18`. Also `frontend/components/feed/feed-client.tsx:152-174`.
- **Problem:** This is the ODY-929 review's N6, now live. `getUnreadAnnouncementCount` runs the whole `fetchAnnouncements` just to read `pagination.total`. That's 4 ID lookups, a 25-row page with deep populate (playlist → droplets → lessons, users with blocked lists), and `attachReminderData`'s enrollment and due-date queries. Because `excludeBroadcasts` changes the URL, it never shares the page's cache entry, even with default filters. The activity layout runs it for every Activity page: My Feed, Droplets, Playlists, Voyages, Favorited and Archived.
- **Failure scenario:** One "Mark as read" on `/activity` costs three feed-sized Strapi reads: the layout re-renders with a freshly revalidated tag, then `FeedClient`'s silent refetch runs, then the `getUnreadAnnouncementCount(roles)` Server Action. The last one is a cache hit only with default filters. Each pill toggle adds another Server Action round trip, and Next runs Server Actions one at a time per client, so the list refetch waits behind it.
- **Fix:** Use the plan's Q8(b). Extract the filter builder from `fetchAnnouncements` and run a lean count with `fields: ["id"]`, no `populate`, `pageSize: 1`, the same tags, and no `attachReminderData`. That's about 40 lines, which fits PR 1's budget. At minimum, skip `attachReminderData` when only the total is needed.

### N2. A failed recount shows 0 and hides the badge. Non-blocking (PR 1 / PR 2)

- **Where:** `frontend/lib/requests/feed.ts:925` (`return 0` on error) and `frontend/components/feed/feed-client.tsx:165-169`.
- **Problem:** An error and a real zero look the same. The layout's `catch` keeps the page rendering, which is right. But `FeedClient` writes the 0 into `feedCount`, which overwrites a correct optimistic value.
- **Failure scenario:** The learner has 6 unread and marks one read, so the badge shows 5. Strapi then hiccups on the recount, `getUnreadAnnouncementCount` returns 0, and the badge disappears until the next successful recount or until they leave the page. The same thing happens on a cold load if the layout's fetch fails.
- **Fix:** Return `null` (or throw) on error, and leave the store alone in `FeedClient` when the value isn't a number. The layout can map `null` to 0 for its prop.

### N3. Switching to Read before the first recount lands makes ±1 start from the default count. Non-blocking (PR 2)

- **Where:** `frontend/components/feed/feed-client.tsx:153` and `frontend/stores/feed-unread-store.ts:27`.
- **Problem:** The recount only runs on the Unread tab. If you switch tabs while it's in flight, cleanup drops it, and `feedCount` stays `null`. A mark unread on the Read tab then adjusts from `serverCount`, which is the default-filters count, not the current filters' count.
- **Failure scenario:** The learner opens `/activity?filters=kudos` (3 unread kudos, 10 by default) and clicks Read right away. They mark one kudos unread, and the badge shows 11 instead of 4. It's correct again once they return to Unread.
- **Fix:** Keep the recount running on both tabs (the count doesn't depend on `tab`), or leave `feedCount` alone in `adjustFeedCount` when it's `null` and roles aren't the default.

### N4. A stale `serverCount` beats the fresh layout prop for one frame. Non-blocking (PR 2)

- **Where:** `frontend/components/feed/feed-left-nav.tsx:37` and `frontend/components/feed/feed-container.tsx:35`.
- **Problem:** The store is a module singleton that lasts across client navigations. The selector reads `feedCount ?? serverCount ?? unreadCount`, so after leaving Activity and coming back, the first paint shows the previous visit's `serverCount`. The new prop only takes over after `FeedContainer`'s effect.
- **Failure scenario:** The learner leaves with 4 unread, gets 3 new announcements and comes back. The badge flashes 4, then shows 7. A reminder that arrives meanwhile can make it flash from hidden to visible.
- **Fix:** Show `feedCount ?? unreadCount` (the prop is always the layout's latest). Use `serverCount` only as the base in `adjustFeedCount`, or reset it in `FeedContainer`'s effect cleanup.

### N5. The empty-roles short-circuit runs before the string filter. Non-blocking (PR 1)

- **Where:** `frontend/lib/requests/feed.ts:916-917`.
- **Problem:** `types.length === 0` is checked on the raw argument. A crafted `getUnreadAnnouncementCount([4])` passes the check, and then `fetchAnnouncements` filters `[4]` down to `[]` and treats that as "all types". That counts review outcomes, the opposite of the "no types → 0" rule. It only exposes the caller's own data, so this is a correctness edge and not a leak.
- **Fix:** Filter to strings (ideally to `AnnouncementType` values) before the length check.

### N6. The plan said "from each Unread fetch's total", but the code makes a separate Server Action per recount. Non-blocking (PR 2, needs the developer's acknowledgement)

- **Where:** `frontend/components/feed/feed-client.tsx:150-174`.
- **Problem:** The decision says `FeedClient` updates the store from each Unread fetch's total. That total includes broadcasts, which the badge leaves out on purpose, so the implementer added a second Server Action. That's a reasonable consequence of the broadcast decision, but it isn't what was agreed, and it doubles client round trips (see N1). The recount runs on filter and refresh changes, not on page changes, which is correct.
- **Fix:** Either accept the deviation in the PR description, or have `fetchAnnouncements` return `{ ..., badgeTotal }` from the lean count (N1) in the same call, so one fetch updates both the list and the badge.

### N7. Clamping at 0 makes rollback asymmetric. Non-blocking (PR 2)

- **Where:** `frontend/stores/feed-unread-store.ts:27`.
- **Problem:** If the base is already 0 (for example after N2), −1 clamps to 0 and the failure rollback +1 then gives 1.
- **Failure scenario:** After N2 the badge is hidden. The learner marks an item read, the action fails, and the badge shows 1 while the tab has several items. It self-corrects on the following recount.
- **Fix:** Fixing N2 removes the usual trigger. Alternatively, store the unclamped value and clamp only at display (`formatUnreadCount` already hides ≤ 0).

### N8. Gaps in test coverage. Non-blocking (PR 2)

- `feed-client.test.tsx` covers non-default filters, the failure rollback and broadcasts. These paths have no test:
  - the **success** path, where −1 is followed by the recount's value;
  - the Read tab's +1 on mark unread;
  - default filters on mount, which must **not** call `getUnreadAnnouncementCount` and must use `serverCount`;
  - a recount that resolves after a mutation and must be dropped.
- Nothing tests `FeedContainer` seeding `serverCount` from the layout prop.
- The left-nav name regex accepts `"My Feed , 7 unread"` (`/^My Feed ?, 7 unread$/`). It would be stronger to assert the exact name the decision specifies.
