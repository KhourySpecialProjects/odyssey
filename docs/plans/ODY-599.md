## Re-scope (why the ticket is smaller now)

The ticket was written before ODY-633 and ODY-597 landed:

- **Draft & Publish migration: no longer needed.** ODY-633 turned Draft & Publish off on all five types, so v5 keeps one row per document and nothing runs twice for a draft and a published version. ODY-633 also removed `publicationState: "preview"` from the frontend, and no code publishes by setting `publishedAt`. Task 3 re-checks both.
- **"Part 1 on v4 before the upgrade tool": no longer possible.** The tool has already run (ODY-597, merged to `feature/strapi-v5`). The tests run on v5 instead, which is what the acceptance criteria care about: each side effect happens exactly once on v5.

## What the v5 source says (Strapi 5.56.0, checked 2026-10-02)

- **The document service** (`@strapi/core/dist/services/document-service/repository.js`, `entries.js`):
  - With Draft & Publish off, `create` makes one `db.query(uid).create`.
  - `update` makes one `findOne` and then one `db.query(uid).update({ where: { id: entry.id } })`.
  - `delete` makes one `db.query(uid).delete({ where: { id } })` per entry.
  - So each content-type lifecycle (`beforeCreate`/`afterCreate`/`beforeUpdate`/`afterUpdate`) fires once per operation, and `event.params.where.id` is still the numeric id.
- **Unknown data keys** such as `regenerateSlug` survive the entity validator, which uses yup with `strict: false` and doesn't strip unknown keys. They reach `beforeUpdate`, where the hook deletes them.
  - The REST controller rejects them earlier with `400 Invalid key` (ODY-700).
  - Updates through the document service, entity service or admin still pass the key to the hook.
- **`strapi.entityService.findOne(uid, numericId)`** still works in v5. It looks up the row by id, then calls `documents.findOne({ documentId })`. It's deprecated; moving off it is ODY-606.
- **`plugin::content-manager.uid` `generateUIDField({ contentTypeUID, field, data, locale })`** has the same signature in 5.56.0, and `findUniqueUID` uses `documents().findMany`. So `lib/lifecycle-utils.ts` `generateSlug` works unchanged.

The tests below prove all of this against a real v5 instance.

## Task 1: Backend test harness (real Strapi v5 on SQLite)

The backend has no tests today. Follow Strapi v5's testing guide pattern:

- **devDependencies** in `backend/package.json`: `jest`, `supertest`, `better-sqlite3`. Keep `package-lock.json` in sync with `npm install --save-dev` in the worktree.
  - `better-sqlite3` is a native module. If its install fails on the local Node (v25), STOP and report the exact error. Don't switch databases or change Node.
- **Scripts:** `"test": "jest --runInBand"`. Add `--forceExit` only if open handles keep Jest alive after `strapi.destroy()`, and say so in a comment.
- **`backend/jest.config.js`:** `testEnvironment: "node"`, `testMatch: ["<rootDir>/tests/**/*.test.js"]`, ignore `dist/`, `.tmp/`, `node_modules/`, plus a generous `testTimeout` for the boot. JS tests keep the harness simple; the app code is TS that Strapi compiles.
- **`backend/tests/helpers/strapi.js`:** a singleton.
  - `setupStrapi()` runs `compileStrapi()` and `createStrapi(appContext).load()`, then `instance.server.mount()`, both from `@strapi/strapi`.
  - `teardownStrapi()` closes the DB connection and calls `strapi.destroy()`.
  - Set test env before boot, **in code, never in a `.env` file**:
    - `NODE_ENV=test`
    - `DATABASE_CLIENT=sqlite`
    - `DATABASE_FILENAME` → a unique file per run under `.tmp/`, which is gitignored
    - dummy `APP_KEYS`, `API_TOKEN_SALT`, `ADMIN_JWT_SECRET`, `JWT_SECRET`, `TRANSFER_TOKEN_SALT`, `ENCRYPTION_KEY`
    - `SLACK_WEBHOOK_URL=https://hooks.slack.test/odyssey`, so the Slack helper actually sends, and tests can count the sends through a `fetch` spy.
  - Removing this run's own `.tmp` test DB in teardown is fine. Don't delete anything else.
- **`backend/config/env/test/`:**
  - `plugins.ts`: `documentation: { enabled: false }`, so the boot doesn't rewrite the tracked `src/extensions/documentation` and `src/api/*/documentation` files. Also use the local upload provider (`upload: { config: { provider: "local" } }`) so there's no S3.
  - `database.ts` only if the base config doesn't already read the env vars above. It does (`DATABASE_CLIENT` defaults to sqlite, `DATABASE_FILENAME` is read), so it's probably not needed.
- **`backend/tests/helpers/api-token.js`:** create a full-access API token through `strapi.service("admin::api-token").create(...)`, and return its access key so REST tests can send `Authorization: Bearer`.
- **Boot test** (`backend/tests/app.test.js`): Strapi boots, the content types exist, and `GET /api/tags` with the token returns 200.
- **Clean tree:** after `npm test`, `git status` must be clean, with no churn in tracked files. Check `types/generated/*`, `src/extensions/documentation/**` and `src/api/*/documentation/**`.
  - If the boot regenerates tracked files, find the config that stops it, e.g. `autogenerate: false` for typegen, or keep the documentation plugin off.
  - Don't commit regenerated files.

## Task 2: Lifecycle tests (characterize the hooks and prove each side effect happens exactly once)

Slack sends go through `fetch`, so count them with `jest.spyOn(global, "fetch")`, filtered to the webhook URL. Reset between tests. For each test, create fixtures through `strapi.documents(uid)`, with the minimal required fields from each `schema.json`.

**`backend/tests/lifecycles/droplet.test.js`** (`src/api/droplet/content-types/droplet/lifecycles.ts`):
- create → the slug comes from `name`. A second droplet with the same name gets `<slug>-1`.
- update with `regenerateSlug: true` → the slug is regenerated from the new name. With `false`, or without the key → the slug is unchanged. `regenerateSlug` is never stored.
- status `draft` → `edit` → **exactly one** Slack send, with the droplet name in it.
- `edit` → `edit`, or an update that doesn't touch `status` → no send.
- `edit` → `published` → no send.
- REST: `POST /api/droplets` and `PUT /api/droplets/:documentId` with a status change to `edit` → exactly one send.
- REST `PUT` with `regenerateSlug` in the body: currently `400 Invalid key regenerateSlug`. Write it as `test.failing(...)`, asserting the intended 200 and a regenerated slug, with a comment pointing at ODY-700. When ODY-700 lands, the test starts passing and Jest flags it, so it gets flipped.

**`backend/tests/lifecycles/lesson.test.js`:**
- create without `blocks`/`blocksV2` → throws "Lesson must have either blocks or blocksV2 content". Create with `blocksV2` → slug set.
- update to empty content (e.g. `blocksV2: null`, `blocks: []`) when the other field is also empty → throws. Update to empty `blocksV2` while `blocks` still has content → OK.
- Autosave-style update with non-empty content → OK.
- `regenerateSlug` behaves as it does for droplets.

**`backend/tests/lifecycles/playlist.test.js`:** create sets the slug; `regenerateSlug` true or false.

**`backend/tests/lifecycles/creation-request.test.js` and `access-request.test.js`:** create (documents API and REST) → **exactly one** Slack send each, containing the user's name or email. No sends on update or delete.

**Delete:** for each type, deleting through the document service runs no create/update hooks and sends nothing.

Keep the tests readable. Use one `describe` per hook and plain fixtures, and avoid snapshot tests of Slack payloads; assert the few fields that matter.
