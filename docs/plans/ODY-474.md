# ODY-474: Strapi-admin data changes must immediately invalidate the Next.js cache

## Problem

Odyssey has **no invalidation path from the Strapi admin into the Next.js data cache.**

Every cached request function tags its fetch (`next: { tags: [...], revalidate: 900 }`), and every Odyssey Server Action correctly calls `revalidateTag()` after mutating. But `revalidateTag()` can only be called from inside the Next.js process. When a staff member edits data directly in the **Strapi Content Manager**, nothing tells Next.js anything changed — so the page serves stale data until the 900-second TTL expires.

The ticket surfaces this as a groups bug, but the defect is platform-wide. Groups are simply where it was noticed.

### Verified evidence

- `frontend/app/(groups)/g/dashboard/page.tsx:40` → `getCachedUserGroups()` (`frontend/lib/requests/cached.ts:68`) → `getUserGroups()` (`frontend/lib/requests/groups.ts:187`), which fetches with `next: { tags: [CACHE_TAGS.allGroups], revalidate: 900 }` at `groups.ts:232`.
- Dumping the live Next data cache inside the running `frontend` container (`/app/.next/cache/fetch-cache/`) confirmed the persisted entry: `revalidate: 900`, `tags: ["groups"]`.
- `frontend/app/api/` contains only `run-code`, `auth/[...nextauth]`, and `user-activity/[userId]`. **There is no revalidation endpoint anywhere in the app**, and no test anywhere imports from a `route.ts` — this will be the repo's first route-handler test.
- `backend/src/api/group/content-types/group/` has **no** `lifecycles.ts`. The five lifecycle files that do exist (`access-request`, `creation-request`, `droplet`, `lesson`, `playlist`) only do slug generation, one validation, and Slack notifications.
- **Strapi's own webhook subsystem is entirely unconfigured.** `backend/config/server.ts:7-9` sets only `webhooks: { populateRelations: env.bool('WEBHOOKS_POPULATE_RELATIONS', false) }` — a tuning flag, not a webhook definition. There is no `strapi.webhookStore` usage, no webhook seeding, and `backend/database/migrations/` contains only `.gitkeep`.
- **Nothing in the backend has ever called the frontend.** The only outbound `fetch` in all of `backend/src` is the Slack webhook (`backend/src/lib/slack.ts:49`). `FRONTEND_URL` is used solely to build a link _string_, never to make a request.
- Odyssey's own `deleteGroup` (`frontend/lib/requests/groups.ts:1043`) _does_ correctly revalidate `authors`, `allGroups`, `allDueDates`, `userDashboard`. **Deleting through the Odyssey UI already works.** Only Strapi-admin-side edits are invisible.

### Ruled out (do not re-investigate)

- **Relations are correct.** `group.admins` ⟷ `authorized-user.groupAdmin` via `inversedBy`/`mappedBy` (verified in both schemas). The Strapi-side edit persists correctly to the join table.
- **Not multi-instance cache divergence.** `terraform/modules/ecs/main.tf:356,400` both set `desired_count = 1`, and `frontend/next.config.mjs` defines no custom `cacheHandler`.
- **No `cache` + `next` mutual-exclusion violation** in this path. `fetchAPI` (`frontend/lib/utils.ts:70`) even guards against it in dev.
- **The `$or` relation filter is sound** — verified against local Strapi: correct counts, no duplicate-row inflation, correct pagination.
- **No CSS height clipping** on the groups grid.
- **No custom controllers/routes/services** exist for `group` or `authorized-user` — all six files are pure `factories.createCoreController(...)` one-liners. Nothing is intercepting these writes.

### The critical subtlety

The ticket's own reproduction steps edit the relation **from the `authorized-user` side** (Content Manager → Authorized Users → remove entries from `groupAdmin`). Strapi fires lifecycle events on **the model being written**, not on the far side of a relation. So a `group`-only hook would _not_ fire for the exact scenario in the ticket. Any fix must cover `authorized-user` as well.

## Acceptance Criteria

- [ ] Deleting a group in the Strapi Content Manager makes it disappear from `/g/dashboard?tab=admin` on the **next page load** (no 15-minute wait).
- [ ] Removing a group from a user's `groupAdmin` relation in Content Manager → Authorized Users (the ticket's literal repro) also invalidates immediately.
- [ ] Bulk-deleting multiple groups via the admin's multi-select invalidates immediately (`deleteMany`, not just `delete`).
- [ ] Creating and updating a group from the admin invalidate immediately.
- [ ] The mechanism is **declarative and generalizable** — covering a new content type means adding one entry to a map, not writing a new file.
- [ ] If the frontend is down, slow, or the secret is unconfigured, the Strapi write **still succeeds** and behavior degrades to today's 900s TTL. No admin-facing error, no hung save.
- [ ] The endpoint rejects unauthenticated callers (no valid shared secret → 401, no revalidation performed).
- [ ] Works in local dev with Strapi in Docker reaching the frontend.
- [ ] A non-group write to an authorized user (e.g. accepting a friend request, editing a bio) does **not** invalidate group tags — verified by the absence of a revalidation log line.
- [ ] Startup logs state plainly whether revalidation is active or inert, naming any missing env var.

- [ ] `cd frontend && npm test` passes.
- [ ] No hardcoded cache-tag strings — everything references `CACHE_TAGS`.

## Settled Decisions (design review, 2026-09-22)

These were worked through explicitly and supersede any conflicting detail below.

1. **Field-gate `authorized-user`, but never gate deletes.** Emit group tags only when the write actually touches `groupAdmin` / `groupManager` / `groupsCreated` / `groups` / `archived_groups`; always emit on `afterDelete` / `afterDeleteMany`, which carry no `params.data` and are unambiguously group-relevant.
2. **Phase 1 watches `group` + `authorized-user` only.** Prove the mechanism against the reported bug before widening the blast radius.
3. **New `REVALIDATE_SECRET`, merged inert.** Code lands and no-ops until the infra change exists; fail-open means the worst case is exactly today's behavior. **Blocked on a manual infra change — see Manual Steps.**
4. **Public ALB for `FRONTEND_URL`**, not internal service discovery. This fires only on admin content edits, so NAT/TLS cost is noise, and it avoids two unverified terraform assumptions.
5. **Hand-rolled request stub in the route test** — do not touch the global `Request` stub in `jest.setup.ts`.
6. **Boot-time configuration log** so "inert by design" is distinguishable from "broken".
7. **Duplicate revalidation is accepted.** Odyssey's own group Server Actions already call `revalidateTag()` and will now also trigger the subscriber. `revalidateTag` only bumps a timestamp; suppressing the duplicate would mean threading a caller header through every Server Action. Not a bug — do not "fix" it.

### Correction to (1) — field names (2026-09-22, post-review)

The original field list in this decision was wrong and has been fixed above. Verified directly against `backend/src/api/authorized-user/content-types/authorized-user/schema.json`, the `authorized-user` side of every group relation is:

| Field             | Relation   | Inverse on `group` |
| ----------------- | ---------- | ------------------ |
| `groupAdmin`      | manyToMany | `admins`           |
| `groupManager`    | manyToMany | `managers`         |
| `groupsCreated`   | oneToMany  | `creator`          |
| `groups`          | manyToMany | `members`          |
| `archived_groups` | manyToMany | `users_archived`   |

Two errors: **`users_archived` is the `group` side**, not the authorized-user side (the correct name is `archived_groups`), so that entry could never match; and **`groupsCreated` was missing entirely**, even though `getUserGroups` `$or`s on `creator` and therefore feeds the exact dashboard this ticket is about. Both were under-coverage bugs — the gate silently fell back to the 900s TTL for archived and creator relations.

### Consequence of (1) worth knowing

Because the gate suppresses the POST entirely for non-group writes to `authorized-user`, **admin-side edits to profile-only fields (name, bio, roles) will still wait out the 900s TTL.** That is deliberate: the alternative — notifying on every `authorized-user` write — would invalidate the global `users` tag on every friend request, block, and sign-in (`frontend/lib/requests/friends.ts` PUTs to `/api/authorized-users/{id}` at nine call sites), which is the exact thundering-herd problem the gate exists to prevent. Profile-field freshness is a phase-2 concern; if it becomes urgent, the right fix is a per-user tag, not an ungated global one.

**Also worth knowing before smoke-testing:** Strapi v4's Content Manager submits the **whole form** on save, so an admin editing only a bio will still include the group relation fields in `params.data` and will trigger a notify. That is over-invalidation, not staleness — harmless, and strictly better than the ungated alternative. The gate does its real work against the frontend's partial `PUT`s (friend requests, blocks, sign-ins), which are the high-frequency path. Do not read a revalidation log line after a bio edit as the gate being broken.

Accordingly the `authorized-user` tag mapping is **`[allGroups, userDashboard]`** — not the wider set an ungated design would need.

## Design Decisions

### Chosen: one global lifecycle subscriber → one frontend revalidation endpoint

Registered once in `backend/src/index.ts` via `strapi.db.lifecycles.subscribe()`, driven by a declarative allow-list. Strapi POSTs `{ model, event, id }` to `POST /api/revalidate` on the frontend, guarded by a shared secret. The frontend maps `model` → `CACHE_TAGS[]` and calls `revalidateTag()` for each.

**Alternatives considered:**

| Approach                                                     | Why not                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Per-content-type `lifecycles.ts` files**                   | Works, and matches existing repo structure (five such files already exist, auto-discovered by convention) — but needs a new file per content type each duplicating the same POST logic. Violates DRY. **Retained as the Task 6 fallback** if `db.lifecycles.subscribe` proves unreliable in v4.22.                                                                                                                                              |
| **Strapi admin-configurable webhooks** (Settings → Webhooks) | Zero code, but the configuration lives **in the database, not in git**. It must be hand-recreated in local/dev/prod, is invisible to code review, and silently disappears on a DB restore. The repo has no migration or seed infrastructure to provision it either (`backend/database/migrations/` is empty, `backend/package.json` has only `dev`/`start`/`build`/`strapi` scripts). Unacceptable for a correctness-critical mechanism.        |
| **Lower the `revalidate` TTL** (e.g. 900 → 10)               | _This is the "minimal option"._ One-line change, no new infra, no secret. Rejected because: it doesn't deliver "immediate" (still up to 10s stale); it puts a Strapi round-trip on nearly every dashboard load, which regresses page performance for all users to serve a rare admin action; and it doesn't generalize — we'd repeat the tradeoff for every content type. Worth revisiting **only** if the webhook mechanism proves unreliable. |

### Why the tag map lives on the frontend, not the backend

The backend sends only `{ model, event, id }` — it knows nothing about cache tags. `CACHE_TAGS` is frontend-owned vocabulary (`frontend/lib/cache-tags.ts`), and `.claude/rules/cache-tags.md` requires tags to always come from that file's constants. Putting the map in the backend would fork the taxonomy across two deployables that version independently. The backend stays dumb; the frontend owns the mapping.

### Why the mapping is a pure module, separate from the route

`frontend/lib/revalidation-map.ts` exports a pure `getTagsForModel(model)` function. This keeps the interesting logic trivially unit-testable — which matters a lot here, because **the repo's Jest setup is actively hostile to route-handler tests** (see the Task 3 context). The route handler stays a thin shell around a well-tested pure function.

### Failure posture: fail-open on the backend, fail-closed on the frontend

- **Backend:** if `REVALIDATE_SECRET` or `FRONTEND_URL` is unset, the notifier is a silent no-op. If the POST fails or times out (5s), log a warning and move on. **The Strapi write must never fail or hang because the frontend is unreachable.** Degrades to today's 900s TTL — i.e. exactly current behavior, never worse.
- **Frontend:** if the incoming secret is missing or wrong → `401`, no revalidation. If `REVALIDATE_SECRET` is unset server-side → `503` and an error log (refuse to run an unguarded revalidation endpoint).

This mirrors `backend/src/lib/slack.ts` almost exactly, which is the established prior art for "Strapi calls out over the network without risking the request."

The endpoint **must do its own auth**: `frontend/middleware.ts` has `matcher: ["/admin", "/admin/:path*", "/d/:path*", "/activity", "/activity/:path*"]` — it does **not** cover `/api`, so anything under `/api` is publicly reachable by default.

### Prior art this builds on (read these first)

- **`backend/src/lib/slack.ts`** — the template for the new notifier: env-gated no-op, `AbortController` 5s timeout, `strapi.log.warn` on failure, swallows all errors, called fire-and-forget (not awaited) from lifecycles. It is the **only** outbound HTTP call in the entire backend and uses global `fetch` (Node 18+); there is no `axios` or `node-fetch` dependency. Copy its shape. **One deliberate difference:** `slack.ts:37` early-returns when `NODE_ENV !== 'production'`. The revalidation notifier must **not** do that — local dev needs it.
- **`backend/src/api/droplet/content-types/droplet/lifecycles.ts:52`** — already reads `process.env.FRONTEND_URL` and fires `sendSlackNotification` fire-and-forget from `afterUpdate`. Proves the pattern works in a lifecycle.
- **`frontend/app/api/user-activity/[userId]/route.ts`** — the route-handler convention: `NextRequest`/`NextResponse`, `NextResponse.json({ error }, { status })`, try/catch with `console.error`.
- **`frontend/app/api/run-code/route.ts`** — the POST-handler convention: env read at module scope with `?? ""`, `await request.json()` inside try/catch → `400 { error: "Invalid JSON" }`, manual `typeof` validation, `Cache-Control: no-store` on the response.

### Backend file conventions (easy to get wrong)

- Lifecycle files use a **hybrid module style**: ES `import` at the top, but `module.exports = { ... }` for the export — **not** `export default`. All five existing files follow this. `backend/src/lib/*.ts` modules use normal `export function`.
- `strapi` is an **ambient global** in backend code — `slack.ts` calls `strapi.log.warn(...)` with no import. Do the same.
- `backend/config/*` files are **`.ts`, not `.js`** (`api.ts`, `server.ts`, `admin.ts`, ...), using `export default ({ env }) => ({ ... })` when they need env access.

### Frontend route-handler conventions

**No route handler in this repo exports `runtime`, `dynamic`, `revalidate`, or `fetchCache`** — those exports appear only on pages. Cache behavior on API routes is expressed with a `Cache-Control` response header instead. Follow that: **do not** add `export const dynamic`. A `POST` handler is never statically optimized anyway.

### `FRONTEND_URL` is currently referenced but declared nowhere

`FRONTEND_URL` appears **only** at `backend/src/api/droplet/content-types/droplet/lifecycles.ts:52`. It is absent from `backend/.env.example`, from `backend/.docker.env.example`, from `docker-compose.yml`, and from the terraform backend secrets list (`terraform/modules/ecs/main.tf:257-335`, which also notably lacks `SLACK_WEBHOOK_URL`). So it is `undefined` in every environment today, and the Slack `reviewUrl` renders as a literal `*<null|Name>*` — a pre-existing latent bug. This plan depends on `FRONTEND_URL`, so setting it fixes that too.

### Bulk operations need the `*Many` events

Strapi v4's admin multi-select delete calls `deleteMany`, which fires **`afterDeleteMany`, not per-entry `afterDelete`**. Same for `createMany`/`updateMany`. Subscribing only to the singular events would produce a fix that works for single deletes and silently fails for bulk ones — the most likely way this ships broken. Subscribe to all six.

### Extension path (do not build now)

To cover a new content type later: add one entry to `MODEL_TAG_MAP` in `frontend/lib/revalidation-map.ts` and one string to `WATCHED_MODELS` in the backend subscriber. If per-user tags are ever needed, the payload already carries `id`, so the map value can widen from `string[]` to `string[] | ((id: number) => string[])` without touching the backend.

## Post-Audit Changes (2026-09-22)

A full-branch audit ran after both defects landed. No critical findings; verdict was approve-with-conditions. Three items were fixed:

### W1 — user deletion invalidated only half the tags it should

`MODEL_TAG_MAP` mapped `authorized-user` to `[allGroups, userDashboard]`, justified by "the backend only notifies for group-relevant writes." **That rationale holds for create/update but not for deletes**, which Settled Decision 1 deliberately exempts from the gate. Deleting a user in the Strapi admin therefore never cleared `users` / `authors`, while Odyssey's own `deleteAuthorizedUser` does — so a deleted user kept appearing in `fetchWebsiteCreators` / `fetchContentEditors`, and those are tagged `revalidate: 3600`, making the stale window **an hour**, not 900s.

Fixed by making the map event-aware. Entries are now `{ always, onDelete? }`; `getTagsForModel(model, event)` widens the set only for `afterDelete` / `afterDeleteMany`. The route passes the `event` the backend already sends. An absent or non-string event is treated as a non-delete — never over-invalidates.

This was a design error in Settled Decision 1: the tag mapping was scoped around the gated case while the same decision exempted deletes from the gate.

### L4 — unauthenticated callers could flood the logs

The `REVALIDATE_SECRET`-unset branch runs before any auth check, and `/api` is not matched by `middleware.ts`, so anyone could `curl` the endpoint in a loop and emit an error line per request. Now `console.warn` **once per process**, with the flag reset if the secret later appears.

The plan's justification for skipping rate limiting ("this endpoint is secret-guarded") did not cover this branch — a gap in the spec's reasoning, not the implementation.

**Deliberately not changed:** 503-vs-401 still lets a prober fingerprint whether the secret is configured. Making them indistinguishable would contradict Task 2's spec and harm debuggability; the leak is config state only, never the secret.

### The field gate is now unit tested

`touchesGroupRelations`, `isGated`, and `GROUP_RELEVANT_FIELDS` moved from `backend/src/index.ts` into `backend/src/lib/group-relations.ts` — pure, no imports, no `strapi` global. Tested from the frontend harness at `frontend/testing/backend/group-relations.test.ts` (23 tests), so **no backend test framework was added**, honoring the Test Strategy constraint. Move the file if a backend harness ever appears.

Coverage: both `params.data` shapes, the `createMany` array regression specifically, all four absent-data delete shapes, and a guard asserting the authorized-user side of every relation — including an explicit `not.toContain("users_archived")`.

Also hardened while extracting: entries are checked with `typeof entry === 'object'` before `field in entry`. `field in <primitive>` throws, and a throw inside an awaited `after*Many` handler would propagate into the Strapi write, breaking the fail-open guarantee.

### Still open from the audit

- **W2 — needs a decision, not a fix.** `getCachedUserGroups` has two callers. The dashboard got `PaginatedGroupsGrid` (12/page); `components/dashboard/my-content.tsx:38` got nothing, and `user-groups.tsx:36` renders the list with no slice. That list was capped at 25 by the old hardcoded `pageSize` and is now **unbounded** — a user in 80 groups renders 80 `GroupCard` client components. Arguably the intended fix, but the two consumers of the same data now behave inconsistently.
- **L3 — `maxPages` guard.** Task 9 specifies one; neither loop has it. Break conditions are correct for every shape `fetchAPI` actually returns, and `pageSize: 100` is under Strapi's `maxLimit: 1000`, so no silent clamping. Only a malformed non-array response could spin forever. Either implement it in both loops or strike it from Task 9 — do not leave the spec contradicted.
- **`"use server"` authorization sweep — filed as ODY-482.** `getUserGroups` / `getManagedGroups` are Server Actions with no caller check, accepting an arbitrary `authorizedUserId` and returning that user's groups including member emails. Pre-existing, not caused by this work. Same class as ODY-481.

### Test status

311/312 suites, 4516/4518 tests pass. The only failures are the two in `admin-stats-authorization.test.ts` (**ODY-481**, unrelated and pre-existing on this branch).
