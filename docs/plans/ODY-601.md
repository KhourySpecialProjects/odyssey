# ODY-601: Use documentId in Strapi URL calls and relation writes

Linear: ODY-601 (parent ODY-28). Branch: `improvement/ody-601-use-documentid-in-strapi-url-calls-and-relation-writes`, cut from `feature/strapi-v5` at `cdf39c89`. PR target: `feature/strapi-v5` (not `develop`). This branch is v5-only.

## What was confirmed first (the ticket asked for this)

Checked against the Strapi 5.56.0 source (`@strapi/core`, the version on `feature/strapi-v5`):

- **Single-entry REST routes need a `documentId`.** `core-api/controller/collection-type.js` passes `ctx.params.id` to `service.findOne/update/delete(documentId)`, which calls `strapi.documents(uid).findOne({ documentId })`. A numeric id is treated as a documentId string, matches nothing, and returns 404. The `Strapi-Response-Format: v4` header (ODY-607) does not change this.
- **v4-format responses include `documentId`.** `core-api/controller/transform.js` returns `{ id, documentId, attributes }`. `flattenAttributes` copies non-`attributes` keys, so flattened objects have `documentId` at the top level. v5 always returns `documentId`, even with a `fields` list.
- **Relation writes:** the v5 source still passes `{ id: N }` and numeric shorthand through as raw row ids (`document-service/transform/relations/utils/map-relation.js`, `transform/data-ids.js`). The docs (docs.strapi.io/cms/api/rest/relations) document only `documentId` (shorthand string or `{ documentId }`). Numeric relation ids are undocumented, so this ticket converts them, as the AC asks.
- **Custom lesson lock routes** (`/lessons/:id/lock`, `/lock/heartbeat`, `/lock-status`, in `backend/src/api/lesson/controllers/custom-lesson.ts`) look the lesson up with `db.query(...).findOne({ where: { id } })`, so they take the **numeric** id. Leave `frontend/lib/requests/lesson-lock.ts` unchanged (moving them is ODY-606).
- Filters on `id` (`filters[id][$eq]=5`, `filters[droplet][id][$eq]=5`) still work on v5. They are not in scope.

## Approach

Callers keep passing what they have today (numeric ids from fetched data, the session, FormData, stored integer columns like `originalDropletId`/`originalLessonId`, and JSON like group due dates). One server-side helper turns a ref into a `documentId`:

- If the caller already has the entity with its `documentId`, use it directly (no lookup).
- Otherwise resolve the numeric id with a filtered list query, which is cached in memory. The id → documentId mapping never changes for the life of a row: with Draft & Publish off (ODY-633) there is one row per document, and a re-created entry gets a new numeric id.

So page URLs and bookmarks that contain numeric ids keep working (AC 3), and Server Action signatures do not change. Threading `documentId` through every component and action is out of scope.

## Task 1: The helper (`frontend/lib/strapi-document-id.ts`)

A plain server module. **No `"use server"` directive**, because that would turn every export into a public Server Action endpoint. Don't import it from `"use client"` files.

```ts
export type StrapiCollection =
  | "access-requests" | "announcements" | "authorized-users" | "authorized-user-roles"
  | "creation-requests" | "datasets" | "droplets" | "droplet-lessons" | "due-dates"
  | "enrollments" | "friendships" | "galleries" | "groups" | "highlights" | "lessons"
  | "notes" | "playlists" | "reports" | "tags" | "voyages" | "voyage-enrollments"
  | "voyage-nodes" | "voyage-node-completions";

/** A numeric id, a documentId string, or an object carrying either. */
export type EntryRef =
  | number
  | string
  | { id?: number | string | null; documentId?: string | null };

export class StrapiEntryNotFoundError extends Error {}

export async function resolveDocumentId(collection: StrapiCollection, ref: EntryRef): Promise<string>;
export async function resolveDocumentIds(collection: StrapiCollection, refs: EntryRef[]): Promise<string[]>;
export async function strapiEntryUrl(collection: StrapiCollection, ref: EntryRef, query?: string): Promise<string>;
/** Tests only. */
export function clearDocumentIdCache(): void;
```

Rules:

- **Ref handling:**
  - An object with a truthy `documentId` → return it.
  - A string that is not all digits → it is already a documentId.
  - A number, or an all-digit string → look it up.
  - An object with only an `id` → look up that id.
  - `null`, `undefined`, `NaN`, or an empty string → throw `TypeError`.
- **Lookup:** `fetchAPI(\`/${collection}\`, { urlParams: { filters: { id: { $eq: id } }, fields: ["documentId"], pagination: { pageSize: 1 } }, cache: "no-store" })`.
  - Use `cache: "no-store"` because this runs inside Server Actions, and `fetchAPI` forbids passing `cache` and `next` together. Our own Map is the cache.
  - No match → throw `StrapiEntryNotFoundError` (message includes the collection and id).
- **Batch (`resolveDocumentIds`):**
  - Dedupe, then use refs that already carry a documentId as they are.
  - Look up the rest with `filters: { id: { $in: [...] } }`, `fields: ["documentId", "id"]`, `pagination: { pageSize: 100 }`, in chunks of 100.
  - Return results in input order. Throw `StrapiEntryNotFoundError` naming every missing id.
- **Cache:** a module-level `Map<string, string>` keyed `${collection}:${id}`, capped at 5,000 entries (drop the oldest on insert). Also keep a `Map` of in-flight promises, so concurrent lookups for the same key share one request. Never cache failures.
- **URL:** `strapiEntryUrl` returns `` `${process.env.NEXT_PUBLIC_STRAPI_API_URL}/api/${collection}/${documentId}` ``, plus `?${query}` when `query` is non-empty. That is the same base every call site uses today.

Tests (`frontend/testing/lib/strapi-document-id.test.ts`, TDD). Mock `@/lib/utils`'s `fetchAPI`:

- A documentId string or an object with a documentId → no fetch.
- Number and all-digit string → one fetch with the exact query above. A second call is served from cache. Concurrent calls share one fetch.
- Not found → `StrapiEntryNotFoundError`, and the next call retries (failures aren't cached).
- Bad refs → `TypeError`.
- Batch: mixed refs, dedupe, order kept, chunking at 100, and one missing id → an error naming it.
- `strapiEntryUrl` with and without a query.

**Global Jest mock:** in `frontend/jest.setup.ts`, mock `@/lib/strapi-document-id` so that existing URL assertions (`/api/droplets/5`) keep passing:

- `resolveDocumentId` returns the documentId if the ref has one, otherwise `String(id)`.
- `resolveDocumentIds` maps the same way.
- `strapiEntryUrl` builds the URL from that.
- Keep the real `StrapiEntryNotFoundError` class (`jest.requireActual`).

The helper's own test calls `jest.unmock("@/lib/strapi-document-id")` (or `jest.requireActual`). Tests that need to prove a documentId is used can override the mock with a non-identity mapping, e.g. `5 → "doc5"`.

Types: in `frontend/types/index.d.ts`, add `documentId?: string` to every Strapi entity type that has an `id: number` (optional, because mocks and v4-era fixtures don't have it).

## Task 2: Convert URL calls and relation writes (3 groups, can run in parallel)

### Common rules for every group

- **Single-entry URLs:** replace every `` `${…_URL}/api/<collection>/${id}` `` or `… + "/api/<collection>/" + id` with `await strapiEntryUrl("<collection>", ref, query)`.
  - Pass the entity object when the function already has it, e.g. `strapiEntryUrl("droplets", droplet)`. That uses its `documentId` with no lookup.
  - Keep any query string (`?populate=roles` → third argument).
- **GET by id:** when the call is a plain read, prefer switching it to the list endpoint with `filters: { id: { $eq: id } }` and taking `[0]`. This needs no lookup, and returns `null` (or whatever the function returned for a 404 before) when empty.
  - Only do this when the response shape and error path stay the same for callers. Otherwise use `strapiEntryUrl`.
- **Reads during rendering:** don't use the helper in code that runs while a page renders and may be static or cached. That means Server Components, `unstable_cache` wrappers, and anything called from `lib/requests/cached.ts`. Use the id filter there.
  - The reason: the helper's `cache: "no-store"` fetch would make a static or ISR route dynamic, and can't run inside `unstable_cache`.
  - Server Actions, and code that already reads the session or cookies, can use the helper.
- **Relation writes:** every relation value sent in a POST/PUT body must be a documentId:
  - explicit `connect`, `disconnect` and `set`
  - shorthand, like `droplet: dropletId`, `authorized_user: userId`, `tags: [1, 2]`

  How:
  - Use `entity.documentId` when the entity is in hand: tags, authors and prerequisites copied from a fetched droplet, and so on.
  - Otherwise use `await resolveDocumentIds("<target collection>", ids)`, or `resolveDocumentId` for a single id. The target collection is the relation's `target` in `backend/src/api/<type>/content-types/<type>/schema.json`.
  - `{ id }` objects in `connect` become documentId strings.
- **Finding the implicit relation writes:** for each write in your files, compare the body's keys with the content type's schema. Any key whose attribute is `"type": "relation"` is a relation write. Components and dynamic zones are not relations; leave component `id`s alone.
- **Not found:** if the helper throws `StrapiEntryNotFoundError`, the call site must behave as it did for a 404 from Strapi:
  - the same `{ ok: false }` / `{ error }` return, or `notFound()`, or a thrown error
  - the same log
  - Server Actions must not start throwing where they used to return an error object.
- **Not Strapi, so leave alone:**
  - `lib/requests/posthog.ts`
  - `lib/requests/user-activity.ts` (PostHog)
  - `components/admin/users/*` calling `/api/user-activity/...` (a Next route)
  - `app/api/run-code`, `lib/code-execution.ts`
  - `lib/requests/lesson-lock.ts`: numeric on purpose, see above.
- **Not a collection:** `lib/requests/lesson.ts:116` calls `/api/authorized-user-activities/${activityId}`, which isn't a Strapi collection. Leave it unchanged and mention it in your report.
- **Tests:** update the tests for the functions you change.
  - Assertions on fetch URLs mostly keep passing thanks to the global identity mock.
  - For each converted relation write, add or adjust one assertion with a non-identity override (e.g. `5 → "doc5"`) proving the body sends documentIds.
  - For each function that now passes an entity object, add one assertion that no lookup happened.
- **Scope limits:** don't change Server Action signatures, auth guards, cache tags, or the `PENDING_AUTH` allowlist.
