# ODY-939 PR A: security review

Branch `origin/claude/ody-939-quiz-attempts` @ `dddd987d`, base `origin/develop`. Plan: `claude/ody-939-plan:docs/plans/ODY-939.md`, all recommendations accepted. Review only: nothing on the branch was changed.

## Verdict: ship

Nothing blocking. The auth model holds: the user id comes only from the session, the browser can't name another user, there is no REST read or write path, and no answer text is stored, logged or sent. N1 is worth fixing before merge because it can break the quiz UI, which goes against the plan's "never blocks or throws" rule. The rest can land in a follow-up.

## What I checked and found sound

- **Server action** (`frontend/lib/requests/quiz-attempt.ts`): `requireRole([])` is the first statement (`:33`). It exports one function and no constants or types. The strict Zod schema (`lib/validations/quiz-attempt.ts:6-16`) rejects `userId` and any other extra key. The POST body is `{ ...parsed, userId: gate.user.id }` (`:59`), so a client value can't override the session id. The auth-guard test passes with no allowlist entry. The request sends `STRAPI_RESPONSE_FORMAT_HEADER` and uses `cache: "no-store"`, with no `next`.
- **Route**: only `POST /quiz-attempts/record` exists, with no core router. The test confirms core POST/GET/PUT/DELETE return 404/405. It requires a token (unauthenticated requests get 401/403). `parseBody` is strict and checks each id against `isRowId`. `questionId` is limited to 1..2^31 on both sides and stored as a `biginteger`. User, lesson and droplet must exist (404) and the user must be enrolled (403). The dedupe check runs before the cap, so a retry never gets a 429. `submitId` is `private` and never in the response (`{ id, attempt }` only). The code uses the Document Service only, and `no-entity-service` passes.
- **Data minimisation**: the schema has no text field (a test pins the attribute list). The PostHog calls are untouched. Logs hold only the Strapi URL plus a status or error object, and the browser warning holds only an error code.
- **Plan conformance**: Q1 stores `quizType` + `questionId`, and attempts are numbered per type, so Classic id collisions are kept apart. Q6: `lessonAccess` is used without `access.mentor`, so hidden or `edit` droplets still record. The ODY-888/890 `onSubmit` code (`hinted`, `mentor_hint_next_try`) is unchanged; the new call sits after it and before `setShowResult`. Open-ended attempts are skipped when `lessonId`, `dropletId` or `userId` is missing, so the presentation renderer (no `userId`) never writes. The daily cap uses `dayBounds`, which starts the day at Boston midnight, the same as the other caps.
- **Enumeration across users**: the action always sends the caller's own id, so a 403 or 404 tells a student only about themselves.

None.

## Non-blocking

**N1 (Important): a synchronous throw in `fireQuizAttempt` breaks the quiz.** `frontend/lib/quiz-attempt-client.ts:16`
`crypto.randomUUID()` runs synchronously, outside the promise chain that `.catch` protects. Where it doesn't exist it throws a `TypeError` inside `onSubmit` / `checkAnswer`, before `setShowResult(true)`. That happens on non-secure origins (plain-http dev on a LAN IP, some preview hosts) and in browsers older than Safari 15.4 or Chrome 92. The student then never sees a result. I confirmed this by making that call throw locally (the change was reverted afterwards): the component suite fails, including "still shows the result". Smallest fix: wrap the body of `fireQuizAttempt` in `try { … } catch (e) { console.warn(e) }`, or move both call sites after `setShowResult(true)`. Add a test that stubs `crypto.randomUUID` to throw.

**N2 (Nit): the action's error codes reveal droplet contents to students who aren't enrolled.** `frontend/lib/requests/quiz-attempt.ts:40-47`
`getMentorSource` loads any droplet by id, including `edit` and hidden ones, and the action answers before the enrollment check. A signed-in student can call it for any droplet and read the result. `not_found` means the lesson isn't in that droplet. `invalid` means the lesson is there but the question isn't. `not_enrolled` means both exist. That reveals which lessons belong to which droplet and which question ids exist, even for unpublished droplets. Only ids leak, never content. `saveMentorFeedback` uses the same order. Smallest fix: return one code to the client (for example `not_saved`) for `not_found`, `invalid` and `not_enrolled`, and keep the detail in the server log.

**N3 (Nit, Pre-existing pattern): heavy Strapi reads run before any limit applies.** `frontend/lib/requests/quiz-attempt.ts:40`
Every call with a new `(dropletId, lessonId)` pair misses the cache and runs a deep-populated `/droplets` query, and each pair adds a cache entry. The 500-a-day cap only runs in the backend after the enrollment check, so made-up pairs never reach it. `saveMentorFeedback` has the same shape. Smallest fix: none needed for this PR. If abuse shows up, add a per-user limit in the action, or check enrollment before `getMentorSource`.

**N4 (Nit): count-then-create isn't atomic.** `backend/src/lib/quiz-attempt.ts:57-89`
Parallel requests can each pass the dedupe check (two rows with the same `submitId`), each read 499 under the cap (overshooting 500 by the number of parallel requests), and share an attempt number. The plan accepts duplicate attempt numbers. The cap overshoot is limited by how many requests can run at once. Smallest fix: none now. If it matters later, add a unique index on `(user, submitId)` in a migration.

**N5 (Nit): the backend doesn't check that the lesson belongs to the droplet.** `backend/src/lib/quiz-attempt.ts:46-54`
It checks that the lesson and the droplet each exist, and that the user is enrolled in the droplet, but never that the lesson is in that droplet. Only the Next action enforces that. The route needs the token, so this is defence in depth only. Smallest fix: look up the droplet with `filters: { id: dropletId, lessons: { id: lessonId } }` and return 404 when there's no match.

**N6 (Nit, Pre-existing pattern): the route has no explicit `config`.** `backend/src/api/quiz-attempt/routes/custom-quiz-attempt.ts:4-8`
It relies on Strapi's default auth. If someone grants `custom-quiz-attempt.record` to a users-permissions role (Public or Authenticated) in the admin, anyone holding that role can write rows for any `userId`. `custom-mentor-feedback` is the same. Smallest fix: none in this PR. Consider a shared route policy that accepts only API tokens.

**N7 (Nit): archived enrollments still count as enrolled.** `backend/src/lib/quiz-attempt.ts:51-53`
The enrollment count ignores `isArchived`. That is probably right, since an archived student can still open the lesson, but no test or doc says so. Smallest fix: one comment line, or `isArchived: false` if archived students shouldn't feed Mentor.

**N8 (Nit): questions with id 0 are silently dropped.** `frontend/lib/validations/quiz-attempt.ts:5`, `backend/src/api/quiz-attempt/controllers/custom-quiz-attempt.ts:14`
A BlockNote quiz block with no `id` gets `blockIndex` as its id (`convert-blocks.ts:328`), so a quiz in the first block gets id 0. A 32-bit hash can also come out as 0. `.positive()` and `q < 1` reject 0, so those submits are never saved. This is rare and does no harm. Smallest fix: allow 0 (`nonnegative()` and `q < 0`), or record it as a known gap.

**N9 (Nit): test gaps.**

- `frontend/tests/components/droplets/quiz-attempt-submit.test.tsx:99`: `findByText(/Right/)` also matches the option label "Right". Assert on the result badge instead (`getByRole("status")` with "That's Right!") so the test proves the result rendered.
- No test for a throwing `crypto.randomUUID` (N1).
- No backend test that yesterday's rows (before Boston midnight) don't count toward the cap.
- No action test that a hidden or `edit` droplet still records (Q6). The `source()` fixture is always published and visible.
- No action test that an unauthenticated call never runs `getMentorSource`. `describeServerActionAuth` only checks `fetchMock`.
