# ODY-928: Nudges: know each enrollment's last progress

Parent: ODY-927 (Nudges). Siblings planned in parallel: ODY-929 (reminder feed item), ODY-930 (My Feed unread count). Reads this ticket's data later: ODY-931. Out of scope: ODY-931, ODY-932, ODY-933.

## Problem

Reminders (ODY-931) need to know when a learner last made progress on each droplet. Nothing records that today:

- `viewedLessons` is a plain manyToMany relation with no timestamp (`backend/src/api/enrollment/content-types/enrollment/schema.json`).
- `enrollment.updatedAt` moves on every PUT: rating (`changeEnrollmentRating`, `frontend/lib/requests/enrollment.ts`), archive (`archiveDroplet`, `frontend/lib/requests/droplet.ts:566`), `isFirstTime` (`updateEnrollmentFirstTime`, `frontend/lib/requests/enrollment.ts:449`), and the completion write.
- Streak days (`backend/src/api/streak-day/content-types/streak-day/schema.json`) are one row per learner per local date, with a JSON `lessonIds` list and no enrollment or droplet.

"Progress" means viewing a lesson for the first time. Viewing it again doesn't count.

## Premises checked against develop

Confirmed:
- `updateViewedLessons` does the `connect` PUT and then calls `recordStreakDay` only when `!alreadyViewed`. A re-view writes nothing (`enrollment.ts:685-718`).
- The only callers are in `components/droplets/footer.tsx:65` and `:122`.
- `viewedLessons` has no timestamps, and `updatedAt` moves on rating, archive and `isFirstTime` (see Problem).

Contradicted or incomplete:
1. **There's almost no streak history to derive from or backfill from.** ODY-918 landed on develop on 2026-11-12 (`c774672`), the day this plan was written. `production` is still Strapi v4 (CLAUDE.md, ODY-603) and has no `streak-day` table at all. So the "derive it from streak days" option has close to zero history on dev and none on prod. It isn't only "nothing from before streaks shipped".
2. **A streak day's `lessonIds` can't be tied to one droplet.** `lesson.droplets` is manyToMany (`backend/src/api/lesson/content-types/lesson/schema.json:48`), so a lesson id in a streak row can belong to several droplets. A streak row also doesn't record which enrollment it came from. Deriving per-enrollment progress from it would credit every droplet that shares the lesson.
3. **`updateViewedLessons` isn't the only code that writes `viewedLessons`.** `markLessonAsComplete` (`frontend/lib/requests/lesson.ts:122`) rewrites the whole list with a PUT. It's an exported server action, so it's a live endpoint, but nothing in `app/`, `components/` or `lib/` calls it (only a comment in `lib/cache-tags.ts:31`). `createEnrollment` and `createEnrollmentFromEmail` accept starting `viewedLessons`, but both UI callers pass `[]` (`components/droplets/enroll-button.tsx:69`, `components/first-time/first-visit-popup.tsx:83`). See Q7.
4. **"A re-view writes nothing" doesn't fully hold under overlapping calls.** Two quick calls for the same unviewed lesson (for example, Next clicked twice) both see `alreadyViewed = false`, so both run the new-view block (`enrollment.ts:685`). With this change the timestamp would be written twice, a few ms apart. That's harmless, but a test can't claim exactly one write per first view under concurrency.
5. **Order matters at deploy.** Strapi rejects unknown body keys with 400 "Invalid key" (CLAUDE.md, strict REST). If the frontend sends the new field before the backend schema has it in that environment, the `connect` PUT fails, and with it every first lesson view. So PR 2 can't reach an environment before PR 1. The same applies to `production`, which only gets either PR when develop is promoted with the v5 cutover (ODY-603).

## Design Questions (open: Jaylen decides)

**Q1. Where does "last progress" live?** Tasks 1, 2, 4 and 5 depend on this.
- **A. A datetime field on `enrollment`** (recommended). One indexed-row read per enrollment. ODY-931 can filter on it in a single Strapi query (for example `lastProgressAt < now - N days`). Costs a schema change, the schema checklist and a backfill.
- **B. Work it out from `streak-day` rows.** No schema change. But there's essentially no history (premise 1), a lesson can't be tied to one droplet (premise 2), and ODY-931 would have to pull every streak day for a learner and match JSON `lessonIds` against each droplet's lessons. That isn't filterable in Strapi.
- **C. A new `lesson-view` collection** (enrollment, lesson, viewedAt), one row per first view. Gives full history and per-lesson times, and "last progress" becomes a max() query. It's the most code (new content type, routes, a second write per view), and Strapi REST has no aggregate, so ODY-931 still has to fetch rows.

**Q2. Where is the timestamp set?** Task 2 depends on this.
- **A. Next.js sends it in the same `connect` PUT** (`enrollment.ts:697`), as `new Date()`. One write that's atomic with the connect, and it matches how `completionDate` is written today. It misses any other writer of `viewedLessons` (premise 3, and the Strapi admin panel).
- **B. A Strapi `beforeUpdate` lifecycle** sets it whenever `viewedLessons.connect` (or `set`) adds a lesson. It catches every writer. But telling "added a new lesson" apart from a `set` that only reorders or removes lessons needs a read inside the lifecycle, and lifecycles on relation changes are fiddly in v5.

**Q3. Which mechanism gives existing enrollments a starting value?** Task 3 depends on this.
- **A. An idempotent boot backfill** in `backend/src/index.ts`, like `review-round-backfill.ts`. It runs on every deploy (dev now, prod at promotion) with no manual step, and the tests follow the existing pattern. It reruns on every boot, so it has to be able to tell "not backfilled yet" apart from a value that's null on purpose (see Q4: if null is meant to stay null, it needs a marker, or it should only touch rows created before a cutoff date).
- **B. A Strapi `database/migrations` file** (the folder `backend/database/migrations/` exists and is empty). Strapi runs it once and records that it ran. Raw knex, so it needs the real table and column names (`enrollments`, `enrollments_viewed_lessons_lnk`; see `docs/agent/learnings/2026-10-06-strapi-v5-join-table-renames.md`). There's no precedent in the repo and it's harder to unit test.
- **C. A one-off SQL script added to the prod migration-day playbook** and run by hand on dev now and on prod at release. Simplest code, but it's a manual step that can be forgotten, and it has to run after the column exists.

**Q4. What starting value do existing enrollments get?** Task 3 depends on this, and so does ODY-931's behaviour on the first day after release.
- **A. `updatedAt`.** That's the latest of any write. It overstates progress for enrollments that were later rated, archived or opened, so stalled learners get reminded later than they should.
- **B. `createdAt`.** It understates progress, so every older unfinished enrollment looks stalled at once and could get a burst of reminders at release.
- **C. The release time (the moment the backfill runs).** Everyone's clock starts fresh, so no burst. Reminders for genuinely stalled enrollments start N days after release.
- **D. Leave it null and let ODY-931 decide** ("unknown": skip, or fall back to `createdAt`). Honest, but it pushes the rule onto ODY-931, and the AC asks for a starting value.
- Sub-question: do enrollments with **zero** viewed lessons (enrolled, never started) get the same value, or stay null (no progress ever)?

**Q5. Field name.** Tasks 1, 2 and 4 depend on this.
- **A. `lastProgressAt`.** Says it's a timestamp.
- **B. `lastProgressDate`.** Matches the existing `completionDate` and `dueDate` naming on enrollment.

**Q6. Does this ticket expose the field to readers?** Task 4 depends on this.
- **A. Types and mock only** (recommended). ODY-931 adds it to the `fields` and populate presets it actually reads (`getEnrollmentsByAuthorizedUser` defaults at `enrollment.ts:103-110`, `enrollment-populates.ts`). That keeps responses lean until something renders it.
- **B. Also add it to `getEnrollmentsByAuthorizedUser`'s default `fields` now,** so ODY-931 is a pure consumer. It adds bytes to every enrollments read, for no reader yet.

**Q7. What happens to `markLessonAsComplete`** (`lib/requests/lesson.ts:122`, an exported but unused endpoint that writes `viewedLessons`)?
- **A. Leave it alone.** It doesn't set last progress, which is acceptable while nothing calls it.
- **B. Make it set last progress too** (about 3 lines in PR 2).
- **C. File a follow-up ticket to delete it** (deleting needs approval, and it's a public endpoint with no caller).
