# ODY-630: Per-role AI limits that hold across servers

Measured on `develop` at `3b1783f4` (2026-11-10). Plan only, no code changes. Ticket owner: Awad Buisir. Overlaps ODY-501 / ODY-504 / ODY-649 (Jaylen Zeng), planned in `docs/plans/security-auth-plan.md` on `origin/claude/security-auth-plan`.

## Problem

`frontend/lib/import/rate-limiter.ts` is the only limit on most of Odyssey's paid Claude calls, and it has two flaws:

1. **Every role gets an authoring quota.** The ticket's line numbers are stale: ODY-884 (`8aa2645a`) added a `student` tier, so `getRoleTier` (`rate-limiter.ts:86-97`) no longer returns `"creator-editor"` for everyone. But `student` has the same numbers as `creator-editor` for every action (`:21-79`), so the effect is unchanged: a plain `User` gets 15 splits, 30 expands, 30 custom prompts, 15 auto-formats and 10 fun facts an hour. With the missing role gates on the AI imports (ODY-504), any signed-in account can spend Anthropic credit.
2. **Counts live in one process.** `usageStore` (`:84`) is an in-memory `Map`. Each ECS task counts separately (N tasks give N times the quota) and every deploy or restart resets it.

Also found: tiers read roles from the **session** (`getCurrentUser`, JWT) in the four AI imports and the bug report, not from Strapi as `requireRole` does, so a revoked role keeps its quota until re-login. The fun fact closure and `createLinearIssue` skip the limit entirely when there's no email (`draft/d/[slug]/page.tsx:133`, `lib/actions.ts:304-306`).

## Acceptance Criteria

- [ ] A user whose only role is `User` (or who has no role) gets 0 calls an hour for `split`, `expand`, `custom-prompt`, `auto-format` and `fun-fact`, and the refusal happens before any Anthropic client is created.
- [ ] Limits are counted in Strapi, so two ECS tasks share one count and a restart doesn't reset it (backend test: two concurrent takes at `limit - 1` give exactly one `allowed`).
- [ ] The tier comes from the user's roles **as stored in Strapi**, never from the session or a client argument.
- [ ] If the counter store is unreachable or errors, every paid action refuses (fail closed); the bug report still files, without the AI sections.
- [ ] No caller skips the limit when the user has no email or id: it refuses instead.
- [ ] The in-memory `usageStore` is gone; `mentor` and `ai-scoring` burst guards use the durable store too.
- [ ] Old counter rows are deleted (nothing older than 7 days remains after the daily prune).
- [ ] Role gates on the four AI imports and the bug report are **not** added here (owned by security PR 13 and PR 2); this ticket doesn't add or remove `PENDING_AUTH` entries.

## Design Decisions

### D1. Ownership split with the security plan

| Concern                                                                                                       | Owner                    |
| ------------------------------------------------------------------------------------------------------------- | ------------------------ |
| Tiers, numbers, the durable counter, fail-closed behaviour, keying by user id, the limiter's API              | **ODY-630 (this plan)**  |
| `requireRole([CC, Faculty, SysAdmin, CE])` on the 4 AI imports                                                | Security PR 13 (ODY-504) |

The limiter's call sites are touched by both. To avoid doing anything twice: PR 13 and PR 2 keep calling `checkRateLimit` as it exists when they merge, passing the gate user. ODY-630's PR C changes every call site to the new async API in one mechanical sweep. Whichever lands second rebases; the conflict is one line per caller. PR A (tier fix) deliberately makes the 4 imports safe **before** PR 13 lands, so the money leak closes even if ODY-504 slips: role gate (PR 13) and zero quota (PR A) are defence in depth, not duplicates.

### D2. Durable store: a Strapi collection with a unique key and a row lock

Options compared:

1. **Strapi collection `ai-usage-counter`** (`key` unique, `count`), incremented inside `strapi.db.transaction` with a `forUpdate()` row lock, and `retryIfKeyTaken` for the first insert race. Pros: the exact pattern of `lockReview` / `retryIfKeyTaken` in `backend/src/lib/review-scores.ts:56-110` and the `reviews_key_uq` index (`review/schema.json:14-20`); Document Service only, so `no-entity-service.test.js` passes; Strapi creates the table, visible in the admin; tests run on the existing SQLite harness. Cons: two or three queries per take instead of one.
2. **Raw Postgres table with `INSERT … ON CONFLICT (key) DO UPDATE SET count = count + 1 WHERE count < $limit RETURNING count`.** Pros: one atomic statement. Cons: a hand-written migration in `backend/database/migrations` (none exist yet); a raw insert into a Strapi-managed table must also invent `document_id`, `created_at`, etc., so it would have to be a non-Strapi table, invisible in the admin; the backend tests default to SQLite (`config/database.ts:4`), so the SQL must work on both; it's a new pattern in this repo.
3. **Reuse Mentor's store** (`mentor-usage`: one row per answer, counted with `mentorAnswersToday`). Pros: exists. Cons: it's an event log with Mentor-specific required fields (`kind` enum, tokens); its check is read-only and unlocked by design (`backend-architecture.md:330`), so concurrent calls overshoot; counting rows per hour per action grows the table by one row per call.

**Recommendation: option 1.** It's atomic under the row lock (Postgres) or SQLite's single writer, follows existing code, and needs no migration. Load is tiny (tens of takes an hour), so the extra queries don't matter.

**Take-then-call:** the slot is taken (count incremented) _before_ the model call and not refunded on failure. That makes the check and the reservation one locked step (no overshoot from in-flight calls, unlike Mentor's read-only check), and a failed call may still have cost tokens.

### D3. Window and reset

Fixed hourly windows on UTC hour boundaries. Key: `<userId>:<action>:<YYYY-MM-DDTHH>` (UTC), e.g. `412:split:2026-11-10T14`. `retryAt` = the end of the hour. This replaces the 1-hour sliding window; a user can get up to 2× the limit across one boundary, which is acceptable at these sizes and keeps one row per user/action/hour. Hourly matches today's semantics and messages (`formatRateLimitError`), so no UI change.

### D4. Tiers are resolved in Strapi

The route takes `{ userId, action }`, loads the authorized-user's roles itself (`populate: { roles: { fields: ['title'] } }`), and picks the tier with today's precedence (System Admin > Faculty > Content Creator/Editor > user). The frontend never sends roles or limits. This removes the session-vs-Strapi role gap and makes the backend the single source for numbers. Unknown user → 404 → frontend refuses.

### D5. Per-role limits (per hour), configured in `backend/src/lib/ai-limits.ts`

| Action          | System Admin | Faculty | Content Creator / Editor | User (no AI) | Notes                                                                       |
| --------------- | -----------: | ------: | -----------------------: | -----------: | --------------------------------------------------------------------------- |
| `split`         |          100 |      20 |                       15 |        **0** | was 1000 / 20 / 15 / 15                                                     |
| `expand`        |          200 |      50 |                       30 |        **0** | was 1000 / 50 / 30 / 30                                                     |
| `custom-prompt` |          200 |      50 |                       30 |        **0** | was 1000 / 50 / 30 / 30                                                     |
| `auto-format`   |          100 |      20 |                       15 |        **0** | was 1000 / 20 / 15 / 15                                                     |
| `fun-fact`      |          100 |      20 |                       10 |        **0** | was 1000 / 20 / 10 / 10                                                     |
| `bug-report`    |           20 |      10 |                        5 |            5 | students file bug reports; over the limit the report still files without AI |
| `ai-scoring`    |           30 |      10 |                       10 |            0 | role-gated to SA/CE anyway; monthly cap stays in Strapi                     |
| `overview-scan` |           10 |      10 |                       10 |           10 | not AI except spelling (shares the Score with AI cap); authors only         |
| `mentor`        |           60 |      20 |                       20 |           20 | burst guard; the daily limit and monthly cap stay in `mentor-setting`       |

System Admin drops from 1000 to 100–200 (Q2): with durable counts, 1000 an hour per action is a real bill if an admin account is misused. Numbers live in one exported constant, `AI_LIMITS`, in code (reviewed, test-pinned), not an admin-editable single type (Q3). The tier name changes from `student` to `user` to match the role title.

### D6. Store down: fail closed

Frontend `takeAiSlot` returns `{ allowed: false, reason: "unavailable" }` on a network error, any non-2xx, or a malformed body, with the message "AI is unavailable right now. Try again in a few minutes." Callers treat it like a limit refusal. Exception: `createLinearIssue` skips the AI sections (today's placeholder path), so a bug report still files. Mentor maps `unavailable` to its existing 503 `unavailable` reason.

### D7. Pruning

No cron exists (`grep cron backend/config` is empty). Enable Strapi cron in `backend/config/server.ts` (`cron: { enabled: true, tasks }`) with one task at 04:00 UTC deleting rows whose `windowStart` is older than 7 days. Every ECS task runs it; the delete is idempotent. 7 days keeps a week for abuse review.
