# ODY-930: Nudges: unread count on My Feed

Parent: ODY-927 (Nudges). Siblings: ODY-928 (last progress per enrollment), ODY-929 (Reminder feed item). Status: **plan only, awaiting Jaylen's approval and answers to Q1–Q8.** Planned in a cloud session with no access to Linear, Slack or Figma.

## Problem

Reminders (ODY-929) only help if learners notice them, and nothing in the nav shows unread feed items today. `FeedLeftNav` (`frontend/components/feed/feed-left-nav.tsx`) renders a static `TABS` list with no counts. `getUnreadAnnouncementCount` (`frontend/lib/requests/feed.ts:795`) exists ("Used for the nav badge") but only `testing/requests/feed.test.js:289` calls it.

## Acceptance Criteria

- [ ] A badge on the **My Feed** link (label from `components/feed/feed-left-nav.tsx`) shows the number of items the **Unread** tab (`components/feed/feed-client.tsx`) shows. What counts as "shows" depends on Q2–Q5.
- [ ] Clicking **Mark as read** (`components/feed/feed-block.tsx`) on an item that can be marked read lowers the badge by 1. **Mark as unread** raises it by 1. How soon depends on Q1.
- [ ] The badge is hidden at 0.
- [ ] Counts over 99 display as "99+".
- [ ] Screen readers hear the count with the link (wording: Q7).

## Out of Scope

- ODY-929's reminder card and filter, ODY-928, ODY-931/932/933.
- Per-user read state for global broadcasts (needs a join table; see Q4).
- Showing review outcomes in the Unread tab (see Q3), unless Jaylen chooses Q3(b).
- A mobile badge: the left nav is `hidden … md:block` (`components/feed/feed-container.tsx`), so phones have no My Feed link today (Q7).

## Current behaviour (develop @ 1fb372e)

- **Unread tab query.** `FeedClient` calls `fetchAnnouncements(page, roles, { archived: false })` (`feed-client.tsx`), which filters `readAt: { $null: true }` and, whenever `roles` is non-empty, `type: { $in: roles }` (`lib/requests/feed.ts`, `fetchAnnouncements`). Page size is 25.
- **Filters change the tab.** `roles` come from the `?filters=` pills (`components/feed/feed-center-content.tsx`). The default is every `AnnouncementTypeTitle` value: Droplet, Playlist, Group, System, Friend, Kudos (`lib/globals.ts:9`, `components/feed/feed-filter-params.ts`). Filter changes use `history.replaceState` with no server round trip (`feed-center-content.tsx`).
- **Review outcomes never show in the tab.** `review_feedback` and `review_published` are announcement types (`backend/src/api/announcement/content-types/announcement/schema.json`), and `fetchAnnouncements` matches them for the recipient (`feed.ts:162`). But they aren't in `AnnouncementTypeTitle`, so the default `type $in` filter drops them. `getUnreadAnnouncementCount` passes `roles = undefined` (no type filter), so it **counts them**.
- **Global broadcasts can't be marked read.** `assertAnnouncementOwnership` (`feed.ts`) rejects `authorized_user = null` rows with "Broadcast announcements cannot be marked read". The tab still shows the button (`onMarkRead` is passed for every unread item in `feed-client.tsx`), so clicking it shows the "Failed to mark as read" toast and the item comes back.
- **Mark read/unread** are Server Actions that PUT `readAt` and then call `revalidateReadState`. That revalidates `CACHE_TAGS.userFeed(ownerId)` for system rows and `CACHE_TAGS.announcements` otherwise (`feed.ts:783`). `fetchAnnouncements` carries both tags (`feed.ts:254`). `FeedClient` removes the item optimistically, then refetches silently.
- **Server re-render after an action.** Because the actions call `revalidateTag`, Next re-renders the current route. `FeedClient` notes that this sends a fresh `initialFeed` but ignores it (`feed-client.tsx`, `seed` comment). The activity layout (`app/(general)/activity/layout.tsx`) is a Server Component that renders `FeedContainer` (client), which renders `FeedLeftNav` (client).
- **Streak card (ODY-919).** `useStreakFeedCard` (`components/streaks/streak-feed-card.tsx`) adds one card to the top of page 1 of the Unread tab when the learner's latest unlock isn't read. Read state is the `streak-card-read:{userId}` key in localStorage, held in the hook's own `useState`. The streak itself is in `useStreakStore` (`stores/streak-store.ts`), which the header's `StreakPill` hydrates on every page (`components/streaks/streak-pill.tsx:26`). Filters don't affect the card.
- **Count cost.** `getUnreadAnnouncementCount` runs the full `fetchAnnouncements`: 4 ID lookups, then a fully populated 25-row page, all cached 900s. On `/activity` with default filters it would not share the page's cache entry, because the page passes the 6 roles and the count passes none (different URL).
- **Auth.** `getUnreadAnnouncementCount` is on the server-action auth allowlist (`testing/security/server-action-auth-allowlist.ts:78`, ODY-506). It takes the viewer from the session. If its signature changes, the allowlist key stays the same.

## Ticket premises the code contradicts

1. **"`getUnreadAnnouncementCount` … for the nav badge":** as written it doesn't match the Unread tab. It counts review outcomes the tab never shows and ignores the filter pills (see Current behaviour).
2. **"Marking an item read lowers it":** not for global system broadcasts. The action refuses them, so any broadcast keeps the badge at ≥ 1 for every learner until per-user read state exists (Q4).
3. **"Badge on My Feed in the Activity left nav":** that nav only exists at `md` and wider. There's no badge location on phones (Q7).

## Design questions (Jaylen to answer)

**Q1. Where the count lives and how it stays in sync.** Tasks 2, 4, 5.
- (a) **Server prop.** The activity layout fetches the count and passes it through `FeedContainer` into `FeedLeftNav`. Mark-read updates it through the route re-render that `revalidateTag` already triggers. Smallest change (no client state). The badge lags the optimistic removal by one round trip. It can't follow filter pills (Q2b) or the localStorage streak card (Q5a) without client help.
- (b) **Client store, seeded by the server.** A small zustand store (like `stores/streak-store.ts`) is seeded from the layout's count. `FeedClient` sets it from each Unread fetch's `pagination.total` and adjusts it ±1 on optimistic mark read/unread. Matches the tab exactly and instantly, and Q5a's streak card can add to it. More moving parts (~60 more lines). Two writers, so `FeedClient` must own the value while it's mounted.
- (c) **Client fetch.** `FeedLeftNav` calls `getUnreadAnnouncementCount` on mount and after each mutation (an event from `FeedClient`). No layout change, but an extra Server Action round trip per page and per click, plus a loading flash.

**Q2. Do the filter pills change the badge?** Tasks 1, 2.
- (a) **No.** The badge counts all of the tab's default types, so with every pill on it matches the tab. Simple, and it's what a nav badge usually means. With some pills off, it's higher than the tab.
- (b) **Yes.** The badge counts the current `?filters=` selection, so it always matches the visible tab. Needs Q1(b), because filters change client-side only. On other Activity pages the badge shows the default count, so it can change just from navigating.

**Q3. Review outcomes (`review_feedback`, `review_published`).** Task 1.
- (a) **Exclude them from the badge** (pass the tab's default types), so the badge matches the tab. Unread review outcomes stay invisible, as they are today.
- (b) **Fix the tab to show them**, e.g. by adding them to the default roles. Then badge and tab both count them. That's a feed behaviour change and probably its own ticket.
- (c) **Count them anyway** (today's `getUnreadAnnouncementCount`). Breaks "the badge matches the Unread tab".

**Q4. Global broadcasts (system rows with no `authorized_user`).** Task 1.
- (a) **Count them.** Matches the tab, but the badge can never reach 0 once a broadcast exists, which defeats "hidden at 0".
- (b) **Exclude them from the badge** (`authorized_user` not null for system). Count can always reach 0, but badge ≠ tab while broadcasts exist.
- (c) **Count them, and file a follow-up ticket** for per-user read state (join table) so they can be marked read. ODY-930 ships with (a)'s limitation until then.

**Q5. Does the streak card count?** Tasks 2, 5.
- (a) **Yes, +1 while it's unread.** Matches the tab. The read key moves from the hook's `useState` into shared client state (with Q1b) so marking it read in the feed lowers the badge. Then the badge can only include it after hydration, a short client-side jump from N to N+1.
- (b) **No.** The badge counts announcements only and stays server-rendered. It's 1 lower than the tab whenever the streak card is unread.

**Q6. What the badge needs from ODY-929 (reminders).** Task 1. Not blocking: the badge ships for what's on develop.
- If reminders are **announcement rows with a new `type`**, they're counted automatically as long as that type is in the badge's type list. The badge should use ODY-929's list (e.g. its addition to `AnnouncementTypeTitle`/filters) rather than its own copy. If ODY-929's "hide reminders" filter should also hide them from the badge, that's Q2(b).
- If reminders are **derived client-side** (like the streak card), ODY-929 needs to expose an unread count (a hook or store field) that the badge adds, which requires Q1(b).
- Question: which does ODY-929 choose? Whichever it is, the contract should go in that plan or a `[CONTRACT]` post.

**Q7. Visuals (Figma "Nudges / Reminders" → Unread Badge couldn't be opened).** Task 3.
- Placement: right-aligned pill at the end of the row (`ml-auto`) vs. a dot/counter overlapping the icon.
- Colour: brand teal `#287697` (used for active nav, `feed-left-nav.tsx`) vs. a red/alert colour. Active and dark-mode variants.
- Size/shape and font: e.g. `min-w-5 h-5 rounded-full text-xs`.
- Accessible name: e.g. "My Feed, 12 unread" via visually hidden text. Exact wording?
- Mobile: no badge (no left nav below `md`), or add one somewhere else (out of scope?).

**Q8. How the count is queried.** Task 1.
- (a) **Reuse `fetchAnnouncements(1, roles)`** and read `pagination.total`. No new query code. On `/activity` it shares the page's cache entry when the arguments match exactly. Elsewhere it costs 5 Strapi queries plus a populated page.
- (b) **A lean count query.** Same filters built by a shared helper extracted from `fetchAnnouncements`, but `fields: ["id"]`, no populate, `pageSize: 1`, same tags. Cheaper on every Activity page, but ~40 more lines, a small refactor of `fetchAnnouncements`, and the helper keeps the two in sync.

## Design Decisions (settled by the code, not by choice)

- No backend change: unread is `readAt = null` on existing announcement rows.
- Cache tags: reuse `CACHE_TAGS.announcements` and `CACHE_TAGS.userFeed(userId)` (`lib/cache-tags.ts`). No new tag, since mark read/unread already revalidate them.
- Display rule lives in one pure helper: `count <= 0` → nothing, `> 99` → "99+".
- Code comments stay 1–2 lines.
